<Brief>

**Аутентификация (authentication)** отвечает на вопрос «кто ты?» — пароль, сертификат, токен, второй фактор. **Авторизация (authorization)** отвечает на вопрос «что тебе можно?». Первая без второй бесполезна: войти — не значит иметь право на всё. Ошибка аутентификации — 401, ошибка авторизации — 403.
Авторизация бывает двух уровней: **операции** («руководитель может смотреть доступы») и **объекта** («…но только своих подчинённых»). Второй уровень чаще всего забывают — и это самая частая уязвимость API.
Модели: **RBAC** — права через роли, **ABAC** — права по атрибутам пользователя, объекта и контекста. Принципы: **минимальные привилегии (least privilege)** и **разделение обязанностей (SoD)**. **Сервисные учётные записи** подчиняются тем же правилам, что и люди.

</Brief>

## Когда применять

| Применять | Не нужно / проще |
|---|---|
| Описываете роли, экраны, отчёты, операции API | Публичная информация без входа (например, справочник отделений на сайте) |
| Новая интеграция: под какой учётной записью и с какими правами работает система | — |
| Разбираете дефект «пользователь видит лишнее» или «не может сделать положенное» | — |
| Готовите ролевую модель для IdM или для своей системы | — |

## Как делать

<Steps>

1. **Перечислить субъектов:** пользователи по ролям, системы, администраторы, аудиторы. Для каждого — как он аутентифицируется (SSO, сертификат, client credentials).

2. **Составить матрицу «роль × операция».** Для каждой операции — кто может, кто нет. Чтение и изменение — разные операции.

3. **Для каждой операции добавить правило на уровне объекта:** «только свои», «только своего подразделения», «только назначенные мне». Записать, откуда система берёт эту связь (оргструктура, назначение согласующего).

4. **Проверить минимальность:** нет ли у роли прав «на всякий случай»; нужны ли права на изменение, если достаточно чтения.

5. **Описать несовместимые права (SoD)** и что происходит при конфликте: запрет, согласование ИБ, компенсирующий контроль.

6. **Описать сервисные учётные записи:** владелец, права, где хранится секрет, кто и как меняет секрет.

7. **Написать негативные тесты:** чужой объект, нет роли, заблокированный пользователь, конфликт SoD.

</Steps>

## Нотация

### Аутентификация и авторизация

| | Аутентификация | Авторизация |
|---|---|---|
| Вопрос | Кто ты? | Что тебе можно? |
| Чем | Пароль, сертификат, токен, Kerberos-билет, второй фактор | Роли, права, атрибуты, правила |
| Ошибка в HTTP | 401 Unauthorized — нет или недействительны учётные данные | 403 Forbidden — личность известна, прав нет |
| Протоколы | OIDC, Kerberos, SAML 2.0, mTLS | OAuth 2.0 (scopes), ролевая модель приложения |

Название кода 401 — «Unauthorized», хотя по смыслу это ошибка аутентификации: так исторически сложилось в HTTP.

**Факторы аутентификации:** знание (пароль), владение (телефон, токен, смарт-карта), свойство (биометрия). Многофакторная аутентификация (MFA) — минимум два **разных** фактора; два пароля — не MFA.

### Модели доступа

| Модель | Как выдаются права | Хорошо для | Слабое место |
|---|---|---|---|
| **RBAC** (role-based) | Пользователю назначают роли, роли содержат полномочия | Типовые должности, понятный аудит «кто что может» | Взрыв ролей, если учитывать все исключения |
| **ABAC** (attribute-based) | Правило по атрибутам: пользователя (подразделение), объекта (владелец, сумма), контекста (время, канал) | «Только своего подразделения», «до лимита суммы», «только в рабочее время» | Сложнее объяснить и проверить, кто что может |
| **ACL** (access control list) | Список доступа у каждого объекта | Файлы, папки, топики брокера | Плохо масштабируется на тысячи пользователей |

На практике модели сочетают: роль даёт право на операцию (RBAC), а атрибуты ограничивают объекты (ABAC). Например, роль «Руководитель» разрешает смотреть доступы сотрудников, а правило «сотрудник — подчинённый» ограничивает, чьи именно.

### Принципы

| Принцип | Смысл | Пример требования |
|---|---|---|
| Минимальные привилегии | Только права, нужные для работы, и только на время работы | «Роль Просмотр выдаётся вместо Операциониста, если нужно только чтение» |
| Разделение обязанностей (SoD) | Критичную операцию не выполняет один человек от начала до конца | «Ввод и подтверждение операции — разные сотрудники» |
| Необходимость знать (need-to-know) | Данные видит только тот, кому они нужны для задачи | «Руководитель видит доступы только подчинённых» |
| Запрет по умолчанию (deny by default) | Всё, что не разрешено явно, запрещено | «Новая операция API недоступна, пока не назначена роль» |

### Сервисные учётные записи

| Правило | Почему |
|---|---|
| У каждой есть владелец | Иначе некому пересматривать права и менять секрет |
| Права — минимальные для интеграции | Компрометация системы не должна давать больше, чем ей нужно |
| Люди под ней не входят | Иначе журнал не покажет, кто на самом деле действовал |
| Секрет — в хранилище секретов, со сроком замены | Пароль, который не меняется годами, знают все, кто когда-либо настраивал интеграцию |
| Отдельная учётная запись на каждую интеграцию и среду | Отзыв одной не ломает остальные |

## Пример из кейса IDM-JOINER

- **RBAC.** <CaseRef href="/case/02-requirements/role-model/" id="Ролевая модель">Ролевая модель</CaseRef>: полномочия (ENT-…) объединены в роли (ROLE-01 «Операционист розничного офиса»), роли назначаются правилами по подразделению и должности (RULE-01).
- **SoD.** SOD-01: «Операционист» и «Контролёр» в АБС — один человек вводил бы и подтверждал операцию. IdM проверяет конфликт до выдачи (FR-12, SEC-02).
- **Минимальные привилегии для сервисных учётных записей.** Коннектор AD создаёт пользователей и управляет группами только в OU пользователей, без прав на административные группы (SEC-07). Административные права выдаются только через PAM (SEC-11).
- **Авторизация на уровне объекта.** В <CaseRef href="/case/05-security/threat-model/" id="THR">матрице доступа к API IdM</CaseRef> для каждой операции указано не только «кто вызывает», но и «с какими объектами»: руководитель — только подчинённые (SEC-10), согласующий — только назначенные ему позиции и не свои заявки (THR-10). Отказ для чужого сотрудника — 404, чтобы перебором номеров нельзя было выяснить, кто работает в банке (THR-05).

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Проверять только роль, без объекта | Руководитель меняет номер в URL и видит чужих сотрудников | Правило на уровне объекта для каждой операции |
| Проверка прав только в интерфейсе (кнопка скрыта) | Вызов API напрямую проходит | Авторизация на сервере для каждого запроса |
| Роль «на всякий случай» с широкими правами | Нарушение минимальных привилегий, лишний ущерб при ошибке или компрометации | Права под задачу; чтение отдельно от изменения |
| Одна сервисная учётная запись на все интеграции | Компрометация одной системы даёт доступ ко всем; нельзя отозвать точечно | Отдельная учётная запись на интеграцию и среду |
| Путать 401 и 403 | Клиент повторяет вход вместо запроса прав или наоборот | 401 — кто ты неизвестно, 403 — известно, но нельзя |
| Самосогласование | Заявитель одобряет свои права | Заявитель не может быть согласующим своей заявки |
