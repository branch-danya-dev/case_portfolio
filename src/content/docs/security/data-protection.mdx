<Brief>

Данные защищают на двух участках: **при передаче (in transit)** — TLS и mTLS на каждом соединении — и **при хранении (at rest)** — шифрование дисков, БД, резервных копий, а для самого чувствительного — отдельных полей. Пароли не шифруют, а **хэшируют**.
Шифрование не помогает, если ключ лежит рядом с данными: **ключи и секреты** хранятся отдельно, в хранилище секретов.
Лучшая защита данных — **не собирать лишнего**. Аналитик описывает, какие **персональные данные (ПДн)** и тайны есть в системе, зачем каждое поле, куда оно передаётся, где маскируется. Логи и тестовые среды — главные места утечек.

</Brief>

## Когда применять

| Применять | Не нужно / проще |
|---|---|
| В системе есть ПДн, банковская тайна, данные карт, коммерческая тайна | Выбор алгоритмов и средств шифрования — решение ИБ и архитектора |
| Новая интеграция передаёт данные о людях | — |
| Проектируете модель данных, маппинг, логи, выгрузки, отчёты | — |
| Готовите тестовые данные или копию для анализа | — |

## Как делать

<Steps>

1. **Классифицировать данные:** для каждой сущности и поля — категория (ПДн, банковская тайна, данные карт, публичные, внутренние). Без классификации нельзя решить, как защищать.

2. **Минимизировать:** для каждого поля ПДн — зачем оно нужно этой системе. Если незачем — не передавать и не хранить.

3. **Описать передачу:** каждое соединение — защищённый канал (TLS, mTLS). Какие поля уходят в какую систему — в маппинге, с пометкой ПДн.

4. **Описать хранение:** где лежат данные, шифруются ли, кто имеет доступ, сколько хранятся и как удаляются по истечении срока.

5. **Описать отображение:** где поля маскируются (номер карты, телефон, паспорт), кто видит полностью и фиксируется ли просмотр в журнале.

6. **Закрыть побочные каналы:** логи, сообщения об ошибках, выгрузки, письма, тестовые среды, аналитические копии.

7. **Перечислить секреты** интеграций: где хранятся, кто владелец, как меняются.

</Steps>

## Нотация

### Шифрование

| Где | Чем | Что пишет аналитик |
|---|---|---|
| Передача между системами | TLS (версия по требованию ИБ, обычно не ниже 1.2), mTLS для систем | «Все интеграции — по защищённому каналу; системные клиенты — с взаимной аутентификацией» |
| Хранение: диски, БД, резервные копии | Шифрование тома или БД | «Данные и резервные копии хранятся в зашифрованном виде» |
| Хранение: отдельные поля | Шифрование на уровне приложения, токенизация | Какие поля — по классификации (например, номер документа) |
| Пароли пользователей | Хэширование специальной функцией с солью — **не шифрование** | «Пароли хранятся только в виде хэша; восстановить пароль нельзя, только сбросить» |
| Ключи | Хранилище секретов, отдельно от данных | «Ключи шифрования и секреты не хранятся вместе с данными и в конфигурации» |

<Check id="sec-03">
В каких случаях банку и его информационным системам обязательна российская криптография (ГОСТ) и сертифицированные СКЗИ — для внешних и внутренних каналов, для ПДн.
</Check>

### Персональные данные и тайны

| Категория | Примеры | На что обратить внимание |
|---|---|---|
| ПДн | ФИО, телефон, табельный номер в связке с ФИО, адрес, паспорт | Цель обработки, минимизация, срок хранения, кому передаются |
| Специальные и биометрические ПДн | Здоровье, биометрия | Отдельные, более строгие правила — сразу к ИБ и юристам |
| Банковская тайна | Счета, операции, остатки клиентов | Доступ только по служебной необходимости, журнал просмотра |
| Данные платёжных карт | Номер карты, срок, CVV | Отдельный стандарт отрасли; CVV не хранится вообще |

Обработку ПДн в России регулирует 152-ФЗ «О персональных данных». Для аналитика главное — принципы: обрабатывать **для заявленной цели**, **не больше, чем нужно**, **не дольше, чем нужно**, и защищать по требованиям ИБ.

<Check id="sec-02">
Требования к локализации баз ПДн граждан РФ и к уровням защищённости ПДн в информационных системах (постановление Правительства № 1119?) — формулировки и применимость к внутренним системам банка.
</Check>

### Где утекают данные

| Место | Что случается | Требование |
|---|---|---|
| Логи | ФИО, телефон, токен, тело запроса целиком | Логировать идентификаторы, не значения ПДн; токены и пароли — никогда |
| Сообщения об ошибках | Стек вызова, SQL, чужие данные в тексте ошибки | Пользователю — общий текст и идентификатор ошибки, детали — в лог |
| Тестовые среды | Копия продуктивной БД | Обезличивание или синтетические данные |
| Выгрузки и отчёты | Полные данные «на всякий случай» | Только нужные поля, маскирование, журнал выгрузок |
| Письма и уведомления | Пароль или ПДн в теле письма | Ссылка на систему вместо данных; пароль — отдельным каналом |
| URL | ПДн в параметрах запроса оседают в логах прокси и истории браузера | ПДн — только в теле запроса |

## Пример из кейса IDM-JOINER

- **Минимизация** (<CaseRef href="/case/05-security/security-requirements/#sec-09" id="SEC-09">SEC-09</CaseRef>, NFR-09): в IdM не передаются паспортные данные, дата рождения, адрес. Мобильный телефон нужен только для отправки одноразового пароля и в AD не передаётся. Ограничения по полям — в маппинге данных.
- **Передача:** все интеграции — TLS 1.2+, API — mTLS + OAuth 2.0 (SEC-08, NFR-07).
- **Секреты:** учётные данные коннекторов — только в хранилище секретов (NFR-08, SEC-07).
- **Логи:** структурированные, с идентификаторами (`personId`, `taskId`) вместо ФИО и телефона.
- **Пароль:** первичный пароль одноразовый, только по SMS, не передаётся по почте и не показывается в интерфейсах (SEC-04).
- **Тестовые среды:** в <CaseRef href="/case/06-rollout/release-plan/" id="Релиз 1.0">плане релиза</CaseRef> реальные ПДн есть только в PROD, а на UAT и PREPROD используется обезличенный срез.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Передавать все поля «вдруг пригодятся» | Больше данных — больше ущерб при утечке, нарушение принципа минимизации | Каждое поле ПДн — с обоснованием |
| «Пароли шифруем» | Зашифрованный пароль можно расшифровать | Хэширование, восстановление только через сброс |
| Ключ шифрования в конфигурации рядом с БД | Шифрование не защищает от того, кто получил доступ к серверу | Ключи — в хранилище секретов |
| Тело запроса целиком в лог | ПДн и токены оказываются в системе логирования, доступной многим | Логировать идентификаторы и коды |
| Продуктивная копия на тесте | Утечка ПДн и тайны | Обезличивание, синтетика |
| Не указан срок хранения | Данные хранятся вечно | Срок и порядок удаления в требованиях |
