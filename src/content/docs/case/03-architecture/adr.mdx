Автор: Архитектор решения (при участии СА) · Утверждает: Архитектурный комитет

ADR (Architecture Decision Record) фиксирует одно значимое решение: контекст, рассмотренные варианты, выбор и его последствия. Через год никто не вспомнит, почему выбрали Kafka, а не REST, — ADR отвечает на этот вопрос.

## <span id="adr-001" class="case-anchor" />ADR-001. Получение кадровых событий

**Статус:** Принято

**Контекст.** IdM должна узнавать о приёме как можно раньше ([BR-01](/case/01-business/business-requirements/#br-01)) и не терять события ([NFR-05](/case/02-requirements/non-functional-requirements/#nfr-05)). Команда HRMS может выделить не более 2 спринтов.

**Варианты.**

| Вариант                              | Плюсы                                                                    | Минусы                                                                          |
| ------------------------------------ | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| A. HRMS вызывает REST API IdM        | Просто, синхронный ответ                                                 | HRMS должна обрабатывать недоступность IdM и повторять вызовы; связность систем |
| B. IdM опрашивает HRMS по расписанию | Не нужна доработка публикации в HRMS                                     | Задержка до интервала опроса; нагрузка на HRMS; сложно отличить изменения       |
| C. HRMS публикует события в Kafka    | Слабая связность, гарантия доставки, событие могут читать другие системы | Нужна идемпотентность на стороне IdM; зависимость от шины                       |

**Решение.** Вариант C плюс ежедневная сверка полным срезом ([FR-05](/case/02-requirements/functional-requirements/#fr-05)) как страховка от потерянных событий и ошибок публикации.

**Последствия.** Нужны идемпотентность ([FR-03](/case/02-requirements/functional-requirements/#fr-03)), DLQ ([FR-02](/case/02-requirements/functional-requirements/#fr-02)), AsyncAPI-контракт, согласованный с командой интеграции.

## <span id="adr-002" class="case-anchor" />ADR-002. Момент создания учётных записей

**Статус:** Принято

**Контекст.** Доступы должны быть готовы к 09:00 первого дня ([BR-04](/case/01-business/business-requirements/#br-04)), но не активны до него. Часть систем (АБС, СЭД) может обрабатывать запрос часами или требовать ручного шага.

**Варианты.** A — создавать в день выхода; B — создавать заранее в заблокированном состоянии и активировать утром.

**Решение.** Вариант B, за 3 рабочих дня ([BRL-01](/case/01-business/to-be/#brl-01)). Этого достаточно, чтобы закрыть ручную задачу СЭД и разобрать сбои.

**Последствия.** Появляются статус CREATED_DISABLED и плановая активация; при отмене приёма нужно удалять созданные учётные записи ([FR-18](/case/02-requirements/functional-requirements/#fr-18)); активация должна учитывать часовой пояс ([FR-08](/case/02-requirements/functional-requirements/#fr-08)).

## <span id="adr-003" class="case-anchor" />ADR-003. Интеграция с АБС

**Статус:** Принято

**Контекст.** У АБС нет публичного API администрирования пользователей. Политика ИБ запрещает прямой доступ к БД АБС.

**Варианты.** A — запись напрямую в таблицы АБС; B — эмуляция действий администратора через UI (RPA); C — REST-адаптер над внутренними административными функциями АБС.

**Решение.** Вариант C. Адаптер разрабатывает команда АБС, контракт описывает СА проекта.

**Последствия.** Дополнительная команда в критическом пути проекта (риск по срокам); адаптер переиспользуется в волнах 2–3 и другими системами.
