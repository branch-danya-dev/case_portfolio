Статусная модель описывает, **в каких состояниях может находиться объект и какие события переводят его из одного состояния в другое**. Это одно из самых полезных для разработки и тестирования описаний: каждый переход — это тест-кейс, а каждый «запрещённый» переход — негативный тест.

Нотация перехода в UML: `Событие [условие] / действие`.

## 1. Учётная запись — таблица переходов

| Из               | В                | Событие             | Условие                              | Действие                                  |
| ---------------- | ---------------- | ------------------- | ------------------------------------ | ----------------------------------------- |
| —                | PLANNED          | Роли определены     | —                                    | Запланировать создание на T−3 рабочих дня |
| PLANNED          | CREATING         | Таймер              | Наступила дата создания              | Создать задачу провижининга CREATE        |
| PLANNED          | —                | HIRE_CANCELLED      | —                                    | Удалить план                              |
| CREATING         | CREATED_DISABLED | Ответ коннектора    | Успех                                | Сохранить `external_id`                   |
| CREATING         | FAILED           | Ответ коннектора    | Повторы исчерпаны или бизнес-ошибка  | Задача в ServiceDesk                      |
| FAILED           | CREATED_DISABLED | Webhook ServiceDesk | Задача закрыта как выполненная       | Запросить `external_id` у администратора  |
| CREATED_DISABLED | ACTIVE           | Таймер              | Дата выхода, 07:00 по часовому поясу | Разблокировать                            |
| CREATED_DISABLED | DELETED          | HIRE_CANCELLED      | —                                    | Удалить в целевой системе                 |
| FAILED           | DELETED          | HIRE_CANCELLED      | —                                    | Отменить задачу ServiceDesk               |
| ACTIVE           | DELETED          | Увольнение          | Волна 2                              | —                                         |

Запрещённые переходы (негативные тесты): ACTIVE → CREATED_DISABLED; DELETED → любой; PLANNED → ACTIVE без создания.

## 2. Задача провижининга — таблица переходов

| Из          | В           | Событие             | Условие                            | Действие                                                              |
| ----------- | ----------- | ------------------- | ---------------------------------- | --------------------------------------------------------------------- |
| —           | SCHEDULED   | Создание задачи     | —                                  | —                                                                     |
| SCHEDULED   | IN_PROGRESS | Таймер              | Наступило `scheduled_at`           | Вызов коннектора с ключом `task_id`                                   |
| SCHEDULED   | CANCELLED   | HIRE_CANCELLED      | —                                  | —                                                                     |
| IN_PROGRESS | DONE        | Ответ               | Успех                              | Запись в журнал аудита                                                |
| IN_PROGRESS | RETRY_WAIT  | Ответ               | Техническая ошибка, `attempts < 3` | `attempts++`, задержка 1 мин после первой попытки, 5 мин после второй |
| RETRY_WAIT  | IN_PROGRESS | Таймер повтора      | —                                  | Повторный вызов с тем же ключом                                       |
| IN_PROGRESS | MANUAL      | Ответ               | `attempts = 3` или бизнес-ошибка   | Задача в ServiceDesk, уведомление руководителю                        |
| MANUAL      | DONE        | Webhook ServiceDesk | Задача закрыта                     | Запись в журнал аудита                                                |
| MANUAL      | CANCELLED   | HIRE_CANCELLED      | —                                  | Отменить задачу ServiceDesk                                           |

## 3. Идентичность и заявка

Переходы показаны на диаграммах [`state-identity.puml`](/case/diagrams/#state-identity) и [`state-access-request.puml`](/case/diagrams/#state-access-request). Особенности:

- Идентичность из TERMINATED и CANCELLED может вернуться в PRE_HIRE — это повторный приём того же `personId` ([BRL-05](/case/01-business/to-be/#brl-05)).
- Заявка согласуется по позициям, поэтому существует статус PARTIALLY_COMPLETED: например, VPN согласован, а роль «Контролёр» отклонена.
