## 2. Большая картина: слои проекта

```
ЗАЧЕМ     00_project        Устав, стейкхолдеры, глоссарий     → цели, границы, участники
ЧТО       01_business       AS-IS, TO-BE, gap, БТ              → что меняется для бизнеса
          02_requirements   Use case, ФТ, НФТ, роли, бэклог    → что должна делать система
КАК       03_architecture   C4, данные, статусы, ADR           → из чего состоит, что хранит
          04_integrations   Карта, sequence, маппинг, API      → с кем и как обменивается
ЗАЩИТА    05_security       Требования ИБ                      → ограничения безопасности
ЗАПУСК    06_rollout        Миграция, внедрение                → как перейти от старого к новому
ПРОВЕРКА  07_testing        ПМИ, тест-кейсы                    → как доказать, что работает
ЖИЗНЬ     08_operations     Сопровождение, мониторинг, инциденты → как эксплуатировать и развивать
```

Каждый слой отвечает на вопросы предыдущего и даёт вход следующему.

- **Требования идут вниз.** Цель → БТ → ФТ → контракт → тест.
- **Вопросы и противоречия идут вверх.** Пример из кейса: при маппинге выяснилось, что код подразделения HRMS не совпадает с кодом филиала АБС. Это не «техническая мелочь»: понадобился справочник соответствия, ответственный за него и поведение при отсутствии значения (бизнес-ошибка → задача в ServiceDesk).

Нумерация папок — удобная условность, её не задаёт ни устав, ни стандарт. В компании структуру обычно задаёт шаблон пространства Confluence или внутренний регламент.

## 3. Этапы проекта и рождение артефактов

| Этап             | Главный вопрос                  | Артефакты                                                           | Кто ведёт           | Что делает СА                                                | Критерий выхода                                                                                         |
| ---------------- | ------------------------------- | ------------------------------------------------------------------- | ------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| Инициация        | Зачем проект и где его границы? | Устав, реестр стейкхолдеров                                         | РП                  | Помогает сформулировать скоуп, называет интеграционные риски | Устав утверждён                                                                                         |
| Обследование     | Как сейчас и что болит?         | AS-IS, BPMN AS-IS                                                   | БА                  | Интервью, статистика, выгрузки из систем                     | Проблемы подтверждены данными                                                                           |
| Бизнес-анализ    | Как должно быть?                | TO-BE, gap-анализ, БТ                                               | БА                  | Проверяет реализуемость TO-BE                                | БТ согласованы заказчиком                                                                               |
| Системный анализ | Что должна делать система?      | Use cases, ФТ, НФТ, ролевая модель, бэклог                          | **СА**              | Основной исполнитель                                         | ФТ согласованы, трассировка к БТ есть                                                                   |
| Проектирование   | Как устроено решение?           | C4, модель данных, статусы, ADR, интеграции, sequence, маппинг, API | Архитектор + **СА** | Данные, статусы, контракты, маппинг, сценарии                | Согласовано архитектурным комитетом и ИБ                                                                |
| Разработка       | —                               | Код, технический дизайн                                             | Разработка          | Отвечает на вопросы, уточняет требования, ревьюит контракты  | Истории соответствуют DoD                                                                               |
| Тестирование     | Работает ли как задумано?       | ПМИ, тест-кейсы                                                     | QA                  | Разбирает спорные дефекты: баг или неверное требование       | Протокол испытаний подписан                                                                             |
| Внедрение        | Как перейти без потерь?         | Миграция, план внедрения, регламенты                                | РП                  | Миграция и сверка данных, инструкции                         | Акт ввода в эксплуатацию                                                                                |
| Эксплуатация     | Достигнуты ли цели?             | Отчёт по метрикам целей                                             | Сопровождение       | Разбор инцидентов, требования на развитие                    | Метрики [G-01](/case/00-project/project-charter/#g-01) … [G-03](/case/00-project/project-charter/#g-03) |

В Agile этапы со 2-го по 7-й повторяются в каждом инкременте. Но инициация и «скелет» проектирования (контекст, ключевые интеграции, модель данных) всё равно делаются в начале. Иначе первые спринты строят то, что потом придётся переделывать.

## 4. Трассировка на живом примере

Одна потребность бизнеса проходит через все слои:

```
G-01   Сотрудник работает с первого дня (≥ 95% к 09:00)                     устав
 └─ BR-04   Доступы готовы к первому дню и не активны до него               БТ
     ├─ FR-07   Создавать за 3 раб. дня в заблокированном состоянии         ФТ
     └─ FR-08   Активировать в 07:00 по часовому поясу подразделения        ФТ
          ├─ UC-02      Активировать доступы в день выхода                  use cases
          ├─ ADR-002    Почему создаём заранее, а не в день выхода          ADR
          ├─ org_unit.timezone                                              модель данных, маппинг
          ├─ CREATED_DISABLED → ACTIVE                                      state-account.puml
          ├─ SEQ-01, этап «День D, 07:00»                                   seq-01-hire.puml
          ├─ NFR-04     Доступность круглосуточно (Владивосток = 00:00 МСК) НФТ
          └─ TC-06      Активация в Москве, Екатеринбурге, Владивостоке     тест-кейсы
```

Если заказчик захочет изменить [BR-04](/case/01-business/business-requirements/#br-04) (например, «активировать в 08:30»), по этой цепочке видно всё, что придётся пересмотреть. Это и есть **анализ влияния** — главная практическая польза трассировки.

## 5. Кто за что отвечает и к кому идти

Полная RACI-матрица — в [`00_project/02_stakeholders-raci.md`](/case/00-project/stakeholders-raci/). Коротко:

| Роль                 | Отвечает за                                                                                                                            |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Руководитель проекта | Сроки, бюджет, риски, устав, коммуникации                                                                                              |
| Бизнес-аналитик      | Как работает бизнес: AS-IS, TO-BE, БТ, регламенты                                                                                      |
| Системный аналитик   | Что делает система и как обменивается данными: ФТ, НФТ, use cases, модель данных, статусы, интеграции, контракты, маппинг, трассировка |
| Архитектор           | Как устроено решение: контейнеры, технологии, ADR                                                                                      |
| ИБ                   | Ограничения безопасности, SoD, согласование ролевой модели                                                                             |
| QA                   | ПМИ, тест-кейсы, протокол испытаний                                                                                                    |
| Заказчик             | Утверждает цели, БТ, приёмку                                                                                                           |

На малом проекте БА и СА — один человек, а иногда и РП тоже.

### Ситуации, в которых аналитик НЕ решает сам

| Ситуация                                              | К кому идти                                         | Пример из кейса                                                                                                                                                                                                                       |
| ----------------------------------------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Требования двух стейкхолдеров противоречат друг другу | Владелец БТ (заказчик), при необходимости — спонсор | HRD: «пусть руководитель сам выбирает права»; CISO: «только по ролям». Решение — роли плюс заявки с согласованием ([BR-03](/case/01-business/business-requirements/#br-03) + [BR-05](/case/01-business/business-requirements/#br-05)) |
| Нужен выбор между техническими вариантами             | Архитектор, оформить ADR                            | Kafka или REST для кадровых событий ([ADR-001](/case/03-architecture/adr/#adr-001))                                                                                                                                                   |
| Требование ИБ ухудшает удобство                       | CISO + заказчик                                     | Пароль только по SMS, без e-mail ([SEC-04](/case/05-security/security-requirements/#sec-04))                                                                                                                                          |
| Смежная команда не успевает                           | РП (это риск)                                       | Команда HRMS может дать только 2 спринта                                                                                                                                                                                              |
| Просят «ещё одну систему, это же мелочь»              | РП, запрос на изменение                             | Риск [R-03](/case/00-project/project-charter/#r-03)                                                                                                                                                                                   |
| Найдена проблема, которую не решить системой          | БА / заказчик, организационная мера                 | Поздние приказы HR ([GAP-09](/case/01-business/gap-analysis/#gap-09))                                                                                                                                                                 |

## 6. Карточки артефактов

Формат карточки: на какой вопрос отвечает · когда появляется · кто пишет и утверждает · что делать на малом проекте · типичные ошибки.

### Слой «Зачем»

**Устав проекта** — [`00_project/01_project-charter.md`](/case/00-project/project-charter/)

- **Вопрос:** зачем проект, какие измеримые цели, что входит и что явно не входит, сроки, риски.
- **Когда:** инициация, до начала анализа.
- **Кто:** пишет РП, утверждает спонсор / заказчик; СА консультирует по скоупу и интеграциям.
- **Малый проект:** одна страница «цель с метрикой + входит / не входит + срок». Совсем без неё нельзя — не будет границы.
- **Ошибки:** цели без метрик; нет раздела «вне рамок»; скоуп сформулирован так, что под него подходит что угодно.

**Реестр стейкхолдеров и RACI** — [`00_project/02_stakeholders-raci.md`](/case/00-project/stakeholders-raci/)

- **Вопрос:** кто влияет на проект, кому что важно, кто что делает и утверждает.
- **Когда:** инициация; дополняется по ходу.
- **Кто:** РП, СА и БА помогают найти стейкхолдеров.
- **Малый проект:** список «кто заказчик, кто согласует, кого спросить».
- **Ошибки:** забытые стейкхолдеры с правом вето (ИБ, аудит, владельцы смежных систем); в строке RACI несколько A.

**Глоссарий** — [`00_project/03_glossary.md`](/case/00-project/glossary/)

- **Вопрос:** что именно означает термин в этом проекте.
- **Когда:** с первых интервью; растёт всё время.
- **Кто:** СА.
- **Малый проект:** 10–15 ключевых терминов всё равно нужны.
- **Ошибки:** общие определения из Википедии вместо проектных; нет колонки «не путать с». В кейсе «роль в АБС» — это полномочие, а не бизнес-роль, и без глоссария путались бы все.

### Слой «Что меняется для бизнеса»

**AS-IS** — [`01_business/01_as-is.md`](/case/01-business/as-is/), [`diagrams/as-is.bpmn`](/case/diagrams/#as-is)

- **Вопрос:** как процесс работает сейчас на самом деле и какие у него проблемы.
- **Когда:** обследование.
- **Кто:** БА (СА на малых проектах).
- **Малый проект:** 5–10 шагов и список проблем. Пропустить можно, если процесса раньше не было вообще.
- **Ошибки:** описать регламент вместо реальности; проблемы без цифр («долго» вместо «6,2 дня»); не указать источники информации.

**TO-BE** — [`01_business/02_to-be.md`](/case/01-business/to-be/), [`diagrams/to-be.bpmn`](/case/diagrams/#to-be)

- **Вопрос:** как процесс будет работать после проекта; бизнес-правила.
- **Когда:** бизнес-анализ.
- **Кто:** БА; утверждает заказчик.
- **Малый проект:** нужен, если меняется работа людей.
- **Ошибки:** TO-BE = AS-IS с «IdM» вместо администратора; не вынесены бизнес-правила (BRL) — они потом теряются в тексте.

**Gap-анализ** — [`01_business/03_gap-analysis.md`](/case/01-business/gap-analysis/)

- **Вопрос:** что конкретно меняется: система, данные, регламент, организация.
- **Когда:** после TO-BE.
- **Кто:** БА.
- **Малый проект:** можно совместить с TO-BE колонкой «что меняется».
- **Ошибки:** видеть только системные изменения. Организационные ([GAP-09](/case/01-business/gap-analysis/#gap-09), [GAP-10](/case/01-business/gap-analysis/#gap-10)) часто важнее.

**Бизнес-требования (БТ)** — [`01_business/04_business-requirements.md`](/case/01-business/business-requirements/)

- **Вопрос:** что нужно бизнесу и зачем, без описания реализации.
- **Когда:** бизнес-анализ.
- **Кто:** БА; утверждает заказчик.
- **Малый проект:** часто сливается с ФТ или user stories.
- **Ошибки:** техника в БТ («читать топик Kafka»); нет приоритета; отложенное требование просто удалено вместо статуса W (см. [BR-12](/case/01-business/business-requirements/#br-12)).

### Слой «Что делает система»

**Use cases** — [`02_requirements/01_use-cases.md`](/case/02-requirements/use-cases/), [`diagrams/use-case.puml`](/case/diagrams/#use-case)

- **Вопрос:** кто и с какой целью взаимодействует с системой и как, включая альтернативы и ошибки.
- **Когда:** системный анализ.
- **Кто:** СА.
- **Малый проект:** диаграмма + краткие описания; полные спецификации — только для сложных сценариев.
- **Ошибки:** описан только основной поток (вся ценность — в альтернативах); use case = кнопка на экране.

**Функциональные требования** — [`02_requirements/02_functional-requirements.md`](/case/02-requirements/functional-requirements/)

- **Вопрос:** что должна делать система. Каждое требование атомарно, проверяемо, однозначно и трассируемо.
- **Когда:** системный анализ.
- **Кто:** СА; утверждает заказчик (смысл) и архитектор (реализуемость).
- **Малый проект:** список ФТ или user stories с критериями приёмки.
- **Ошибки:** «система должна быть удобной»; несколько требований в одном; нет детализации там, где она критична (правило логина, политика повторов, реакции на изменения).

**Нефункциональные требования** — [`02_requirements/03_non-functional-requirements.md`](/case/02-requirements/non-functional-requirements/)

- **Вопрос:** насколько хорошо система работает: скорость, надёжность, безопасность, сопровождаемость.
- **Когда:** системный анализ, вместе с архитектором.
- **Кто:** СА; утверждает архитектор.
- **Малый проект:** 3–5 ключевых: нагрузка, время отклика, доступность, безопасность.
- **Ошибки:** неизмеримые формулировки; забыть, что НФТ влияют на архитектуру ([NFR-05](/case/02-requirements/non-functional-requirements/#nfr-05) → идемпотентность).

**Ролевая модель** — [`02_requirements/04_role-model.md`](/case/02-requirements/role-model/)

- **Вопрос:** справочные данные предметной области, без которых система не работает: полномочия, роли, правила назначения, SoD.
- **Когда:** системный анализ; часто самый долгий по согласованию артефакт.
- **Кто:** СА, утверждает ИБ.
- **Малый проект:** в другом домене на этом месте будет своё — тарифная сетка, справочник продуктов, матрица статусов. Смысл тот же: **данные, которые настраивают поведение системы, — тоже требования**.
- **Ошибки:** откладывать «на потом, это просто справочник»; не назначить владельца данных после запуска.

**Бэклог** — [`02_requirements/05_backlog.md`](/case/02-requirements/backlog/)

- **Вопрос:** как требования режутся на единицы работы для спринтов.
- **Когда:** перед разработкой; ведётся постоянно.
- **Кто:** Product Owner владеет, СА пишет истории и критерии приёмки.
- **Малый проект:** часто единственный вид требований — тогда критерии приёмки должны быть особенно точными.
- **Ошибки:** истории без критериев приёмки; «горизонтальная» нарезка (сначала вся БД, потом весь API) вместо вертикальной (тонкий сквозной сценарий).

**Матрица трассировки** — [`02_requirements/06_traceability-matrix.md`](/case/02-requirements/traceability-matrix/)

- **Вопрос:** как связаны цели, требования, сценарии и тесты.

### 7.2. Как выбрать диаграмму

| Если нужно показать…                                    | Используй                          |
| ------------------------------------------------------- | ---------------------------------- |
| Последовательность работы людей и передачу между ролями | BPMN                               |
| Кто пользуется системой и для чего                      | Use Case                           |
| Границы системы и соседей                               | C4 контекст                        |
| Из каких сервисов, баз и очередей состоит решение       | C4 контейнеры                      |
| Какие сущности хранятся и как связаны                   | ER                                 |
| Жизненный цикл одного объекта со статусами              | State                              |
| Кто кого вызывает в одном сценарии, включая ошибки      | Sequence                           |
| Алгоритм с ветвлениями внутри одной системы             | Activity                           |
| Серверы, сети, кластеры                                 | Deployment                         |
| Точный формат запроса или сообщения                     | Не диаграмма, а OpenAPI / AsyncAPI |

**Частые путаницы:**

- **BPMN или Activity.** BPMN — бизнес-процесс с участниками и передачей работы между ними. Activity — алгоритм внутри системы, например генерация логина ([FR-06](/case/02-requirements/functional-requirements/#fr-06), раздел 2.1).
- **BPMN или Sequence.** BPMN показывает, что делают участники. Sequence показывает, какие сообщения они передают друг другу и в каком порядке.
- **State или Activity.** State — про объект («учётная запись бывает такой-то»). Activity — про действия («сначала сделать то, потом это»).

### 7.3. BPMN

**Зачем.** Показать процесс целиком: участников, шаги, развилки, ожидания и передачи работы. На AS-IS видны потери (очереди, возвраты, ручная работа), на TO-BE — что меняется.

**Когда и кто.** Обследование (AS-IS) и бизнес-анализ (TO-BE). Рисует БА, СА читает и проверяет.

**Элементы нотации:**

| Элемент                 | Как выглядит               | Значение                                                                                                                                                                     |
| ----------------------- | -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Стартовое событие       | Тонкий круг                | Начало; называется состоянием: «Кандидат принял оффер»                                                                                                                       |
| Промежуточное событие   | Двойной круг               | Что-то происходит по ходу; таймер (часы), сообщение (конверт). В TO-BE — «День выхода, 07:00»                                                                                |
| Конечное событие        | Жирный круг                | Результат процесса                                                                                                                                                           |
| Задача                  | Скруглённый прямоугольник  | Работа; название — «глагол + объект». Типы: пользовательская (человек в системе), сервисная (система сама), ручная (без системы), отправка и получение сообщения, скриптовая |
| Исключающий шлюз (XOR)  | Ромб с ×                   | Выбирается ровно одна ветка; название — вопрос                                                                                                                               |
| Параллельный шлюз (AND) | Ромб с +                   | Все ветки сразу; на слиянии ждёт все ветки                                                                                                                                   |
| Включающий шлюз (OR)    | Ромб с ○                   | Одна или несколько веток                                                                                                                                                     |
| Шлюз по событию         | Ромб с пятиугольником      | Ветку выбирает событие, которое наступит первым                                                                                                                              |
| Пул                     | Большой прямоугольник      | Участник: организация или система                                                                                                                                            |
| Дорожка                 | Полоса внутри пула         | Роль или подразделение внутри участника                                                                                                                                      |
| Поток операций          | Сплошная стрелка           | Порядок шагов внутри одного пула                                                                                                                                             |
| Поток сообщений         | Пунктир с кружком в начале | Обмен между разными пулами                                                                                                                                                   |
| Аннотация               | Квадратная скобка          | Комментарий; в AS-IS так отмечены проблемы [P-01](/case/01-business/as-is/#p-01) … [P-07](/case/01-business/as-is/#p-07)                                                     |
| Подпроцесс              | Задача со знаком «+»       | Свёрнутая группа шагов                                                                                                                                                       |

**Как читать архив.** В AS-IS видно 4 последовательные задачи администраторов (A6–A9) и цикл возврата заявки — это проблемы [P-03](/case/01-business/as-is/#p-03) и [P-04](/case/01-business/as-is/#p-04). В TO-BE большая часть шагов — сервисные задачи IdM, а люди остались только в исключениях (T6, T8).

> В архиве IdM — это дорожка в общем пуле. Строже по нотации было бы вынести HRMS и IdM в отдельные пулы и связать их потоками сообщений. Один пул выбран ради читаемости. На собеседовании полезно уметь объяснить оба варианта.

**Уровень детализации.** Шаг — это единица работы одного исполнителя, а не клик мышью. Если на схеме больше 20–25 задач, выноси части в подпроцессы.

**Типичные ошибки:**

- задача без глагола («Заявка»);
- шлюз без вопроса;
- поток операций между пулами вместо потока сообщений;
- параллельные ветки слились без AND-шлюза — процесс «продолжится дважды»;
- AS-IS и TO-BE на одной схеме;
- нет конечного события или неясно, чем процесс заканчивается.

**Вопросы на собеседовании:**

- Чем XOR отличается от OR и AND?
- Пул и дорожка — в чём разница?
- Поток операций и поток сообщений?
- Что такое токен? Воображаемая метка, которая движется по процессу: AND-шлюз размножает токены и на слиянии ждёт их все.

### 7.4. Use Case (варианты использования)

**Зачем.** Зафиксировать, кто и с какой целью использует систему. Диаграмма даёт обзор, а текстовая спецификация — детали: основной поток, альтернативы, исключения.

**Когда и кто.** Системный анализ, СА.

**Элементы:**

| Элемент          | Значение                                                                                                                                                                                           |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Актор            | Роль, внешняя по отношению к системе: человек или другая система. Один человек может выступать в двух ролях                                                                                        |
| Прецедент (овал) | Цель актора, достигаемая с помощью системы                                                                                                                                                         |
| Граница системы  | Прямоугольник вокруг прецедентов                                                                                                                                                                   |
| `<<include>>`    | Базовый прецедент **всегда** включает другой. Стрелка от базового: [UC-01](/case/02-requirements/use-cases/#uc-01) → «Проверить SoD»                                                               |
| `<<extend>>`     | Прецедент расширяет базовый **при условии**. Стрелка от расширения к базовому: [UC-04](/case/02-requirements/use-cases/#uc-04) → [UC-01](/case/02-requirements/use-cases/#uc-01) при SoD-конфликте |
| Обобщение        | Актор или прецедент-наследник                                                                                                                                                                      |

**Шаблон спецификации** — см. [UC-01](/case/02-requirements/use-cases/#uc-01) в архиве: акторы, предусловия, триггер, постусловия (успех и неуспех), основной поток, альтернативные потоки, исключения, связанные требования.

**Типичные ошибки:**

- прецедент = кнопка или экран («Нажать "Сохранить"»);
- функциональная декомпозиция в виде дерева include;
- путаница направлений include и extend;
- описан только основной поток.

**Вопросы на собеседовании:**

- Include или extend — в чём разница?
- Может ли система быть актором? Да: HRMS и Таймер в архиве.
- Чем use case отличается от user story? Use case — полное описание взаимодействия с альтернативами. User story — небольшая единица ценности для планирования. Один use case обычно даёт несколько историй.

### 7.5. C4 (контекст и контейнеры)

**Зачем.** Показать архитектуру на нужном уровне приближения, как карту с масштабом.

| Уровень       | Что показывает                                  | Аудитория                                 |
| ------------- | ----------------------------------------------- | ----------------------------------------- |
| 1. Контекст   | Система, пользователи, внешние системы          | Все, включая бизнес                       |
| 2. Контейнеры | Приложения, сервисы, БД, очереди внутри системы | Архитекторы, разработка, СА, эксплуатация |
| 3. Компоненты | Модули внутри одного контейнера                 | Разработка                                |
| 4. Код        | Классы                                          | Обычно не рисуют                          |

**Правила.** У каждого элемента есть имя, тип, технология и описание. У каждой стрелки — что передаётся и как (протокол). Одна диаграмма — один уровень.

**Как читать архив.** На контексте 8 внешних систем, а значит, 8 потенциальных владельцев, которых нужно вовлечь (сравни с реестром стейкхолдеров). На контейнерах видно, что кадровые события не идут в ядро напрямую: между ними обработчик с DLQ. Это следствие [ADR-001](/case/03-architecture/adr/#adr-001).

**Типичные ошибки:**

- контейнер C4 = Docker-контейнер (нет: это любая отдельно разворачиваемая часть, включая БД);
- стрелки без подписей;
- смешение уровней на одной диаграмме;
- шина нарисована одним прямоугольником без топиков.

**Вопросы на собеседовании:** зачем нужен уровень 1, если есть уровень 2; чем контейнер отличается от компонента.

### 7.6. ER-диаграмма (модель данных)

**Зачем.** Описать, что система хранит и как данные связаны. От модели зависят API, маппинг, отчёты и то, выдержит ли система «неудобные» случаи (совместительство, повторный приём).

**Нотация «вороньи лапки» (Crow's Foot):**

| Символ в PlantUML | Значение       |
| ----------------- | -------------- |
| `\|\|`            | Ровно один     |
| `\|o`             | Ноль или один  |
| `}o`              | Ноль или много |
| `}\|`             | Один или много |

Пример: `identity ||--o{ employment` — у идентичности ноль или много трудоустройств, у трудоустройства ровно одна идентичность.

**Ключи.** PK — первичный ключ. FK — внешний ключ (ссылка). UK — уникальный бизнес-ключ. В архиве `identity_id` — суррогатный ключ (uuid), а `person_id` — натуральный ключ из HRMS с ограничением уникальности.

**Связь «многие ко многим»** реализуется через связующую сущность: `role_entitlement` между ролями и полномочиями.

**Нормализация, коротко:**

- 1НФ — значения атомарны, нет списков в одном поле.
- 2НФ — неключевые атрибуты зависят от всего составного ключа.
- 3НФ — нет зависимостей неключевых атрибутов друг от друга.

Денормализуют осознанно, ради производительности или отчётности.

**Уровни модели:** концептуальная → логическая (СА) → физическая (разработка, DBA).

**Типичные ошибки:**

- склеить разные сущности: «сотрудник» = «учётная запись»;
- M:N без связующей таблицы;
- нет уникальных бизнес-ключей;
- нет полей основания и истории там, где нужен аудит.

**Вопросы на собеседовании:**

- Виды связей и их реализация.
- Нормальные формы.
- PK и UK.
- Суррогатный и натуральный ключ.
- Мягкое удаление (soft delete): строка не удаляется, а помечается признаком.

### 7.7. Статусная модель (State Machine)

**Зачем.** Однозначно определить жизненный цикл объекта. Для разработки это логика, для тестирования — готовый список тестов: каждый переход — позитивный тест, каждый запрещённый переход — негативный.

**Элементы:**

| Элемент              | Значение                                                                           |
| -------------------- | ---------------------------------------------------------------------------------- |
| Состояние            | Название — существительное или причастие: «Создана, заблокирована», а не «Создать» |
| Начальное / конечное | Чёрный круг / круг с ободком                                                       |
| Переход              | Стрелка с подписью `событие [условие] / действие`                                  |
| Самопереход          | Событие не меняет состояние, но выполняет действие (эскалация в заявке)            |

**Как читать архив.** [`state-provisioning-task.puml`](/case/diagrams/#state-provisioning-task) — это вся политика повторов [FR-16](/case/02-requirements/functional-requirements/#fr-16) в одной картинке. В [`04_state-models.md`](/case/03-architecture/state-models/) та же модель дана таблицей переходов: таблицу удобнее согласовывать и превращать в тесты, диаграмму — объяснять.

**Типичные ошибки:**

- состояния названы действиями;
- нет переходов для ошибок и отмены;
- не определено, что делать с «невозможным» событием (отмена после активации — [FR-18](/case/02-requirements/functional-requirements/#fr-18));
- смешаны статусы разных объектов (статус заявки и статус задачи).

**Вопросы на собеседовании:** чем state отличается от activity; как статусная модель помогает тестированию; кто имеет право менять статус.

### 7.8. Sequence-диаграмма

**Зачем.** Показать порядок сообщений между участниками в одном сценарии. Это главный инструмент проектирования интеграций.

**Элементы:**

| Элемент      | Значение                                        |
| ------------ | ----------------------------------------------- |
| Линия жизни  | Участник: система, сервис, человек, очередь, БД |
| `->`         | Синхронный вызов: отправитель ждёт ответа       |
| `-->`        | Ответ                                           |
| `->>`        | Асинхронное сообщение: отправитель не ждёт      |
| `alt / else` | Ветвление по условию                            |
| `opt`        | Необязательный фрагмент                         |
| `loop`       | Цикл                                            |
| `par`        | Параллельное выполнение                         |
| `== … ==`    | Разделитель этапов во времени                   |
| `autonumber` | Нумерация шагов, на которые удобно ссылаться    |

**Правила.** Один сценарий — одна диаграмма. Участники — на одном уровне абстракции (сервисы, а не классы и не кнопки). Ошибки показывают отдельной диаграммой или через `alt`.

**Как читать архив.** [`seq-02-abs-failure.puml`](/case/diagrams/#seq-02-abs-failure) — главный учебный пример. Первый запрос завершился таймаутом, и неизвестно, создан ли пользователь в АБС. Повтор с тем же `Idempotency-Key` безопасен: если пользователь уже создан, адаптер вернёт его, а не ошибку «логин занят».

**Типичные ошибки:**

- 15–20 участников на одной диаграмме;
- нет ответов;
- только успешный путь;
- смешаны действия в интерфейсе и SQL-запросы.

**Вопросы на собеседовании:**

- Синхронный и асинхронный обмен — когда что выбирать?
- Что такое идемпотентность и зачем ключ идемпотентности?
- At-least-once или exactly-once?
- Как обработать таймаут, если неизвестно, выполнилась ли операция? Ответ: повтор с тем же ключом.

### 7.9. Контракты: OpenAPI и AsyncAPI

Это не диаграммы, но тоже схемы, и для СА они не менее важны.

**OpenAPI** ([`idm-api.openapi.yaml`](/case/04-integrations/api-idm/), [`abs-adapter.openapi.yaml`](/case/04-integrations/api-abs-adapter/)) описывает REST API:

- `paths` — адреса;
- методы и параметры;
- `requestBody` — тело запроса;
- `responses` — ответы, включая ошибки;
- `components/schemas` — модели данных;
- `securitySchemes` — аутентификация.

| Метод  | Назначение                      | Идемпотентен?                         |
| ------ | ------------------------------- | ------------------------------------- |
| GET    | Получить                        | Да                                    |
| POST   | Создать / выполнить действие    | Нет — поэтому нужен `Idempotency-Key` |
| PUT    | Заменить или установить целиком | Да                                    |
| PATCH  | Изменить часть                  | Не гарантированно                     |
| DELETE | Удалить                         | Да                                    |

| Код             | Значение                                              |
| --------------- | ----------------------------------------------------- |
| 200 / 201 / 204 | Успех / создано / успех без тела                      |
| 400             | Синтаксически неверный запрос                         |
| 401             | Не аутентифицирован (кто ты?)                         |
| 403             | Нет прав (знаю, кто ты, но нельзя)                    |
| 404             | Не найдено                                            |
| 409             | Конфликт состояния (логин занят, задача уже отменена) |
| 422             | Бизнес-валидация не прошла                            |
| 429             | Слишком много запросов                                |
| 5xx / 503       | Ошибка или недоступность сервера                      |

В архиве ошибки описаны в формате RFC 7807 (`application/problem+json`).

**AsyncAPI** ([`hr-events.asyncapi.yaml`](/case/04-integrations/api-hr-events/)) описывает асинхронный обмен:

- `channels` — топики;
- `operations` — кто отправляет и кто получает;
- `messages` — сообщения;
- схемы полезной нагрузки.

Важное в архиве:

- ключ сообщения `personId` гарантирует порядок событий одного человека;
- `eventId` — ключ идемпотентности;
- версия схемы `.v1` в имени топика;
- DLQ для некорректных сообщений.

**Вопросы на собеседовании:**

- REST, SOAP, gRPC, очереди — когда что?
- 401 и 403; 400 и 422; PUT и PATCH.
- Как версионировать API?
- Кто владелец контракта?

### Минимальный набор для малого проекта

1. Страница «цель с метрикой + входит / не входит».
2. TO-BE, если меняется работа людей.
3. Требования: ФТ или истории с критериями приёмки.
4. Модель данных, хотя бы концептуальная.
5. Контекст + интеграции и контракты, если есть внешние системы.
6. Статусная модель для каждого объекта со статусами.
7. Приёмочные сценарии.

| Термин                  | Значение                                                                |
| ----------------------- | ----------------------------------------------------------------------- |
| AS-IS / TO-BE           | Текущее и целевое состояние процесса или системы                        |

| RBAC / ABAC             | Доступ по ролям / по атрибутам                                          |
| SoD                     | Разделение полномочий: запрет конфликтующих сочетаний                   |
| Birthright              | Права, которые положены всем без запроса                                |
| Провижининг             | Создание учётных записей и выдача прав в целевых системах               |
| Ресертификация          | Периодическое подтверждение руководителем, что права ещё нужны          |
| PAM                     | Управление привилегированным доступом                                   |
| Ролевой майнинг         | Построение ролей из анализа фактических прав                            |
| Orphan account          | Учётная запись без владельца-сотрудника                                 |
| SLA                     | Согласованный уровень сервиса (срок, доступность)                       |
| RTO / RPO               | Допустимое время восстановления / допустимая потеря данных              |
| Пилот                   | Ограниченный запуск для проверки на реальных пользователях              |
| ПМИ / UAT               | Программа и методика испытаний / приёмочное тестирование пользователями |

### Упражнения: дорисуй проект сам

Это лучший способ закрепить материал — сделать артефакт, которого в архиве нет, по образцу соседних.

1. **BPMN процесса Leaver** (увольнение): блокировка в день увольнения, срочное увольнение, передача почтового ящика руководителю.
2. **Статусная модель трудоустройства** (`employment`) с переходами для совместительства.
3. **Sequence для [UC-10](/case/02-requirements/use-cases/#uc-10)** (ежедневная сверка с HRMS): включая случай, когда HRMS недоступна.
4. **Activity-диаграмма** алгоритма генерации логина ([FR-06](/case/02-requirements/functional-requirements/#fr-06), раздел 2.1).
5. **Подключение новой системы** (например, CRM): строка в карте интеграций, колонка в маппинге, полномочия в каталоге, новые тест-кейсы. Затем проверь по матрице трассировки, что ничего не забыто.
6. **Процесс Mover** (перевод): какие права отзывать, когда, как избежать периода, когда у сотрудника нет никаких прав.
