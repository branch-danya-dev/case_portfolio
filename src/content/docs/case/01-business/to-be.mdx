## 1. Принципы целевого процесса

1. **Триггер — кадровое событие.** Процесс запускает приказ в HRMS, а не заявка руководителя.
2. **Права по роли, а не «как у коллеги».** Базовая роль всем, бизнес-роль по должности и подразделению.
3. **Готово заранее, активно с первого дня.** Учётные записи создаются заранее в заблокированном состоянии и активируются утром в день выхода.
4. **Человек — только для исключений.** Согласование нужно для SoD-конфликтов и дополнительных прав; ручная работа администраторов — для систем без коннектора и при сбоях.
5. **Всё с основанием.** Каждое полномочие имеет основание (роль или заявка) в журнале аудита.

## 2. Шаги процесса

| №   | Шаг                                                                      | Исполнитель   | Система           |
| --- | ------------------------------------------------------------------------ | ------------- | ----------------- |
| T1  | Оформить приказ о приёме не позднее чем за 2 рабочих дня до выхода       | HR-специалист | HRMS              |
| T2  | Принять и проверить кадровое событие                                     | IdM           | IdM               |
| T3  | Создать идентичность, сгенерировать логин                                | IdM           | IdM               |
| T4  | Определить бизнес-роли                                                   | IdM           | IdM               |
| T5  | Проверить SoD                                                            | IdM           | IdM               |
| T6  | Рассмотреть SoD-конфликт (только при конфликте)                          | Инженер ИБ    | Портал IdM        |
| T7  | Создать учётные записи в заблокированном состоянии                       | IdM           | AD, Exchange, АБС |
| T8  | Исполнить задачу вручную (СЭД, технические сбои)                         | Администратор | ServiceDesk       |
| —   | Ожидание: день выхода, 07:00 по времени подразделения                    | IdM (таймер)  | —                 |
| T9  | Активировать учётные записи                                              | IdM           | AD, АБС           |
| T10 | Отправить сотруднику одноразовый пароль по SMS, уведомить руководителя   | IdM           | SMS-шлюз, e-mail  |
| T11 | Получить уведомление; при необходимости запросить дополнительные доступы | Руководитель  | Портал IdM        |

Запрос дополнительных доступов (T11) — отдельный процесс с собственным маршрутом согласования, см. [UC-03](/case/02-requirements/use-cases/#uc-03) и [UC-04](/case/02-requirements/use-cases/#uc-04) в [`02_requirements/01_use-cases.md`](/case/02-requirements/use-cases/).

## 3. Бизнес-правила

| ID                                             | Правило                                                                                                                                                                                  |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| <span id="brl-01" class="case-anchor" />BRL-01 | Учётные записи создаются за 3 рабочих дня до даты выхода. Если событие пришло позже — сразу.                                                                                             |
| <span id="brl-02" class="case-anchor" />BRL-02 | Активация выполняется в 07:00 по часовому поясу подразделения сотрудника.                                                                                                                |
| <span id="brl-03" class="case-anchor" />BRL-03 | Если для пары «тип подразделения + должность» нет правила назначения роли, выдаётся только базовая роль, руководитель и владелец ролевой модели получают уведомление.                    |
| <span id="brl-04" class="case-anchor" />BRL-04 | Полномочие, образующее SoD-конфликт, не выдаётся до решения ИБ. Остальные полномочия выдаются без задержки.                                                                              |
| <span id="brl-05" class="case-anchor" />BRL-05 | При повторном приёме используется прежняя идентичность; учётные записи создаются заново; прежний логин переиспользуется, если он свободен.                                               |
| <span id="brl-06" class="case-anchor" />BRL-06 | При отмене приёма созданные, но не активированные учётные записи удаляются, задачи ручного исполнения отменяются.                                                                        |
| <span id="brl-07" class="case-anchor" />BRL-07 | Если у сотрудника уже есть активное трудоустройство в банке (внутреннее совместительство), новая учётная запись AD не создаётся; к идентичности добавляются роли нового трудоустройства. |
| <span id="brl-08" class="case-anchor" />BRL-08 | Первичный пароль одноразовый, передаётся только по SMS на мобильный телефон из HRMS в день выхода и подлежит смене при первом входе.                                                     |

## 4. Ожидаемый эффект

| Показатель                      | AS-IS                               | TO-BE                          |
| ------------------------------- | ----------------------------------- | ------------------------------ |
| Готовность доступов             | через 4–5 рабочих дней после выхода | к 09:00 первого дня            |
| Участие руководителя            | обязательно (заявка)                | только для дополнительных прав |
| Ручные операции администраторов | 4 системы на каждого сотрудника     | только СЭД и сбои              |
| Основание выдачи                | свободный текст заявки              | роль или заявка в журнале      |
