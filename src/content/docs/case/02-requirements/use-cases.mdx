Use case описывает взаимодействие актора с системой ради значимого для актора результата. Диаграмма показывает **кто и что** делает с системой, а текстовая спецификация — **как именно**, включая альтернативы и ошибки. Основная ценность — в альтернативных потоках: именно там прячутся требования, которые иначе забывают.

## <span id="uc-01" class="case-anchor" />3. UC-01. Обработать кадровое событие о приёме

| Поле                  | Значение                                                                                                                                                                                                                                                                                                                    |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Основной актор        | Кадровая система (HRMS)                                                                                                                                                                                                                                                                                                     |
| Второстепенные акторы | AD, Exchange, АБС, ServiceDesk                                                                                                                                                                                                                                                                                              |
| Цель актора           | Новый сотрудник получает доступы, соответствующие должности, к первому рабочему дню                                                                                                                                                                                                                                         |
| Предусловия           | Приказ о приёме проведён в HRMS; событие `HIRE` опубликовано в шину                                                                                                                                                                                                                                                         |
| Триггер               | Событие `HIRE` в топике `hr.employee.events.v1`                                                                                                                                                                                                                                                                             |
| Постусловия (успех)   | Идентичность в статусе `PRE_HIRE`; учётные записи созданы в статусе `CREATED_DISABLED`; активация запланирована                                                                                                                                                                                                             |
| Постусловия (неуспех) | Событие в DLQ, создан инцидент; доступы не выдаются                                                                                                                                                                                                                                                                         |
| Связанные требования  | [FR-01](/case/02-requirements/functional-requirements/#fr-01) … [FR-12](/case/02-requirements/functional-requirements/#fr-12), [FR-15](/case/02-requirements/functional-requirements/#fr-15) … [FR-17](/case/02-requirements/functional-requirements/#fr-17), [FR-21](/case/02-requirements/functional-requirements/#fr-21) |

**Основной поток**

1. IdM получает событие `HIRE`.
2. IdM проверяет обязательные поля и уникальность `eventId` ([FR-02](/case/02-requirements/functional-requirements/#fr-02), [FR-03](/case/02-requirements/functional-requirements/#fr-03)).
3. IdM ищет идентичность по `personId`; не находит и создаёт новую ([FR-04](/case/02-requirements/functional-requirements/#fr-04)).
4. IdM генерирует уникальный логин ([FR-06](/case/02-requirements/functional-requirements/#fr-06)).
5. IdM назначает базовую роль и бизнес-роли по правилам назначения ([FR-09](/case/02-requirements/functional-requirements/#fr-09), [FR-10](/case/02-requirements/functional-requirements/#fr-10)).
6. IdM проверяет SoD-правила — конфликтов нет ([FR-12](/case/02-requirements/functional-requirements/#fr-12)).
7. IdM планирует создание учётных записей на дату «дата выхода − 3 рабочих дня» ([FR-07](/case/02-requirements/functional-requirements/#fr-07)).
8. В запланированную дату IdM создаёт заблокированные учётные записи в AD, Exchange, АБС и задачу в ServiceDesk для СЭД ([FR-15](/case/02-requirements/functional-requirements/#fr-15), [FR-17](/case/02-requirements/functional-requirements/#fr-17)).
9. IdM записывает все операции в журнал аудита ([FR-21](/case/02-requirements/functional-requirements/#fr-21)).

**Альтернативные потоки**

- 3a. Найдена идентичность с завершённым трудоустройством (повторный приём): используется прежняя идентичность, создаётся новое трудоустройство ([BRL-05](/case/01-business/to-be/#brl-05)).
- 3b. Найдена идентичность с активным трудоустройством (внутреннее совместительство): учётная запись AD не создаётся, к идентичности добавляются роли нового трудоустройства ([BRL-07](/case/01-business/to-be/#brl-07)).
- 4a. Логин занят: добавляется цифровой суффикс ([FR-06](/case/02-requirements/functional-requirements/#fr-06)).
- 5a. Правило назначения роли не найдено: назначается только базовая роль, руководитель и владелец ролевой модели получают уведомление ([FR-11](/case/02-requirements/functional-requirements/#fr-11)).
- 6a. Обнаружен SoD-конфликт: конфликтующее полномочие ожидает решения ИБ ([UC-04](#uc-04)), остальные полномочия выдаются без задержки ([BRL-04](/case/01-business/to-be/#brl-04)).
- 7a. До даты выхода меньше 3 рабочих дней: создание выполняется сразу.

**Исключения**

- 2a. Событие не прошло проверку: событие помещается в DLQ, группе сопровождения HRMS создаётся инцидент ([FR-02](/case/02-requirements/functional-requirements/#fr-02)).
- 2b. `eventId` уже обработан: событие подтверждается без побочных эффектов ([FR-03](/case/02-requirements/functional-requirements/#fr-03)).
- 8a. Целевая система вернула техническую ошибку: повторы по политике [FR-16](/case/02-requirements/functional-requirements/#fr-16), затем задача в ServiceDesk. См. [`04_integrations/diagrams/seq-02-abs-failure.puml`](/case/diagrams/#seq-02-abs-failure).

## <span id="uc-03" class="case-anchor" />4. UC-03. Запросить дополнительные доступы

| Поле                  | Значение                                                                                                                                                                                     |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Основной актор        | Руководитель                                                                                                                                                                                 |
| Второстепенные акторы | Владелец ресурса, Инженер ИБ                                                                                                                                                                 |
| Цель актора           | Сотрудник получает полномочия, которых нет в его бизнес-роли                                                                                                                                 |
| Предусловия           | Руководитель аутентифицирован на портале (SSO); сотрудник в его подчинении; идентичность в статусе `PRE_HIRE` или `ACTIVE`                                                                   |
| Постусловия (успех)   | Заявка в статусе `COMPLETED`, полномочия выданы с основанием «заявка № …»                                                                                                                    |
| Связанные требования  | [FR-12](/case/02-requirements/functional-requirements/#fr-12) … [FR-14](/case/02-requirements/functional-requirements/#fr-14), [FR-23](/case/02-requirements/functional-requirements/#fr-23) |

**Основной поток**

1. Руководитель открывает портал IdM и выбирает сотрудника.
2. Портал показывает текущие роли, полномочия и статус подготовки доступов ([FR-23](/case/02-requirements/functional-requirements/#fr-23)).
3. Руководитель выбирает полномочия из каталога и указывает обоснование.
4. IdM проверяет SoD с учётом уже имеющихся полномочий — конфликтов нет ([FR-12](/case/02-requirements/functional-requirements/#fr-12)).
5. IdM создаёт заявку и маршрут согласования: владелец ресурса, затем ИБ, если полномочие критичное ([FR-14](/case/02-requirements/functional-requirements/#fr-14)).
6. Согласующие одобряют заявку ([UC-04](#uc-04)).
7. IdM выдаёт полномочия. Если сотрудник ещё не вышел — в заблокированную учётную запись.
8. Руководитель получает уведомление о выполнении.

**Альтернативные потоки**

- 3a. Нужного полномочия нет в каталоге: портал предлагает создать обращение в ServiceDesk вне IdM (вне скоупа волны 1).
- 4a. SoD-конфликт: руководитель видит предупреждение, в маршрут обязательно добавляется ИБ.
- 6a. Согласующий отклоняет заявку: статус `REJECTED`, руководитель получает уведомление с комментарием.
- 6b. Срок согласования (1 рабочий день) истёк: эскалация руководителю согласующего.
