<Brief>

Выкладка — несколько часов работы эксплуатации. Вокруг неё — то, где нужен аналитик: **release notes** (что изменилось и для кого), **go/no-go** (выпускать ли — по критериям, а не по ощущениям), **smoke-проверка** (жива ли система после выкладки) и **мониторинг после релиза** (решает ли изменение задачу на реальных данных).
Smoke отвечает на вопрос «работает ли», за минуты. **Проверка на продуктиве** отвечает на вопрос «решает ли задачу» и занимает дни. Это разные проверки с разными критериями.
Для крупного запуска добавляется **усиленное сопровождение (hypercare)**: первые недели команда проекта вместе с сопровождением разбирает каждое отклонение.

</Brief>

## Когда применять

| Применять | Не нужно / проще |
|---|---|
| Релиз меняет поведение для пользователей, смежных систем или сопровождения | Техническое исправление без видимых изменений — достаточно короткой записи в журнале изменений |
| Запуск новой системы или крупной функции | — |
| В релизе изменения контрактов, данных или процессов | — |
| Релиз затрагивает несколько команд и систем | — |

## Как делать

<Steps>

1. **Написать release notes для каждой аудитории.** Сопровождению — компоненты, версии, новые алерты и процедуры. Поддержке — что увидят пользователи и как отвечать. Пользователям — что изменилось для них и с какой даты. Смежным командам — изменения контрактов.

2. **Согласовать критерии go/no-go заранее,** а не в день выпуска: тесты, дефекты, данные, готовность сопровождения, состояние смежных систем. Указать, кто принимает решение.

3. **Описать smoke-проверку:** короткий список шагов, который выполняется сразу после выкладки и не портит реальные данные.

4. **Определить метрики после релиза:** что смотрим, где, кто, сколько дней и какая норма. Метрики вытекают из цели изменения, а не только из технических показателей.

5. **Провести go/no-go.** Если критерий не выполнен — переносить, а не выпускать «с оговорками». Решение записать.

6. **После выкладки** — smoke, затем проверка на продуктиве по метрикам. Отклонения разбирать сразу, пока команда в сборе.

7. **Закрыть релиз:** обновить документацию, требования и runbook, снять флаги, завести задачи на найденное.

</Steps>

## Шаблон

### Release notes

```md
# Релиз <система> <версия> · <дата выкладки>

## Что изменилось
- <изменение для пользователя или смежной системы> (<ID требования или задачи>)

## Для сопровождения
- Компоненты и версии: …
- Новые и изменённые алерты, процедуры runbook: …
- Изменения конфигурации и флагов: …

## Изменения контрактов
- <API или событие>: <версия> — <что изменилось, совместимо ли>

## Известные ограничения
- …

## Откат
- <как откатываемся и что откатом не вернуть>
```

### Go/no-go

| Группа | Критерии |
|---|---|
| Качество | Приёмочные тесты пройдены; нет открытых дефектов высокой критичности |
| Выкладка | Выкладка и откат отрепетированы на PREPROD; известен порядок и точка невозврата |
| Данные | Миграция данных выполнена и сверена по критерию |
| Сопровождение | Алерты настроены, runbook обновлён, дежурные назначены |
| Люди | Поддержка и пользователи предупреждены, release notes разосланы |
| Окружение | Нет инцидентов в смежных системах, нет моратория на изменения (change freeze) |

### Smoke против проверки на продуктиве

| | Smoke-проверка | Проверка на продуктиве |
|---|---|---|
| Вопрос | Система жива и связана с соседями? | Изменение решает задачу? |
| Когда | Сразу после выкладки | Дни и недели после |
| Длительность | Минуты | Дни |
| Пример | Сервисы запущены, коннекторы подключаются, тестовая операция проходит | Доля сотрудников с доступами к первому дню ≥ 95% |
| Если не прошла | Откат или исправление сразу | Разбор, при необходимости — изменение |

## Пример из кейса IDM-JOINER

В <CaseRef href="/case/06-rollout/release-plan/" id="Релиз 1.0">плане релиза 1.0</CaseRef>:

- **Release notes** — для четырёх аудиторий: сопровождению (алерты ALR-01 … ALR-06 и процедуры runbook), ServiceDesk (как отвечать на вопрос «где доступы нового сотрудника»), администраторам целевых систем (новая очередь ручных задач) и руководителям пилотных подразделений.
- **Go/no-go** — за день до включения пилотных подразделений. Решают руководитель проекта, владелец продукта, CISO и руководитель сопровождения. Среди критериев — ПМИ без дефектов критичности 1–2, нагрузочный тест TC-19 на PREPROD, ≥ 98% учётных записей AD сопоставлены при миграции, нет инцидентов P1 и P2 в AD, АБС и HRMS.
- **Smoke** — без учётных записей реальных сотрудников. Коннекторы проверяются чтением служебной учётной записи, а тестовый приём выполняется в служебном тестовом подразделении.
- **Мониторинг и hypercare** — первые две недели пилота: каждое утро готовность доступов к 09:00 (NFR-02, норма ≥ 95%), ежедневно задачи MANUAL, DLQ и расхождения сверки. Hypercare заканчивается, когда метрики неделю держатся без отклонений.

Тот же подход в малом масштабе — в <CaseRef href="/case/08-operations/change-request/" id="CHG-01">CHG-01</CaseRef>: проверка на продуктиве назначена на ближайший понедельник с массовым созданием учётных записей. Ожидается, что ответы 429 есть, задач MANUAL по АБС нет, а создание заканчивается до 12:00.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Release notes — список задач из трекера | Сопровождение и пользователи не понимают, что изменилось для них | По аудиториям, языком аудитории |
| Критерии go/no-go придумывают в день выпуска | Решение принимают «по ощущениям» и под давлением сроков | Критерии согласованы заранее, решение записано |
| «Выпускаем с оговорками» | Оговорка становится инцидентом | Невыполненный критерий — перенос |
| Smoke создаёт реальные записи | Лишние учётные записи, письма, SMS реальным людям | Служебные данные и чтение без побочных эффектов |
| После smoke релиз считается завершённым | Не проверено, решает ли изменение задачу | Проверка на продуктиве по метрикам цели |
| Мониторинг после релиза — «если что, позвонят» | Отклонения находят пользователи | Метрики, ответственный, срок наблюдения |
