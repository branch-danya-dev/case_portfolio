<Brief>

**Kanban** — метод управления **потоком** работы без итераций фиксированной длины: работа визуализируется на доске, **незавершённая работа (WIP) ограничивается**, поток измеряется и постоянно улучшается.
Главная идея: **меньше начинать, больше заканчивать** — чем меньше задач одновременно в работе, тем быстрее проходит каждая.
Подходит для поддержки, эксплуатации и потока заявок разного размера. Аналитик здесь готовит задачи так, чтобы они не застревали на входе в разработку.

</Brief>

## Когда применять

| Применять | Не нужно / лучше другое |
|---|---|
| Поддержка и развитие работающей системы, поток заявок | Новый продукт с общей целью и вехами → Scrum или гибрид |
| Непредсказуемые поступления, срочные задачи | — |
| Команда перегружена «всем сразу» | — |
| Нужно увидеть узкие места процесса | — |

## Как делать

<Steps>

1. **Визуализируйте поток:** колонки — реальные этапы работы, включая анализ: «Новые» → «Анализ» → «Готово к разработке» → «Разработка» → «Тестирование» → «Готово».

2. **Ограничьте WIP** на колонках: не больше N задач в анализе, в разработке.

3. **Сделайте правила явными:** что значит «готово к разработке» (по сути DoR), кто может брать задачи, как обрабатывать срочное.

4. **Классы обслуживания:** срочные, с фиксированной датой, обычные — с разными правилами.

5. **Измеряйте:** время цикла, пропускную способность, накопительную диаграмму потока.

6. **Регулярно улучшайте:** где копится работа, почему задачи возвращаются из разработки в анализ.

</Steps>

## Нотация: практики и метрики

| Практика Kanban | Смысл |
|---|---|
| Визуализация | Доска с реальными этапами потока |
| Ограничение WIP | Лимит задач в работе на этапе или на человека |
| Управление потоком | Следить за тем, чтобы задачи двигались, а не накапливались |
| Явные правила | Критерии перехода между колонками, приоритеты |
| Петли обратной связи | Регулярные встречи по потоку, ретроспективы |
| Совместное улучшение | Изменения процесса на основе данных |

| Метрика | Смысл |
|---|---|
| Время выполнения (lead time) | От поступления запроса до готовности — то, что видит заказчик |
| Время цикла (cycle time) | От начала работы до готовности |
| Пропускная способность (throughput) | Сколько задач завершено за период |
| WIP | Сколько задач в работе сейчас |
| CFD | Накопительная диаграмма: расширяющаяся полоса этапа = там копится работа |

**Закон Литтла:** среднее время цикла = средний WIP / средняя пропускная способность. При той же скорости команды меньший WIP означает более быстрое прохождение каждой задачи.

```text title="Доска с колонкой анализа и лимитами"
| Новые | Анализ (≤3) | Готово к разработке | Разработка (≤4) | Тестирование (≤3) | Готово |
|-------|-------------|---------------------|-----------------|-------------------|--------|
|  ...  |  в работе   |   прошло DoR        |                 |                   |        |
```

## Пример из кейса IDM-JOINER

Kanban — естественный режим **после запуска** IdM, когда проект переходит в развитие и поддержку:

- поток заявок на подключение новых целевых систем в волнах 2–3 (каждая — типовая задача по <CaseRef href="/case/02-requirements/non-functional-requirements/#nfr-10" id="NFR-10">NFR-10</CaseRef>: коннектор, маппинг, полномочия в каталоге, тесты);
- изменения ролевой модели по запросам владельцев ресурсов (<CaseRef href="/case/02-requirements/role-model/" id="Роли">ролевая модель</CaseRef>);
- разбор инцидентов и DLQ.

Колонка «Анализ» с лимитом и правилом «готово к разработке» не даст задачам на подключение систем попадать в разработку без маппинга и контрактов.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Доска без лимитов WIP | Это просто список задач, поток не улучшается | Лимиты на колонках |
| Нет колонки анализа | Не видно, где задачи ждут требований | Анализ — отдельный этап потока |
| Правила перехода не записаны | Задачи «прыгают» неготовыми | Явные критерии (как DoR) |
| Не измерять поток | Улучшения «на ощущениях» | Время цикла, CFD |
| Срочное без правил | Всё становится срочным | Классы обслуживания с лимитами |
