<Brief>

Сбой должен обнаруживать **мониторинг, а не пользователь**, а разбираться в нём должно быть возможно по **логам и сквозному идентификатору**. Это закладывается в требования заранее — обычно как НФТ «наблюдаемость».
Что требует аналитик: **метрики**, отвечающие на бизнес-вопрос («успеем ли к сроку»), **алерты** с порогом и **ссылкой на процедуру**, **структурированные логи без ПДн**, **traceId** через все системы, **runbook** для типовых ситуаций.
Хорошая проверка: можно ли по одному `traceId` собрать путь операции через все системы и понять, где она споткнулась.

</Brief>

## Когда применять

| Применять | Не нужно / проще |
|---|---|
| Система с интеграциями, очередями, отложенными операциями | Внутренний инструмент без интеграций — достаточно базового мониторинга эксплуатации |
| Есть сроки, к которым результат должен быть готов | — |
| После инцидента: чего не хватило, чтобы узнать раньше и разобраться быстрее | — |

## Как делать

<Steps>

1. **Начните с вопросов эксплуатации:** работает ли сейчас? успеем ли к сроку? где застряло? — и подберите метрики под них.

2. **Для каждого алерта** задайте порог, приоритет, получателя и **процедуру** в runbook.

3. **Опишите логи:** обязательные поля, уровни, идентификаторы бизнес-объектов, что запрещено писать (ПДн, секреты).

4. **Введите сквозной идентификатор**, который передаётся во все вызовы и попадает в журнал аудита.

5. **Опишите runbook** для типовых ситуаций: признаки → что проверить → действия → когда эскалировать.

6. **После каждого инцидента** дополняйте метрики, алерты и runbook тем, чего не хватило.

</Steps>

## Нотация

| Метрика | Вопрос | Пример |
|---|---|---|
| Задержка обработки | Успеваем ли? | 95% событий не дольше 5 минут |
| Длина очередей, отставание потребителей | Не копится ли работа? | Сообщения в топике, задачи в ожидании повтора |
| Доля ошибок по интеграциям | Здорова ли интеграция? | Ошибки коннектора за час по системам |
| Ручные задачи | Не превратился ли сбой в ручную работу? | Задачи на ручное исполнение по системам за час |
| Готовность к сроку | Будет ли результат вовремя? | Активации к 07:00 по часовым поясам |

```json title="Структурированная запись лога"
{
  "ts": "2027-06-14T09:00:04.112+03:00",
  "level": "WARN",
  "component": "provisioning",
  "traceId": "7d1c0e3b9a4f4c2e8b5a61f0d2c4e9a1",
  "taskId": "t-90412",
  "personId": "P-100611",
  "system": "ABS",
  "operation": "CREATE",
  "attempt": 1,
  "httpStatus": 503,
  "msg": "technical error, retry scheduled"
}
```

В записи — идентификаторы, а не ФИО и телефоны. Сквозной идентификатор передаётся между системами в заголовке `traceparent` по стандарту W3C Trace Context.

```markdown title="Процедура runbook — каркас"
### RB-NN. <Ситуация>
- **Признаки:** алерт …, обращение …
- **Проверить:** …
- **Действия:** …
- **Эскалация:** когда и кому
```

## Пример из кейса IDM-JOINER

- <CaseRef href="/case/08-operations/monitoring-alerting/" id="Мониторинг">Мониторинг и алерты</CaseRef>: метрики из NFR-11, алерты ALR-01…ALR-06, у каждого — процедура runbook; `traceId` попадает в журнал аудита (`correlation_id`).
- <CaseRef href="/case/08-operations/runbook/" id="Runbook">Runbook</CaseRef>: DLQ, задачи на ручное исполнение, повторный запуск с проверками, активация, сверка, откат подразделения.
- Урок инцидента INC-01: ALR-02 «ошибки коннектора» сработал через 7 минут, но **роста ручных задач** как отдельного сигнала не было — алерт ALR-04 добавлен по итогам разбора.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Метрики только «сервер жив» | Система «работает», а задачи стоят | Метрики на бизнес-вопрос: успеем ли |
| Алерт без процедуры | Дежурный не знает, что делать | Ссылка на runbook у каждого алерта |
| Слишком много алертов | На них перестают реагировать | Алерт — только когда нужно действие |
| ПДн в логах | Нарушение требований ИБ и закона | Идентификаторы вместо персональных данных |
| Нет сквозного идентификатора | Путь операции не собрать | traceId во всех вызовах и в аудите |
