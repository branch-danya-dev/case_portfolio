<Brief>

Типичная постановка: **«CRM должна начать работать с АБС»** — и вы отвечаете только за эту связку. Не нужно анализировать всю CRM и всю АБС: нужно описать **обмен между ними** так, чтобы обе команды его реализовали одинаково, а при сбое было понятно, что делать.
Рамка вопросов: **кто провайдер и потребитель, кто владелец данных, SLA, контракт, маппинг, ошибки, идемпотентность, безопасность, мониторинг, тестовый контур, процесс релиза**.
Результат — описание интеграции и согласованный контракт.

</Brief>

## Что известно на входе

- Бизнес-потребность в одну фразу и, возможно, срок.
- Две (или больше) системы, у каждой своя команда, свои приоритеты и своё понимание задачи.
- Иногда — уже существующий API у одной из сторон, иногда — ничего.
- Почти всегда неясно, кто владелец данных и что делать при ошибках.

## Главная задача аналитика

Согласовать между командами **одно понимание обмена** — данные, контракт, поведение при ошибках, безопасность, эксплуатацию — и зафиксировать его так, чтобы по описанию можно было разработать, протестировать и сопровождать интеграцию.

## С кем поговорить

| Кто | Что выяснить |
|---|---|
| Бизнес-заказчик интеграции | Сценарии, объёмы, насколько срочно данные нужны, что будет при задержке |
| Аналитики и разработчики обеих систем | Что умеет каждая система, существующие API, ограничения |
| Владелец данных | Какая система — мастер для каждого атрибута |
| Архитектор, команда интеграции | Стандарты: синхронно или через брокер, шина, форматы |
| ИБ | Аутентификация, шифрование, ПДн и банковская тайна, сетевой доступ |
| Эксплуатация обеих систем | Мониторинг, кто разбирает инциденты, окна обслуживания |

## Что изучить

<Steps>

1. **Провайдер и потребитель:** кто отдаёт данные или функцию, кто использует; кто инициирует обмен.

2. **Владелец данных:** мастер-система для каждой сущности и атрибута; кто имеет право менять.

3. **SLA и объёмы:** сколько сообщений или вызовов, пики, допустимая задержка, доступность.

4. **Контракт:** операции или события, схемы, версии — в OpenAPI, AsyncAPI или WSDL.

5. **Маппинг:** поле в поле, преобразования, справочники, обязательность.

6. **Ошибки:** какие бывают, какие повторять, куда уходит то, что не удалось обработать (DLQ, задача человеку).

7. **Идемпотентность:** ключ, по которому повтор не создаёт дубль.

8. **Безопасность:** аутентификация (mTLS, OAuth 2.0), ПДн, сетевые доступы.

9. **Мониторинг:** метрики, алерты, кто реагирует.

10. **Тестовый контур:** стенды обеих систем, заглушки, тестовые данные.

11. **Процесс релиза:** порядок выкатки, обратная совместимость, переключение.

</Steps>

## Что проверить самостоятельно

- Для каждого поля маппинга известен источник, формат и что делать, если его нет.
- Для каждой ошибки определено: повторять или нет, сколько раз, что потом и кто разбирает.
- Ключ идемпотентности действительно уникален для операции и одинаков при повторе.
- Обе команды согласны с контрактом письменно (а не «вроде договорились на созвоне»).
- Есть способ сверить данные между системами, если что-то потеряется.

## Какие артефакты создать

| Артефакт | Зачем |
|---|---|
| Описание интеграции (одна страница) | Общая картина: кто, что, как, что при сбое |
| Контракт (OpenAPI / AsyncAPI) | Основа для разработки и тестов обеих сторон |
| Маппинг данных | Поле в поле, преобразования, справочники |
| Sequence-диаграмма с ветками ошибок | Поведение при сбоях на одной картинке |
| Строка в карте интеграций | Чтобы интеграцию нашли следующие люди |

Каркас описания — в [генераторе шаблонов](/tools/artifact-generator/) (шаблон «Описание интеграции»), проверка контракта — в [просмотрщике OpenAPI](/tools/openapi-viewer/).

## Первый результат работы

**Согласованное обеими командами описание интеграции и черновик контракта** — с владельцем данных, маппингом, таблицей ошибок и ключом идемпотентности. Дальше по нему пишут код и тесты обе стороны.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Анализировать всю чужую систему | Недели работы без результата | Только то, что касается обмена |
| Не определить владельца данных | Две системы перезаписывают друг друга | Мастер-система для каждого атрибута |
| Описать только успешный сценарий | Потери и дубли в эксплуатации | Таблица ошибок, повторы, идемпотентность, DLQ |
| Договориться устно | На тестах выясняется, что поняли по-разному | Контракт и описание, согласованные письменно |
| Забыть тестовый контур и релиз | Интеграцию негде проверить, выкатили в неверном порядке | Стенды, заглушки, порядок релизов — в описании |
