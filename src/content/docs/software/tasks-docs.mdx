<Brief>

Два места, где живёт работа аналитика: **трекер** — единицы работы (эпики, истории, дефекты), **вики или репозиторий** — долгоживущее описание системы (требования, интеграции, модели).
Связка «страница требований ↔ задачи трекера» — основа трассировки на практике.
Docs-as-code (Markdown в Git) заменяет вики там, где документация должна проходить ревью вместе с кодом.

</Brief>

## Как выбрать

| Нужно | Инструмент |
|---|---|
| Бэклог, спринты, дефекты | Трекер: Jira, YouTrack, Яндекс Трекер, Kaiten, Redmine |
| Описание системы, которое читают годами | Вики: Confluence или аналог |
| Требования с ревью и историей изменений | Markdown в Git: VS Code + GitLab / GitHub |
| Личные заметки, конспекты интервью | Obsidian или любой Markdown-редактор |
| Маппинг, матрица трассировки, RACI | Таблица — потом перенести в вики |

## Пример из кейса IDM-JOINER

<CaseRef href="/case/02-requirements/backlog/" id="Бэклог">Бэклог кейса</CaseRef> прямо описывает связку: каждая история в Jira — отдельная задача со ссылкой на ФТ в Confluence; ФТ — долгоживущее описание системы, истории — единицы работы. Для малого проекта шпаргалка кейса советует вести трассировку «FR → тест» связями задач в Jira вместо отдельной таблицы.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Требования только в описаниях задач | После закрытия задач нет актуального описания системы | ФТ — в вики, в задаче — ссылка |
| Вики без структуры и владельцев | Дубли и устаревшие страницы | Шаблон пространства, владелец раздела, статус страницы |
| Трекер без связей | Трассировка теряется | Связи «эпик → история → тест», ссылки на страницы |
| Таблица как постоянное хранилище | Версии расходятся по почте | Таблица — черновик, итог — в вики |
