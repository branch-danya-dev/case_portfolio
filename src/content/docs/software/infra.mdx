<Brief>

Это не инструменты аналитика, а **инструменты проекта**, с которыми аналитик сталкивается каждый день: где запущены сервисы (Docker, Kubernetes), как изменение попадает на среду (CI/CD), где смотреть логи, метрики и трассы (Kibana, Grafana, Prometheus, Jaeger), откуда берутся токены и секреты (Keycloak, Vault), что стоит перед API (шлюз).
Настраивать их аналитик не должен. Нужно **понимать, что они делают и как это влияет на требования**, и уметь **читать**: найти запрос по `traceId`, открыть дашборд после релиза, увидеть, на какой среде какая версия.
На каком уровне что нужно знать — на странице [«Технологический стек для аналитика»](/software/stack/).

</Brief>

## Что аналитик делает с этими инструментами

| Задача | Инструмент | Что смотреть |
|---|---|---|
| Разобрать дефект или инцидент | Kibana / OpenSearch Dashboards, Jaeger | Все записи одной операции по `traceId`; где в цепочке ошибка или задержка |
| Проверить релиз на продуктиве | Grafana | Ошибки, задержки, очереди и бизнес-метрики до и после выкладки |
| Понять, когда изменение будет на среде | GitLab CI / Jenkins | Прошёл ли конвейер, какая версия на TEST, UAT, PROD |
| Поднять заглушку или учебное окружение | Docker | Контейнер с заглушкой по контракту, базой, брокером |
| Объяснить поведение при нескольких экземплярах сервиса | Kubernetes | Сколько подов, как выкладывается новая версия, что при перезапуске |
| Описать доступ интеграции | Keycloak | Клиент, scopes, роли, сроки жизни токенов |
| Описать секреты интеграции | Vault | Какие секреты, кто владелец, как меняются без простоя |
| Понять ошибку на входе в API | API-шлюз | Лимиты, проверка токенов, 429, 502 и 504 от шлюза, а не от сервиса |
| Объяснить «показывает старые данные» | Redis | Срок жизни ключа кэша и когда он сбрасывается |

## Пример из кейса IDM-JOINER

- **Логи и трассировка.** В <CaseRef href="/case/08-operations/incident-example/" id="INC-01">разборе INC-01</CaseRef> путь операции собирается по `traceId`: лог сервиса провижининга показывает три ответа 503 подряд и переход задачи в MANUAL. Именно так это выглядит в Kibana.
- **Метрики и алерты.** <CaseRef href="/case/08-operations/monitoring-alerting/" id="ALR">Мониторинг кейса</CaseRef> — метрика `event_processing_seconds` и правила ALR-01 … ALR-06: в Prometheus это метрики и правила, в Grafana — дашборд дежурного.
- **Секреты.** NFR-08 и SEC-07: учётные данные коннекторов — только в хранилище секретов, отдельно для каждой среды.
- **Среды и выкладка.** <CaseRef href="/case/06-rollout/release-plan/" id="Релиз 1.0">План релиза</CaseRef>: одна сборка проходит DEV → TEST → UAT → PREPROD → PROD, меняются только конфигурация и секреты — это и делает конвейер CI/CD.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| «Это DevOps, мне не нужно» | Требования не учитывают несколько экземпляров, перезапуски, лимиты шлюза | Понимать следствия для требований, не настраивая инструменты |
| Ждать от разработчиков выгрузку логов | Разбор инцидента растягивается на дни | Самому искать по `traceId` в системе логов с доступом на чтение |
| Проверять релиз только smoke-тестом | Не видно, решает ли изменение задачу | Смотреть метрики до и после на дашборде |
| Запрашивать у администраторов пароли интеграций «для теста» | Секреты расходятся по людям и документам | Описывать, какой секрет нужен; значение — только в хранилище |
| Путать ошибки шлюза и сервиса | Неверный вывод «сервис упал» | 502 и 504 — шлюз не дождался сервиса; смотреть логи обоих |
