<Brief>

**Обязательный минимум для любого уровня:** SQL и клиент БД, HTTP и REST с Postman или curl, чтение OpenAPI, JSON и XML, Jira и Confluence, нотации BPMN и UML в инструменте диаграмм, понятия брокеров (топик, очередь, DLQ), поиск по логам по `traceId`, Git на уровне чтения и merge request, DevTools браузера. Без этого аналитик не может проверить ни требование, ни интеграцию.
Дальше уровни отличаются не числом технологий, а **глубиной**: junior знает, что это и как пользоваться; middle учитывает в требованиях и сам разбирает проблемы; senior выбирает решения и обсуждает компромиссы с архитектором и эксплуатацией.
От аналитика обычно **не ждут** настройки инфраструктуры: Dockerfile, манифесты Kubernetes, конвейеры, администрирование. Ждут понимания, **как это влияет на требования**.

</Brief>

## Когда применять

| Применять | Не нужно / проще |
|---|---|
| Готовите резюме или собеседование: что честно написать в стеке и как об этом рассказать | Вакансия аналитика данных или BI — там другой стек (DWH, ETL, BI-инструменты) |
| Входите в проект и видите незнакомые технологии в архитектуре | Нужно настроить инструмент — это задача DevOps и администраторов |
| Планируете развитие: что подтянуть для перехода на следующий уровень | — |
| Пишете вакансию или проводите собеседование как интервьюер | — |

## Как делать

<Steps>

1. **Закройте обязательный минимум.** Для каждого пункта таблицы ниже — практика на сайте: SQL-тренажёр, API Lab, просмотрщик OpenAPI, JSON / YAML.

2. **Сверьтесь с вакансией.** Подчеркните технологии из стека компании и определите, на каком уровне матрицы вы по каждой.

3. **Поднимайте уровень через задачи, а не курсы.** Middle по Kafka — это не «прочитал документацию», а «описал обработку дублей и DLQ и сам нашёл событие при разборе дефекта».

4. **Для незнакомой технологии на проекте** задайте три вопроса: что она делает в нашей системе, как влияет на требования (повторы, задержки, доступ, конфигурация), где смотреть её состояние (логи, метрики, UI).

5. **На собеседовании** рассказывайте про технологию через задачу: «нашёл по `traceId` в Kibana, что адаптер отвечает 503» звучит сильнее, чем «знаю ELK».

</Steps>

## Матрица стека

### Обязательно для любого уровня

| Навык | Что уметь | Как проверить себя на сайте |
|---|---|---|
| SQL и клиент БД (DBeaver или аналог) | SELECT, фильтры, JOIN, GROUP BY; найти данные для разбора дефекта | [SQL-тренажёр](/tools/sql-trainer/), уровни «база» и «средний» |
| HTTP и REST | Методы, коды ответов, заголовки, тело; отправить запрос в Postman или curl | [API Lab](/tools/api-lab/), [справочник HTTP](/tools/http-reference/) |
| OpenAPI (Swagger) | Читать контракт: методы, обязательные поля, ошибки, схемы | [Просмотрщик OpenAPI](/tools/openapi-viewer/) |
| JSON, XML, JSON Schema | Читать структуру, проверить документ по схеме | [JSON / YAML](/tools/json-yaml/) |
| Jira и Confluence | Задачи и связи, страницы требований, история изменений | [Каталог ПО: задачи и документация](/software/tasks-docs/) |
| Нотации и инструмент диаграмм | BPMN, sequence, state в draw.io, PlantUML или Mermaid | [Песочница Mermaid](/tools/mermaid-sandbox/), [BPMN-редактор](/tools/bpmn-editor/) |
| Брокеры — понятия | Событие, топик, очередь, группа потребителей, DLQ; найти сообщение в UI | [Брокеры сообщений](/integrations/messaging/) |
| Логи | Найти все записи одной операции по `traceId` | [Мониторинг, логи и runbook](/operations/observability/) |
| Git — чтение | Найти файл контракта, посмотреть историю, оставить комментарий в merge request | [Docs-as-code](/documentation/docs-as-code/) |
| DevTools браузера | Какой запрос ушёл с фронтенда, что вернулось, какой код | [Каталог ПО: API](/software/api/) |

### По уровням

**Junior** — знает, что это и зачем, пользуется под руководством. **Middle** — применяет сам, учитывает в требованиях, разбирает проблемы. **Senior** — выбирает и проектирует, обсуждает компромиссы, учит других.

| Технология | Junior | Middle | Senior |
|---|---|---|---|
| **Данные** | | | |
| Реляционные СУБД (PostgreSQL, Oracle, MS SQL) | SELECT, JOIN, агрегаты; читает ER | Подзапросы, оконные функции; логическая модель, нормализация, индексы в требованиях | Модели для интеграций и отчётности, миграция данных, компромиссы денормализации |
| NoSQL и Redis | Знает типы БД и что такое кэш | Описывает срок жизни и сброс кэша, проверяет ключи | Выбирает тип хранилища под требования согласованности |
| **Интеграции** | | | |
| REST и OpenAPI | Читает контракт, отправляет запросы | Проектирует API: ошибки, идемпотентность, пагинация, версии | Правила API для нескольких команд, совместимость и порядок выкладки |
| SOAP, XSD, WSDL | Читает WSDL и XSD | Описывает интеграцию с SOAP-сервисом, маппинг | Переход SOAP → REST, работа с шиной |
| Kafka | Топик, партиция, событие, группа потребителей | Описывает гарантии доставки, дубли, порядок, DLQ, схему события; ищет события в UI | Выбирает между брокерами, проектирует событийную модель и версии схем |
| RabbitMQ | Очередь, обменник, привязка | Маршрутизация, подтверждения, повторы, DLQ | Выбор между Kafka и RabbitMQ под задачу |
| gRPC, GraphQL | Знает, что это и когда применяют | Читает .proto и схему GraphQL | Выбирает стиль интеграции |
| API-шлюз | Знает, что запросы идут через шлюз | Учитывает лимиты, ошибки шлюза, маршрутизацию версий | Решает, что выносить в шлюз, а что в сервис |
| **Инфраструктура и поставка** | | | |
| Git и merge request | Читает файлы и историю, комментирует | Ведёт контракты и требования в репозитории, проходит ревью | Выстраивает docs-as-code в команде |
| Docker | Знает, что такое образ и контейнер | Поднимает заглушку или окружение по инструкции | Учитывает в требованиях конфигурацию и секреты по средам |
| Kubernetes / OpenShift | Знает, что сервис работает в нескольких экземплярах | Учитывает в требованиях перезапуски, параллельность, поэтапную выкладку | Обсуждает масштабирование и отказоустойчивость с архитектором |
| CI/CD (GitLab CI, Jenkins) | Знает, как изменение попадает на среду | Отслеживает версии на средах, предлагает автопроверки (линтер OpenAPI) | Встраивает проверки требований и контрактов в конвейер |
| Среды и конфигурация | Знает DEV, TEST, UAT, PREPROD, PROD | Описывает параметры, различающиеся по средам | Планирует выпуск: порядок, флаги, откат |
| **Наблюдаемость** | | | |
| Логи (ELK, OpenSearch, Loki) | Ищет по `traceId` по подсказке | Сам проходит путь операции, формулирует требования к логам | Выстраивает стандарт логирования и трассировки |
| Метрики (Prometheus, Grafana) | Открывает дашборд, видит всплеск | Формулирует метрики и пороги алертов, смотрит релиз на дашборде | Определяет бизнес-метрики и SLO вместе с владельцем продукта |
| Трассировка (Jaeger, OpenTelemetry) | Знает, что такое трасса | Находит по трассе медленный или упавший участок | Требует сквозной трассировки в новых интеграциях |
| **Безопасность** | | | |
| OAuth 2.0, OIDC, Keycloak | Отличает аутентификацию от авторизации, знает про токены | Описывает клиентов, scopes, роли и сроки токенов | Проектирует модель доступа вместе с ИБ |
| Секреты (Vault) | Знает, что пароли не хранят в коде | Описывает секреты интеграции, владельца, замену | Учитывает ротацию и отказоустойчивость хранилища секретов |
| TLS и mTLS | Знает, что канал шифруется | Описывает сертификаты и сроки их действия | Решает с ИБ, где нужен mTLS |
| **Процессы** | | | |
| BPM-движок (Camunda и аналоги) | Читает BPMN | Описывает исполняемый процесс: задачи, события, таймеры | Решает, что автоматизировать движком, а что кодом |

### Чего от аналитика обычно не ждут

| Не ждут | Но ждут |
|---|---|
| Писать Dockerfile и манифесты Kubernetes | Понимать, что сервис запущен в нескольких экземплярах и может перезапуститься |
| Настраивать конвейеры CI/CD | Знать, когда изменение будет на среде и какие проверки его остановят |
| Администрировать Kafka, Keycloak, Vault | Описывать события, доступы и секреты, которые им нужны |
| Писать код сервиса | Читать код точечно, чтобы подтвердить правило (зависит от компании) |
| Настраивать сбор логов и метрик | Формулировать, что логировать и какие алерты нужны |

В некоторых компаниях роль аналитика шире: читать Java или Python, писать скрипты, самому собирать окружение. Это видно по вакансии — уточняйте на собеседовании.

## Пример из кейса IDM-JOINER

Стек кейса и что аналитик делал с каждой технологией:

| Технология | Где в кейсе | Работа аналитика |
|---|---|---|
| Kafka | Кадровые события `hr.employee.events.v1` и DLQ | <CaseRef href="/case/04-integrations/api-hr-events/" id="AsyncAPI">Контракт событий</CaseRef>, гарантии доставки, идемпотентность по `eventId` (FR-03) |
| REST и OpenAPI | API IdM и адаптера АБС | Контракты, ошибки, `Idempotency-Key` |
| Реляционная БД | БД IdM | <CaseRef href="/case/03-architecture/data-model/" id="Модель данных">Модель данных</CaseRef>, запросы для разбора и сверки |
| Логи и трассировка | `traceId` во всех вызовах, `traceparent` | Требования к логам без ПДн, разбор INC-01 |
| Метрики и алерты | ALR-01 … ALR-06 | Метрики и пороги по НФТ |
| OAuth 2.0, mTLS, Kerberos | API IdM, адаптер АБС, портал | Схемы безопасности, клиенты и scopes |
| Хранилище секретов | Учётные данные коннекторов | NFR-08, SEC-07 |
| Кластерное развёртывание | Доступность 99,5% (NFR-04) | Требования к идемпотентности и повторам при нескольких экземплярах |

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Список из 30 технологий в резюме | На собеседовании спросят про каждую, а ответить нечего | Честный уровень и пример задачи по каждой |
| «Kafka — это очередь» | Не видны гарантии доставки, порядок, хранение и повторное чтение | Понимать отличия от очереди и следствия для требований |
| Учить инструменты вместо понятий | При смене компании знания обесцениваются | Сначала понятие (метрика, трасса, секрет), потом конкретный продукт |
| Игнорировать инфраструктуру | Требования не учитывают повторы, параллельность, сроки токенов, лимиты | Три вопроса к каждой технологии: что делает, как влияет, где смотреть |
| Пытаться стать DevOps | Время уходит не на аналитику | Глубина — там, где технология меняет требования |
