<Brief>

**Тест-дизайн** — как из требований получить **минимальный набор тестов, который находит максимум ошибок**.
Четыре основные техники: **классы эквивалентности** (одно значение на группу с одинаковым поведением), **граничные значения** (ошибки живут на границах), **таблицы решений** (комбинации условий), **переходы состояний** (разрешённые и запрещённые переходы). Для многих параметров — **попарное тестирование**.
Аналитику эти техники нужны, чтобы писать **полные** требования: если для границы непонятно ожидаемое поведение — требование неполное.

</Brief>

## Когда применять

| Техника | Когда |
|---|---|
| Классы эквивалентности | Поле или параметр с множеством значений, которые ведут себя группами |
| Граничные значения | Диапазоны, лимиты, сроки, длины |
| Таблица решений | Результат зависит от комбинации нескольких условий |
| Переходы состояний | Объект со статусами |
| Попарное тестирование | Много параметров, полный перебор невозможен |
| Сценарии use case / sequence | Сквозные сценарии, альтернативы, ошибки интеграций |

## Как делать

<Steps>

1. **Выпишите входы** требования: поля, параметры, условия, события.

2. **Разбейте на классы** допустимых и недопустимых значений.

3. **Найдите границы** каждого диапазона и проверьте значения на границе и рядом.

4. **Комбинации условий** — таблица решений; проверьте, что для каждой комбинации определено действие.

5. **Статусы** — таблица переходов; добавьте запрещённые переходы.

6. **Сформулируйте ожидаемый результат** для каждого теста. Если не можете — требование неполное, задайте вопрос.

</Steps>

## Нотация: техники на примерах кейса

<Tabs>
<TabItem label="Классы эквивалентности">

Требование: IdM принимает события `HIRE`, `HIRE_CHANGED`, `HIRE_CANCELLED`; некорректное событие — в DLQ (FR-01, FR-02).

| Класс | Пример | Ожидаемое поведение |
|---|---|---|
| Допустимый: HIRE | `HIRE` | Создать идентичность, запланировать учётные записи |
| Допустимый: HIRE_CHANGED | `HIRE_CHANGED` | Пересчитать по таблице реакций FR-18 |
| Допустимый: HIRE_CANCELLED | `HIRE_CANCELLED` | Отменить / удалить по FR-18 |
| Недопустимый: неизвестный тип | `HIRE_TRANSFER` | DLQ + инцидент |
| Недопустимый: пусто / нет поля | `""`, поле отсутствует | DLQ + инцидент |

Три допустимых типа — **разные** классы, потому что у каждого своя логика. Все недопустимые — один класс: поведение одинаковое.

</TabItem>
<TabItem label="Граничные значения">

**Длина логина** — не более 20 символов, при превышении усекается фамилия (FR-06):

| Длина исходного логина | Ожидание |
|---|---|
| 19 | Как есть |
| 20 | Как есть (граница) |
| 21 | Усечение фамилии до 20 символов |

**Срок создания** — за 3 рабочих дня до выхода; если меньше — сразу (FR-07, BRL-01):

| Событие пришло до выхода | Ожидание |
|---|---|
| 4 рабочих дня | Создание запланировано на T−3 |
| 3 рабочих дня | Создание в день события (граница) |
| 2 рабочих дня | Создание сразу |
| 1 рабочий день | Создание сразу — TC-07 |

Техника сразу поднимает вопросы к требованию: какие дни рабочие и по какому времени считать? В кейсе ответ уже есть — раздел 2.2 ФТ: производственный календарь банка и часовой пояс подразделения (`orgUnit.timezone`). Если бы его не было, это был бы пробел в требовании.

</TabItem>
<TabItem label="Таблица решений">

**Политика повторов** (FR-16) — комбинация «ответ системы» × «номер попытки»:

| Условие / правило | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| Ответ | Успех | 5xx / тайм-аут | 5xx / тайм-аут | 429 | 4xx (кроме 429) |
| Попытка < 3 | — | да | нет | да | — |
| **Действие** | DONE | Повторить (RETRY_WAIT) | MANUAL + задача в ServiceDesk | Повторить | MANUAL + задача в ServiceDesk, без повторов |

Каждая колонка — тест. Пустая или противоречивая колонка — вопрос к требованию.

</TabItem>
<TabItem label="Переходы состояний">

**Учётная запись** (<CaseRef href="/case/03-architecture/state-models/" id="Статусы">статусная модель</CaseRef>):

| Тест | Исходное | Событие | Ожидаемое |
|---|---|---|---|
| Позитивный | PLANNED | Таймер, наступила дата | CREATING |
| Позитивный | CREATING | Успех коннектора | CREATED_DISABLED |
| Позитивный | CREATED_DISABLED | 07:00 в день выхода | ACTIVE |
| Позитивный | CREATED_DISABLED | HIRE_CANCELLED | DELETED |
| **Негативный** | ACTIVE | Попытка вернуть в CREATED_DISABLED | Отклонено |
| **Негативный** | DELETED | Любое событие | Отклонено / без изменений |
| **Негативный** | PLANNED | Активация без создания | Отклонено |

</TabItem>
<TabItem label="Попарное тестирование">

Параметры приёма из тестовых данных ПМИ: часовой пояс подразделения (4), фамилия (обычная, длинная, двойная — 3), тип трудоустройства (MAIN, PART_TIME — 2), отчество (есть, нет — 2). Полный перебор — 4 × 3 × 2 × 2 = 48 комбинаций. Попарный набор покрывает каждую пару значений любых двух параметров; его нижняя граница — произведение двух самых больших доменов, 4 × 3 = 12 тестов, и генераторы попарных наборов обычно подбирают набор, близкий к ней.

</TabItem>
</Tabs>

## Пример из кейса IDM-JOINER

<CaseRef href="/case/07-testing/test-cases/#tc-12" id="TC-12">TC-12</CaseRef> — подробный тест-кейс, построенный сразу несколькими техниками:

- **sequence-диаграмма** SEQ-02 дала сценарий «АБС недоступна»;
- **таблица решений** политики повторов — шаги 3–4 (`attempts = 1` → RETRY_WAIT, `attempts = 3` → MANUAL);
- **статусная модель** задачи — ожидаемые статусы на каждом шаге;
- **контракт** адаптера — проверка, что все три запроса ушли с одинаковым `Idempotency-Key` (шаг 7);
- **управляемое время стенда** — сдвиг на D−3 и на 5 минут, иначе тест длился бы дни.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Проверять только «среднее» значение | Ошибки на границах пропущены | Значения на границе и рядом |
| Каждое значение — отдельный тест | Сотни тестов без пользы | Одно значение на класс эквивалентности |
| Не проверять комбинации условий | Пропущены правила, которые срабатывают «вместе» | Таблица решений |
| Только разрешённые переходы | Запрещённые переходы проходят в проде | Негативные тесты по статусной модели |
| Нет ожидаемого результата | Тест нельзя пройти или провалить | Если ожидание неясно — вопрос к требованию |
