<Brief>

Хорошее требование **необходимо, однозначно, атомарно, проверяемо, выполнимо и трассируемо**. Хороший набор требований — ещё и **полный и непротиворечивый**.
Главный практический тест: **можно ли по этому требованию написать тест?** Если нет — требование размыто.
Размытые слова («быстро», «удобно», «и т. д.», «по возможности») заменяются измеримыми критериями.

</Brief>

## Когда применять

| Применять | Не нужно |
|---|---|
| Ревью своих и чужих требований перед согласованием | Требовать формальной идеальности от черновика на мозговом штурме |
| Перед передачей в разработку (DoR) | — |
| Разбор спорного дефекта: «баг или неверное требование?» | — |
| Подготовка ТЗ или ФТ к формальному согласованию | — |

## Как делать

<Steps>

1. **Одно требование — одно утверждение.** Видите «и», «а также», «или» — проверьте, не два ли это требования.

2. **Субъект — система или конкретная роль**, глагол — «должна» + действие. Не «предусмотреть возможность», а «IdM должна…».

3. **Конкретика вместо оценок:** числа, единицы, условия. «Быстро» → «за 5 минут для 95% событий».

4. **Условия и исключения — явно:** при каком условии, что если данных нет, что при ошибке.

5. **Ссылка на источник** — БТ, стейкхолдер, нормативный документ.

6. **Критерий приёмки** — как проверить, что требование выполнено.

7. **Прогон по чек-листу** (ниже) и ревью коллегой: однозначность лучше всего проверяет другой человек.

</Steps>

## Нотация: свойства, размытые слова, чек-лист

### Свойства требования

| Свойство | Вопрос для проверки |
|---|---|
| Необходимое | Что сломается, если его убрать? Есть ли источник? |
| Однозначное | Поймут ли его одинаково разработчик, тестировщик и заказчик? |
| Атомарное (единичное) | Одно ли это требование? |
| Проверяемое | Можно ли написать тест? Какой результат ожидаем? |
| Выполнимое | Реализуемо ли в рамках технологий, бюджета, сроков? |
| Корректное | Отражает ли реальную потребность? Подтверждено ли источником? |
| Трассируемое | Есть ли ID, связь с БТ, с тестом? |
| Независимое от реализации | Описывает ли «что», а не «как»? (для БТ и ФТ) |

Для **набора** требований: **полнота** (покрыты все БТ, альтернативы, ошибки), **непротиворечивость**, **понятность** — общая терминология (глоссарий).

### Размытые слова и замены

| Размытое | Почему плохо | Чем заменить |
|---|---|---|
| быстро, оперативно, своевременно | Не измерить | «не дольше 5 минут для 95% запросов» |
| удобно, интуитивно, дружественно | Субъективно | «пользователь без обучения выполняет X за 3 минуты» |
| надёжно, стабильно | Не измерить | доступность %, RTO, RPO |
| и т. д., и пр., и др. | Список не закончен — не реализовать и не проверить | Полный перечень |
| при необходимости, по возможности, желательно | Непонятно, обязательно ли | Условие («если…») или приоритет (S, C) |
| должна поддерживать, обрабатывать | Непонятно, что именно делает | Конкретные действия: принимает, проверяет, сохраняет… |
| как минимум, не менее (без числа) | Нет границы | Конкретное значение |
| гибкий, масштабируемый, современный | Не проверить | Конкретное изменение или нагрузка, которую выдержит |
| все, всегда, никогда | Часто неверно, проверить невозможно | Перечень случаев; явные исключения |
| и/или | Неоднозначно | Два требования или явное условие |

### Чек-лист ревью требования

```markdown title="Чек-лист: ревью требования"
- [ ] Есть ID и источник (БТ, стейкхолдер, документ)
- [ ] Одно требование — одно утверждение (нет «и», «а также»)
- [ ] Субъект — система или роль; глагол — действие
- [ ] Нет размытых слов (быстро, удобно, и т. д., по возможности)
- [ ] Числа с единицами и условиями
- [ ] Описаны условия, исключения, поведение при ошибке
- [ ] Термины совпадают с глоссарием
- [ ] Не противоречит другим требованиям
- [ ] Описывает «что», а не «как» (если это не осознанное ограничение)
- [ ] Есть критерий приёмки / тест
- [ ] Указан приоритет
```

## Пример из кейса IDM-JOINER

Документ ФТ кейса задаёт шаблон: «Система должна \<действие\> \<объект\> \<условие/ограничение\>» и требует, чтобы ФТ было атомарным, проверяемым, однозначным и трассируемым. Сравните:

| Плохо | Как в кейсе |
|---|---|
| Система должна быстро обрабатывать события | 95% кадровых событий обрабатываются не дольше 5 минут — <CaseRef href="/case/02-requirements/non-functional-requirements/#nfr-01" id="NFR-01">NFR-01</CaseRef> |
| Система должна создавать логины | IdM должна генерировать уникальный логин по правилу из раздела 2.1 — <CaseRef href="/case/02-requirements/functional-requirements/#fr-06" id="FR-06">FR-06</CaseRef>, а правило расписано по шагам с таблицей примеров (транслитерация, длина, коллизии) |
| Портал должен быть удобным | Руководитель создаёт заявку не более чем за 3 минуты без обучения; проверка — юзабилити-тест на пилоте — <CaseRef href="/case/02-requirements/non-functional-requirements/#nfr-12" id="NFR-12">NFR-12</CaseRef> |
| Система должна обрабатывать повторы | IdM должна обрабатывать события идемпотентно по `eventId`: повторная доставка не приводит к повторным действиям — <CaseRef href="/case/02-requirements/functional-requirements/#fr-03" id="FR-03">FR-03</CaseRef> |

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Несколько требований в одном | Половину реализовали — требование «выполнено» или нет? | Разбить, каждому свой ID |
| «Предусмотреть возможность…» | Непонятно, что делает система | «Система должна \<действие>» |
| Только счастливый путь | Ошибки и исключения решает разработчик «по-своему» | Условия, ошибки, пустые данные |
| Решение вместо требования («кнопка в правом углу») | Связывает руки дизайну без причины | Цель и критерий; решение — если это осознанное ограничение |
| Разные слова для одного понятия | Разработка делает две сущности вместо одной | Глоссарий и единые термины |
| Нет критерия приёмки | Спор «сделано или нет» на приёмке | Критерий или сценарий Gherkin |
