<Brief>

**Пользовательская история** (user story) — короткое описание ценности с точки зрения пользователя: **«Как \<роль\>, я хочу \<действие\>, чтобы \<ценность\>»** плюс критерии приёмки.
История — не спецификация, а приглашение к разговору (**3C:** Card — карточка, Conversation — обсуждение, Confirmation — критерии приёмки).
Хорошая история отвечает **INVEST** и режется **вертикально**: каждая даёт работающий сквозной результат.

</Brief>

## Когда применять

| Применять | Не нужно / лучше другое |
|---|---|
| Scrum и Kanban: планирование работы небольшими порциями | Нужно полное описание взаимодействия с множеством ветвлений → use case |
| Команда рядом с пользователем, детали уточняются в диалоге | Формальное согласование по ГОСТ 34 → ФТ в ТЗ |
| Продуктовая разработка с частыми релизами | Интеграционный контракт → OpenAPI / AsyncAPI, а не история |
| В гибриде — как единица работы поверх долгоживущих ФТ | — |

## Как делать

<Steps>

1. **Роль — конкретная:** «руководитель», «администратор АБС», а не «пользователь».

2. **Действие — что хочет сделать**, без решения интерфейса.

3. **Ценность — зачем.** Если «чтобы» не придумывается — возможно, история не нужна или это enabler.

4. **Критерии приёмки** — список правил или сценарии Gherkin, включая ошибки.

5. **Проверка по INVEST.** Не помещается в спринт — режьте вертикально.

6. **Связь с эпиком и ФТ** — история ссылается на долгоживущее описание.

7. **Рефайнмент с командой** до DoR: понятно, оценено, зависимости согласованы.

</Steps>

## Нотация: формат, INVEST, нарезка

```markdown title="Шаблон истории"
### US-NN. <Короткое название> (EPIC-NN, FR-NN)

Как <роль>, я хочу <действие>, чтобы <ценность>.

**Критерии приёмки**
- <правило 1>
- <правило 2>
или сценарии Gherkin (Дано / Когда / Тогда)

**Заметки:** интеграции, контракты, макеты, зависимости
```

| Буква | Критерий | Вопрос для проверки |
|---|---|---|
| **I** | Independent — независимая | Можно ли сделать её отдельно от других? |
| **N** | Negotiable — обсуждаемая | Не превратилась ли в контракт с готовым решением? |
| **V** | Valuable — ценная | Кто получит пользу и какую? |
| **E** | Estimable — оцениваемая | Понимает ли команда, сколько работы? |
| **S** | Small — небольшая | Помещается ли в спринт (лучше — в несколько дней)? |
| **T** | Testable — проверяемая | Есть ли критерии, по которым QA скажет «готово»? |

### Иерархия

| Уровень | Что это | Пример из кейса |
|---|---|---|
| Эпик (epic) | Крупная цель, несколько спринтов | EPIC-01 «Приём кадровых событий» |
| История (story) | Ценность, помещается в спринт | US-01 «Автоматический запуск по приказу» |
| Enabler | Техническая работа без прямой ценности для пользователя, но нужная другим историям | US-06 «Подключить коннектор AD» |
| Задача (task) | Шаг реализации внутри истории | «Добавить таблицу hr_event_inbox» |

### Как резать историю (вертикально)

| Приём | Пример |
|---|---|
| По шагам процесса | Создать учётную запись → активировать → уведомить |
| По правилам и вариантам | Обычный приём → повторный приём → совместительство |
| По данным / системам | Сначала AD, затем Exchange, затем АБС |
| По сценариям | Успешный путь → повторы и ошибки |
| По операциям (CRUD) | Создать роль → изменить → удалить |
| По качеству | Сначала работает, затем — быстрее (НФТ отдельно) |

**Story mapping** — раскладка историй по шагам пользователя (горизонтально) и приоритету (вертикально): верхняя «полоса» — минимальный сквозной сценарий, то есть первый релиз.

## Пример из кейса IDM-JOINER

Из <CaseRef href="/case/02-requirements/backlog/" id="Бэклог">бэклога кейса</CaseRef>:

> **US-02.** Как администратор AD, я хочу, чтобы логин генерировался по единому правилу, чтобы не разбирать коллизии вручную. (<CaseRef href="/case/02-requirements/backlog/#us-02" id="US-02">EPIC-02, FR-06</CaseRef>)

```gherkin title="Критерии приёмки US-02"
Сценарий: Коллизия логина
  Дано в AD существует учётная запись "ivanov.ap"
  Когда принимается сотрудник "Иванов Андрей Павлович"
  Тогда ему назначается логин "ivanov.ap2"

Сценарий: Длинная фамилия
  Когда принимается сотрудник "Константинопольский Ярослав Юрьевич"
  Тогда ему назначается логин "konstantinopolski.ii" длиной 20 символов
```

Что показывает кейс:

- **ФТ и истории сосуществуют:** ФТ в Confluence — долгоживущее описание системы, истории в Jira — единицы работы со ссылкой на ФТ.
- **Ценность у технических ролей:** «как администратор АБС, я хочу получать задачу только после исчерпания повторов» (US-07) — ценность реальная, хотя пользователь не бизнес.
- **Enabler назван честно:** US-06 «Подключить коннектор AD» — без придуманной «ценности».
- **DoR и DoD** записаны прямо в бэклоге: есть критерии, ссылки на контракты, зависимости от команд HRMS и АБС согласованы.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| «Как пользователь, я хочу…» | Непонятно, для кого и какие права | Конкретная роль |
| Нет «чтобы» | Не видно ценности, сложно приоритизировать | Ценность или честный enabler |
| История = техническая задача («создать таблицу») | Нет ценности, нельзя принять | Задача внутри истории |
| Горизонтальная нарезка (сначала БД, потом API, потом UI) | Ни одна история не даёт результата | Вертикальная: тонкий сквозной сценарий |
| Нет критериев приёмки | Спор «готово или нет» | Правила или Gherkin до начала работы |
| История на весь спринт и больше | Риск не закончить, нет промежуточного результата | Резать до нескольких дней |
| Детальная спецификация в истории | Теряется гибкость и обсуждение | Детали — в критериях и ФТ |
