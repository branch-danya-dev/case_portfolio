<Brief>

**Use case** (вариант использования, прецедент) описывает взаимодействие **актора** с системой ради **значимого для актора результата** — включая альтернативы и ошибки.
Диаграмма показывает **кто и что** делает с системой, текстовая спецификация — **как именно**: предусловия, основной поток, альтернативы, исключения, постусловия.
Главная ценность — в **альтернативных потоках**: там прячутся требования, которые иначе забывают.

</Brief>

## Когда применять

| Применять | Не нужно / лучше другое |
|---|---|
| Сценарий с множеством ветвлений, ошибок и интеграций | Простая CRUD-операция → история с критериями приёмки |
| Нужно полное, долгоживущее описание поведения системы | Планирование работы в спринте → user stories, нарезанные из use case |
| Несколько акторов, включая системы и таймеры | Бизнес-процесс с передачей работы между людьми → BPMN |
| Источник для тест-кейсов: каждая альтернатива — тест | Алгоритм внутри системы → activity-диаграмма |

## Как делать

<Steps>

1. **Найдите акторов** — люди и системы вне вашей системы. Таймер тоже может быть актором.

2. **Для каждого актора — его цели.** Название use case = цель актора: «глагол + объект» («Запросить дополнительные доступы»), а не кнопка или экран.

3. **Нарисуйте диаграмму** — обзор: акторы, прецеденты, граница системы.

4. **Выберите, что детализировать.** Полная спецификация — для сложных и рискованных сценариев, краткая (2–3 предложения) — для простых.

5. **Опишите основной поток** — 5–10 шагов «актор делает / система делает», без деталей интерфейса.

6. **Для каждого шага спросите «а что может пойти иначе?»** — альтернативы (3a, 4a) и исключения.

7. **Пред- и постусловия**, включая постусловие неуспеха.

8. **Свяжите с ФТ** и используйте альтернативы как источник тест-кейсов.

</Steps>

## Нотация: шаблон спецификации

```markdown title="Шаблон спецификации use case"
## UC-NN. <Глагол + объект>

| Поле | Значение |
|---|---|
| Основной актор | |
| Второстепенные акторы | |
| Цель актора | <какой результат важен актору> |
| Предусловия | <что должно быть верно до начала> |
| Триггер | <что запускает сценарий> |
| Постусловия (успех) | <состояние системы после успеха> |
| Постусловия (неуспех) | <состояние после неуспеха> |
| Связанные требования | FR-…, BR-… |

**Основной поток**
1. <Актор> <действие>.
2. Система <действие>.

**Альтернативные потоки**
- 2a. <Условие>: <что происходит>, возврат к шагу N / завершение.

**Исключения**
- 3a. <Ошибка>: <реакция системы>.
```

| Элемент | Правило |
|---|---|
| Название | Цель актора: «глагол + объект». Не «Нажать Сохранить», не «Экран заявки» |
| Актор | Роль, внешняя по отношению к системе. Один человек может быть в двух ролях |
| Шаг | Одно действие одного участника; без деталей UI («выбирает сотрудника», а не «кликает по строке») |
| Альтернатива | Привязана к шагу (4a), описывает условие и что дальше |
| Исключение | Ошибка, после которой цель не достигается или достигается иначе |
| Уровень цели | Пользовательская цель (одно «присесть и сделать»); крупнее — обзорный, мельче — подфункция |

Про диаграмму (include, extend, обобщение) — в разделе UML: Use case.

## Пример из кейса IDM-JOINER

<PlantUmlDiagram file="02_requirements/diagrams/use-case.puml" title="Use case IdM (кейс IDM-JOINER)" showSource={false} />

Полная спецификация — <CaseRef href="/case/02-requirements/use-cases/#uc-01" id="UC-01">UC-01. Обработать кадровое событие о приёме</CaseRef>. На что обратить внимание:

- **Актор — система** (HRMS), а второстепенные — AD, Exchange, АБС, ServiceDesk.
- **Два постусловия:** при успехе — идентичность `PRE_HIRE`, учётные записи `CREATED_DISABLED`; при неуспехе — событие в DLQ и инцидент.
- **Альтернативы почти дублируют бизнес-правила** — повторный приём (3a, BRL-05), совместительство (3b, BRL-07), занятый логин (4a), нет правила роли (5a), SoD-конфликт (6a), меньше 3 дней до выхода (7a). Без них система работала бы только для «идеального» приёма.
- **Исключения** — некорректное событие (2a), повторный `eventId` (2b), техническая ошибка целевой системы (8a) со ссылкой на sequence SEQ-02.
- **Краткие спецификации** для простых сценариев (UC-02, UC-04 … UC-10) — 1–2 предложения. Не каждый use case нужно расписывать полностью.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Use case = кнопка или экран | Теряется цель, спецификаций становится сотни | Цель актора: «глагол + объект» |
| Только основной поток | Ошибки и редкие случаи решаются «как получится» | На каждом шаге: «а что может пойти иначе?» |
| Детали интерфейса в шагах | Спецификация устаревает при каждом изменении макета | Действия, а не клики |
| Нет постусловия неуспеха | Непонятно, в каком состоянии остаётся система | Два постусловия |
| Функциональная декомпозиция через include | Диаграмма превращается в дерево функций | include — только для реально общих частей |
| Актор — внутренний компонент системы | Граница системы нарушена | Акторы — только внешние |
