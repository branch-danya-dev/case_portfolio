<Brief>

**Анализ влияния** (impact analysis) отвечает на вопрос: **что ещё затронет изменение**, кроме того, о чём попросили. Бизнес говорит «добавим статус SUSPENDED» — а за этим стоят статусная модель, enum в контракте, ограничение в БД, экраны, отчёты, события в брокере, внешние потребители, правила, тесты, документация и **обратная совместимость**.
Метод: идти **по слоям** и по каждому отвечать «затронуто / не затронуто / неизвестно — кто скажет». Опора — [трассировка](/requirements/traceability/), но проверка — **по реальной системе**: поиск по коду и контрактам, запросы к данным, логи, список потребителей.
Это типичная работа middle-аналитика и частый вопрос на собеседовании.

</Brief>

## Когда применять

| Применять | Не нужно / проще |
|---|---|
| Любое изменение поведения существующей системы — статус, поле, правило, формат, интеграция | Изменение текста подсказки в интерфейсе |
| Изменение контракта API или события | Новая изолированная функция без связей — достаточно трассировки |
| Перед оценкой и планированием — от анализа зависит объём | — |
| Запрос на изменение посреди проекта — чтобы показать цену изменения | — |

## Как делать

<Steps>

1. **Зафиксировать изменение одной фразой** и с примером: «у заявки появляется статус SUSPENDED; ИБ переводит в него заявку на время проверки».

2. **Пройти трассировку** вверх (какие бизнес-требования и правила за этим стоят) и вниз (ФТ, UC, интеграции, тесты).

3. **Пройти по слоям** — чек-лист ниже. Для каждого слоя: затронут ли, что меняется, кто владелец.

4. **Проверить по реальной системе.** Поиск по коду и контрактам по значению (`ON_APPROVAL`, имя поля), запросы к БД (`SELECT DISTINCT status …`), логи и журнал вызовов — кто реально пользуется API и событиями.

5. **Найти владельцев** затронутого: смежные команды, владельцы отчётов, ИБ, эксплуатация. «Неизвестно» без владельца — не результат.

6. **Оценить совместимость и порядок выкатки:** ломает ли изменение существующих потребителей и в каком порядке выкатывать.

7. **Оформить таблицу влияния** — по ней оценивают объём, планируют регресс и согласуют изменение.

</Steps>

| Слой | Где смотреть | Типичный вопрос |
|---|---|---|
| Требования, правила | Матрица трассировки, ФТ, бизнес-правила | Какие правила опираются на изменяемое значение? |
| Статусная модель | Диаграмма состояний, таблица переходов | Из каких статусов и в какие? Что с таймерами? |
| API и контракты | OpenAPI, AsyncAPI, поиск по репозиторию | Это значение в ответе или в запросе? Кто клиенты? |
| БД | Схема, ограничения, `SELECT DISTINCT`, запросы с `IN (…)` | Пропустит ли ограничение новое значение? Где жёсткие списки? |
| Интерфейс | Экраны на стенде, макеты | Где показывается, фильтруется, меняется значение? |
| Отчёты | Список отчётов и выгрузок, их запросы | Попадёт ли новая запись в итоги или выпадет? |
| События, потребители | Схема события, группы потребителей топика, журнал вызовов API | Кто читает и как обработает незнакомое значение? |
| Безопасность, аудит | Ролевая модель, журнал аудита, правила SIEM | Кто имеет право? Что увидит ИБ? |
| Тесты | Тест-кейсы, автотесты | Какие проверки поменяются и что прогнать в регрессе? |

### Совместимость изменений API

| Изменение | Для существующих клиентов | Комментарий |
|---|---|---|
| Новое необязательное поле в ответе | Обычно совместимо | Если клиенты игнорируют незнакомые поля |
| Новое обязательное поле в запросе | Несовместимо | Старые клиенты его не отправляют |
| Удаление или переименование поля | Несовместимо | Нужна новая версия или переходный период |
| Новое значение enum **в запросе** | Совместимо | Старые клиенты просто его не используют |
| Новое значение enum **в ответе или событии** | Часто несовместимо | Клиент с жёстким перечислением упадёт на незнакомом значении |
| Сужение формата или длины | Несовместимо | Ранее допустимые данные станут ошибкой |
| Изменение смысла поля при той же схеме | Несовместимо | Самое опасное — схема проверку проходит |

Порядок выкатки несовместимого изменения — **«сначала потребители, потом провайдер»**: потребители учатся понимать новое (или терпимо относиться к незнакомым значениям), затем провайдер начинает его отдавать. Для крупных изменений — новая версия контракта или топика и переходный период, когда работают обе. Когда первым выкладывается поставщик, а когда потребитель, — на странице [«Совместимость и порядок выкладки»](/release/compatibility/).

## Пример из кейса IDM-JOINER

Учебная доработка на материале кейса: ИБ просит **приостанавливать заявку на доступ** на время служебной проверки — новый статус **SUSPENDED**. Путь доработки целиком — на странице [«Жизненный цикл доработки»](/role/change-lifecycle/). Таблица влияния:

| Слой | Что затронуто в кейсе | Что меняется или что выяснить |
|---|---|---|
| Статусная модель | <CaseRef href="/case/03-architecture/state-models/" id="Статусы">Заявка на доступ</CaseRef>: DRAFT → ON_APPROVAL → APPROVED / REJECTED / PROVISIONING → … | Переходы ON_APPROVAL → SUSPENDED и обратно, SUSPENDED → CANCELLED (отзыв, отмена приёма). Можно ли приостановить уже APPROVED или PROVISIONING? |
| Бизнес-правила | FR-14: срок согласования 1 рабочий день, при просрочке — эскалация | Останавливается ли срок на время приостановки? Иначе эскалации пойдут по каждой приостановленной заявке |
| API | <CaseRef href="/case/04-integrations/api-idm/" id="API IdM">API IdM</CaseRef>: `AccessRequest.status` — enum из 8 значений | Новое значение enum в **ответе** — проверить клиентов. Операции «приостановить» и «возобновить»: права (только ИБ → иначе 403), недопустимый переход → 409 |
| Позиции заявки | У позиций свой enum: ON_APPROVAL, APPROVED, REJECTED, GRANTED, FAILED | Приостанавливается заявка целиком или позиции тоже? Решение — в требованиях |
| БД | <CaseRef href="/case/03-architecture/data-model/" id="ER">Модель данных</CaseRef>: статус заявки | Ограничение на допустимые значения; запросы «активные заявки» с жёстким списком статусов |
| Интерфейс | Портал IdM: заявки руководителя, очередь согласующего (FR-13, FR-14) | Как показывать приостановленную, кто видит кнопки, что видит руководитель |
| Отчёты | FR-22 «Доступы сотрудника»; отчёты о сроках согласования | Не исказит ли приостановка статистику просрочек |
| События и потребители | INT-09: журнал аудита → Kafka → SIEM, схема `idm.audit.v1` ведёт ИБ | Новые действия «приостановлена / возобновлена» в журнале (FR-21); правила SIEM, которые фильтруют по статусам |
| Внешние потребители API | Системные клиенты API IdM (например, ServiceDesk) | Кто читает статус заявки — по журналу вызовов; предупредить до выкатки |
| Связанные правила | Отмена приёма: ON_APPROVAL → CANCELLED по HIRE_CANCELLED; SoD-проверка при отправке; уведомления FR-19 | HIRE_CANCELLED должен отменять и приостановленную заявку; перепроверять ли SoD при возобновлении; уведомлять ли руководителя |
| Тесты | TC-14 (заявка на критичное полномочие), TC-15 (отказ, просрочка, эскалация), TC-11 (SoD), TC-17 (аудит и SIEM) | Новые тесты переходов, включая запрещённые; регресс заявок, эскалаций, аудита |
| Документация | Статусная модель, OpenAPI, глоссарий, тест-кейсы, инструкции | Обновить в источнике истины после проверки на продуктиве |
| Совместимость | enum статуса в ответе API и, возможно, в событиях | Порядок: потребители готовы → IdM начинает отдавать SUSPENDED |

Вывод для заказчика: «один новый статус» — это изменения в шести слоях и согласование с ИБ и владельцами SIEM. Альтернатива, которая может оказаться дешевле, — флаг «приостановлена» поверх ON_APPROVAL без нового значения enum.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Смотреть только на то, о чём попросили | Ломаются отчёты, интеграции, потребители событий | Все слои по чек-листу |
| Анализ только по документации | Пропущено то, что в документах не отражено | Поиск по коду, данным, логам, журналу вызовов |
| «Неизвестно» без владельца | Вопрос так и остаётся открытым до инцидента | У каждого «неизвестно» — кто ответит и когда |
| Считать новое значение enum безопасным | Падают клиенты с жёстким перечислением | Проверить, где значение в ответах и событиях; порядок выкатки |
| Забыть про таймеры, сроки и уведомления | Ложные эскалации и рассылки | Проверить правила, которые опираются на статус и время |
| Не спланировать регресс | Анализ сделан, а проверять изменения будут только по новому | Из таблицы влияния — список регрессионных проверок |
