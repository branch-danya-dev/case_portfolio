<Brief>

**Критерии приёмки** (acceptance criteria) — условия, при которых требование или история считаются выполненными. Пишутся **до разработки**, проверяются тестом.
Два формата: **список правил** и **сценарии Gherkin** — **Дано** (контекст) / **Когда** (действие) / **Тогда** (проверяемый результат).
Хорошие критерии конкретны (с данными), покрывают ошибки и границы, а не только успешный путь.

</Brief>

## Когда применять

| Применять | Не нужно |
|---|---|
| Каждая история и каждое значимое ФТ | Писать Gherkin ради Gherkin для тривиального правила — хватит строчки в списке |
| Спорные правила: пример снимает неоднозначность лучше любых слов | Описывать UI пошагово («нажать кнопку, ввести…») — это тест-кейс, а не критерий |
| BDD и автотесты (Cucumber и аналоги) | — |
| Приёмка у заказчика: «что именно проверяем» | — |

## Как делать

<Steps>

1. **Начните с правил:** что должно быть верно, когда история готова.

2. **Для неочевидных правил — пример**: конкретные данные на входе и ожидаемый результат.

3. **Один сценарий — одно поведение.** Одно «Когда», результат в «Тогда».

4. **Пишите о поведении, а не об интерфейсе:** «руководитель отправляет заявку», а не «нажимает синюю кнопку».

5. **Покройте ошибки и границы:** пустые данные, дубликаты, лимиты, недоступность смежной системы.

6. **Однотипные проверки с разными данными** — через Scenario Outline и таблицу Examples.

7. **Обсудите с QA и разработкой** на рефайнменте — «Три амиго» (бизнес / аналитик, разработка, тестирование).

</Steps>

## Нотация: Gherkin

| Ключевое слово | Русский вариант | Назначение |
|---|---|---|
| `Feature` | Функция | Название функциональности и краткое описание |
| `Background` | Предыстория | Общие «Дано» для всех сценариев файла |
| `Scenario` | Сценарий | Один пример поведения |
| `Scenario Outline` | Структура сценария | Шаблон сценария с параметрами `<имя>` |
| `Examples` | Примеры | Таблица значений для Scenario Outline |
| `Given` | Дано | Исходное состояние |
| `When` | Когда | Действие или событие |
| `Then` | Тогда | Ожидаемый, проверяемый результат |
| `And`, `But` | И, Но | Продолжение предыдущего шага |

<Check id="req-02">
Русские ключевые слова Gherkin приведены по памяти; у каждого английского слова может быть несколько русских синонимов (например, для Given — «Допустим», «Пусть», «Дано»). Сверить с официальным списком языков Gherkin (cucumber/gherkin, файл gherkin-languages.json).
</Check>

## Пример из кейса IDM-JOINER

Сценарии на вкладках выше взяты из кейса:

- **Идемпотентность** — <CaseRef href="/case/02-requirements/backlog/#us-01" id="US-01">US-01</CaseRef>: второй сценарий проверяет повторную доставку того же события. Это прямое следствие at-least-once доставки (<CaseRef href="/case/02-requirements/non-functional-requirements/#nfr-05" id="NFR-05">NFR-05</CaseRef>) — без такого критерия идемпотентность легко «забыть».
- **Таблица примеров** — правило генерации логина и примеры из раздела 2.1 <CaseRef href="/case/02-requirements/functional-requirements/#fr-06" id="FR-06">функциональных требований</CaseRef>. В кейсе примеры даны таблицей — их удобно превратить в Scenario Outline один к одному.

Обратите внимание: сценарии пишут **о поведении системы** (событие, статус, запись в журнале), а не о кликах.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Описывать клики и экраны | Критерий ломается при любом изменении интерфейса | Поведение и результат |
| Несколько «Когда» в одном сценарии | Непонятно, что именно проверяем | Один сценарий — одно поведение |
| «Тогда система работает корректно» | Не проверить | Конкретный наблюдаемый результат |
| Только успешный путь | Ошибки не проверены | Сценарии на ошибки, дубли, границы |
| Абстрактные данные («какой-то сотрудник») | Неоднозначно, нельзя автоматизировать | Конкретные значения |
| Критерии пишутся после разработки | Превращаются в описание того, что сделали | До начала работы, на рефайнменте |
