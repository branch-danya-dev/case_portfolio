<Brief>

**Индекс** — отдельная структура (чаще всего **B-дерево**), которая позволяет найти строки по значению столбца без просмотра всей таблицы — как предметный указатель в книге.
Индекс ускоряет **поиск, соединения и сортировку**, но **замедляет запись** и занимает место. Поэтому индексы ставят под частые сценарии чтения.
Индексы проектирует разработка или DBA. Аналитик даёт вход: **какие поиски и отчёты частые, какие объёмы, какие поля уникальны**.

</Brief>

## Когда применять

| Аналитику важно | Не нужно |
|---|---|
| Описать сценарии поиска и фильтры (портал, API, отчёты) | Выбирать тип индекса и параметры хранения |
| Указать объёмы и рост данных, частоту запросов | Требовать «индекс на каждое поле» |
| Отметить бизнес-уникальность — из неё следуют уникальные индексы | — |
| Понимать, почему «медленно», при разборе НФТ и инцидентов | — |

## Как делать

<Steps>

1. **Выпишите сценарии чтения:** поиск сотрудника по табельному номеру, заявки руководителя, задачи на сегодня.

2. **Для каждого — поля фильтра и сортировки** и ожидаемая частота.

3. **Объёмы:** сколько строк сейчас и через год. Индекс на таблице из 300 строк почти ничего не даёт; на миллионах — критичен.

4. **Уникальность** из требований («`person_id` уникален») — уникальный индекс.

5. **Передайте разработке / DBA** вместе с НФТ по времени ответа. Проверка — план выполнения запроса (`EXPLAIN`) и нагрузочный тест.

</Steps>

## Нотация: виды индексов и правила

| Вид | Что это | Пример |
|---|---|---|
| B-дерево (B-tree) | Тип по умолчанию в большинстве реляционных СУБД; равенство, диапазоны, сортировка | `employment(hire_date)` |
| Уникальный | Индекс + запрет дублей | `identity(person_id)` |
| Составной | По нескольким столбцам; порядок важен | `account(identity_id, system_code)` |
| Покрывающий | Содержит все нужные запросу столбцы — таблицу можно не читать | Зависит от СУБД |
| Частичный / фильтрованный | Только строки по условию | Задачи в статусе `SCHEDULED` |
| Полнотекстовый | Поиск по словам в тексте | Поиск по описанию заявки |

**Правила, которые полезно знать:**

- **Составной индекс работает слева направо.** Индекс `(identity_id, system_code)` помогает поиску по `identity_id` и по паре, но обычно не помогает поиску только по `system_code`.
- **Функция над столбцом мешает индексу:** `WHERE lower(login) = 'ivanov.ap'` не использует обычный индекс по `login` — нужен индекс по выражению или нормализация данных при записи.
- **`LIKE '%текст'`** с ведущим `%` обычный индекс не использует.
- **Низкая избирательность** (столбец «статус» с тремя значениями) — индекс часто бесполезен сам по себе.
- **Внешние ключи** обычно индексируют — по ним постоянно соединяют таблицы.

```sql title="Индексы для сценариев (иллюстрация, синтаксис PostgreSQL / SQLite)"
-- Уникальность из требований
CREATE UNIQUE INDEX ux_identity_person ON identity (person_id);

-- Поиск задач, которые пора выполнить (планировщик)
CREATE INDEX ix_task_status_time ON provisioning_task (status, scheduled_at);

-- Учётные записи человека в системе
CREATE UNIQUE INDEX ux_account_identity_system ON account (identity_id, system_code);

-- Как СУБД собирается выполнять запрос
EXPLAIN SELECT * FROM provisioning_task
WHERE status = 'SCHEDULED' AND scheduled_at <= '2027-03-15 07:00';
```

## Пример из кейса IDM-JOINER

Что из требований кейса — вход для индексов:

- **Уникальность:** `person_id` уникален, `hr_employment_id` уникален, пара (`identity_id`, `system_code`) уникальна в волне 1 — см. <CaseRef href="/case/03-architecture/data-model/" id="Модель">модель данных</CaseRef>.
- **Идемпотентность:** проверка `event_id` в `hr_event_inbox` выполняется на **каждое** событие — поиск по первичному ключу.
- **Планировщик:** выбирает задачи по статусу и времени — отсюда составной индекс `(status, scheduled_at)`.
- **Объёмы** скромные: до 300 событий в день в пике, ~4 000 сотрудников (<CaseRef href="/case/02-requirements/non-functional-requirements/#nfr-03" id="NFR-03">NFR-03</CaseRef>). Для IdM индексы важны прежде всего для журнала аудита — он хранится 5 лет и растёт постоянно (NFR-06), а отчёты аудитора ищут по сотруднику и периоду.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| «Добавим индексы на всё» | Медленная запись, место, сложность сопровождения | Под сценарии чтения |
| Нет требований к поиску и объёмам | DBA гадает, проблемы всплывают на проде | Сценарии, частота, объёмы — в НФТ |
| Составной индекс «не в том порядке» | Запрос не использует индекс | Первым — самый частый фильтр |
| Функции и приведения типов в условиях | Индекс не используется | Нормализовать данные при записи |
| Уникальность только «в коде» | Дубли при гонках и загрузках | Уникальный индекс |
