<Brief>

Модель данных описывает, **что система хранит и как данные связаны**. Три уровня: **концептуальная** (сущности и связи бизнеса), **логическая** (атрибуты, ключи, кардинальности — зона СА), **физическая** (таблицы, типы, индексы — разработка и DBA).
От модели зависят API, маппинг, отчёты и то, выдержит ли система «неудобные» случаи: повторный приём, совместительство, историю.
ER-диаграмма — основной способ её нарисовать; самая распространённая нотация — «вороньи лапки» (Crow's Foot).

</Brief>

## Когда применять

| Применять | Не нужно |
|---|---|
| Почти любой проект с хранением данных — хотя бы концептуальная модель | Физическую модель — аналитику обычно не нужно (её делает DBA) |
| Проектирование интеграций и маппинга | Дублировать модель в трёх нотациях |
| Миграция: понять модель источника и приёмника | — |
| Требования к отчётности и аудиту | — |

## Как делать

<Steps>

1. **Концептуальная:** выпишите понятия из глоссария и требований, нарисуйте связи без атрибутов. Обсудите с бизнесом — правильно ли понятия разделены.

2. **Логическая:** добавьте атрибуты, ключи (PK, UK, FK), кардинальности, обязательность.

3. **M:N** — замените связующими сущностями.

4. **Проверьте на сценариях**, особенно неудобных: повторный приём, совместительство, отмена, история изменений, аудит.

5. **Опишите ключевые решения текстом** — почему сущности разделены так, а не иначе. Без этого через год модель «упростят».

6. **Согласуйте** с архитектором и командой, которая будет делать физическую модель.

</Steps>

## Нотация

| Уровень | Что показывает | Кто делает |
|---|---|---|
| Концептуальная | Сущности и связи бизнеса, без атрибутов | БА / СА |
| Логическая | Сущности, атрибуты, ключи, связи, кардинальности; без привязки к СУБД | СА |
| Физическая | Таблицы, типы СУБД, индексы, партиционирование | Разработка / DBA |

**Кардинальность в нотации «вороньи лапки»** (так же записывается в Mermaid и PlantUML):

| Символ | Значение |
|---|---|
| `\|\|` | Ровно один |
| `\|o` | Ноль или один |
| `}o` | Ноль или много |
| `}\|` | Один или много |

Пример: `identity ||--o{ employment` — у идентичности ноль или много трудоустройств, у трудоустройства ровно одна идентичность.

| Нотация | Особенности |
|---|---|
| Чена (Chen) | Сущности — прямоугольники, связи — ромбы, атрибуты — овалы. Наглядна для концептуальной модели, громоздка для больших |
| «Вороньи лапки» (Crow's Foot / IE) | Кардинальность значками на концах линий. Самая распространённая в инструментах |
| IDEF1X | Стандарт с различием зависимых и независимых сущностей; встречается в госпроектах и CASE-инструментах |
| UML class | Диаграмма классов с кратностями `1`, `0..*` — тоже применяется для логической модели |

## Пример из кейса IDM-JOINER

<PlantUmlDiagram file="03_architecture/diagrams/er-model.puml" title="Логическая модель данных IdM" />

Ключевые решения <CaseRef href="/case/03-architecture/data-model/" id="Модель">модели кейса</CaseRef>:

- **Идентичность ≠ трудоустройство ≠ учётная запись.** Человек может иметь несколько трудоустройств (совместительство, повторный приём) и много учётных записей (по одной на систему).
- **Роли назначаются на трудоустройство**, а не на человека — при совместительстве роли не смешиваются, при увольнении с одной должности понятно, что отзывать.
- **У каждого выданного полномочия есть основание** — `basis_type` + `basis_id` (роль, заявка, исключение SoD). Это реализация цели G-03.
- **Идемпотентность хранится в данных:** `hr_event_inbox.event_id` и `provisioning_task.task_id`.
- **Журнал аудита — отдельное хранилище** и поэтому не показан на ER.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Склеить разные понятия (сотрудник = учётная запись) | Повторный приём и совместительство ломают модель | Проверка на неудобных сценариях |
| M:N без связующей таблицы | Списки в полях, невозможно обновлять по одному | Связующая сущность |
| Нет бизнес-ключей | Дубли при повторной загрузке, нельзя сопоставить данные систем | UK на натуральный ключ |
| Нет полей основания и истории | Невозможен аудит «кто, когда, почему» | Основание, даты, автор изменений |
| Сразу физическая модель | Обсуждение типов вместо смысла | Сначала концептуальная и логическая |
| Решения не описаны | Модель «упрощают» и ломают | Раздел «ключевые решения» |
