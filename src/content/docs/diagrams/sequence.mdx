<Brief>

**Диаграмма последовательности** (sequence diagram) показывает **порядок сообщений между участниками во времени** в одном сценарии: кто кого вызывает, синхронно или асинхронно, что отвечает и что происходит при ошибке.
Это **главный инструмент проектирования интеграций**: из неё выводятся контракты, политика повторов, тайм-ауты и тест-кейсы.
Правило: **один сценарий — одна диаграмма**; ошибки — через `alt` или отдельной диаграммой.

</Brief>

## Когда применять

| Применять | Не нужно / лучше другое |
|---|---|
| Интеграция нескольких систем: порядок вызовов и ответов | Работа людей и передача между ролями → BPMN |
| Сценарии ошибок: тайм-ауты, повторы, компенсация | Точный формат сообщений → OpenAPI / AsyncAPI |
| Согласовать со смежной командой «кто что вызывает» | Логика внутри одного сервиса → activity |
| Источник для тест-кейсов интеграций | Жизненный цикл объекта → state |

## Как делать

<Steps>

1. **Участники** слева направо в порядке первого появления: инициатор → посредники → получатели. На одном уровне абстракции — сервисы, а не классы и не кнопки.

2. **Успешный путь:** сообщения сверху вниз. Подписывайте операцию и ключевые данные: `POST /users (Idempotency-Key)`.

3. **Ответы** — для синхронных вызовов, с кодом или результатом.

4. **Ветки ошибок** — `alt`: тайм-аут, 4xx, 5xx, недоступность. Что делает вызывающий в каждом случае?

5. **Повторы и циклы** — `loop` с условием выхода.

6. **Этапы во времени** — разделители (`== День D, 07:00 ==`), если сценарий растянут.

7. **Нумерация шагов** — чтобы ссылаться из требований.

8. **Проверка по чек-листу:** у каждого синхронного вызова есть ответ; для каждого вызова описана ошибка; участников не больше 6–8.

</Steps>

## Нотация

| Элемент | Mermaid | PlantUML | Значение |
|---|---|---|---|
| Синхронный вызов | `A->>B: msg` | `A -> B : msg` | Отправитель ждёт ответа |
| Ответ | `B-->>A: ok` | `B --> A : ok` | Возврат результата |
| Асинхронное сообщение | `A-)B: event` | `A ->> B : event` | Отправитель не ждёт |
| Активация | `activate B` / `+` | `activate B` | Участник занят обработкой |
| Ветвление | `alt … else … end` | `alt … else … end` | Взаимоисключающие варианты |
| Необязательный фрагмент | `opt … end` | `opt … end` | Выполняется при условии |
| Цикл | `loop … end` | `loop … end` | Повторение |
| Параллельно | `par … and … end` | `par … else … end` | Одновременно |
| Нумерация | `autonumber` | `autonumber` | Номера шагов |
| Заметка | `Note over A,B: …` | `note over A, B : …` | Пояснение |

Обратите внимание: в Mermaid `->>` — **синхронное** сообщение со сплошной стрелкой, а асинхронное — `-)`. В PlantUML наоборот: `->` — обычный вызов, `->>` — асинхронный. При переносе диаграмм между инструментами это частая ошибка.

```mermaid title="Создание пользователя в АБС с тайм-аутом и повтором (по мотивам SEQ-02)"
sequenceDiagram
    autonumber
    participant P as Сервис провижининга
    participant A as Адаптер АБС
    participant SD as ServiceDesk
    P->>A: POST /users (Idempotency-Key = taskId)
    alt ответ получен
        A-->>P: 201 Created
    else тайм-аут — неизвестно, создан ли пользователь
        loop до 3 попыток (1 мин, 5 мин)
            P->>A: повтор с тем же Idempotency-Key
            A-->>P: 200 OK — пользователь уже создан
        end
    else 4xx — бизнес-ошибка
        A-->>P: 409 / 422 (problem+json)
        P->>SD: создать задачу администратору
    end
```

## Пример из кейса IDM-JOINER

В кейсе 4 sequence-диаграммы — <CaseRef href="/case/04-integrations/scenarios/" id="SEQ">сценарии взаимодействия</CaseRef>. Главная учебная — SEQ-02:

Что разобрать на ней:

- **Тайм-аут — самый коварный случай:** неизвестно, создан ли пользователь. Повтор с тем же `Idempotency-Key` безопасен — адаптер вернёт ранее созданного пользователя, а не ошибку «логин занят».
- **Политика повторов** — из <CaseRef href="/case/02-requirements/functional-requirements/#fr-16" id="FR-16">FR-16</CaseRef>: технические ошибки повторяются, бизнес-ошибки (4xx, кроме 429) — нет.
- **После исчерпания повторов** — задача в ServiceDesk и закрытие через webhook (<CaseRef href="/case/02-requirements/functional-requirements/#fr-17" id="FR-17">FR-17</CaseRef>).
- **Та же логика в статусной модели** задачи провижининга: RETRY_WAIT → MANUAL → DONE.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Только успешный путь | Ошибки и тайм-ауты реализуются «как получится» | `alt` для каждого типа ошибки |
| 15–20 участников | Нечитаемо | Один сценарий; объединить второстепенных; `ref` на другие диаграммы |
| Нет ответов на синхронные вызовы | Непонятно, что получает вызывающий | Ответ с кодом / результатом |
| Смешаны уровни: клики, SQL, сервисы | Диаграмма ни для кого | Один уровень абстракции |
| Синхронное и асинхронное не различаются | Неверные ожидания по ожиданию и надёжности | Разные типы стрелок |
| Нет номеров шагов | Не сослаться из требований и тестов | `autonumber` |
