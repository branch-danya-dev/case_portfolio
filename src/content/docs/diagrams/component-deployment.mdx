<Brief>

**Диаграмма компонентов** (component diagram) — из каких модулей состоит система и **через какие интерфейсы** они связаны: предоставляемые («леденец») и требуемые («гнездо»).
**Диаграмма развёртывания** (deployment diagram) — **где и на чём** всё работает: узлы (серверы, кластеры, ВМ), артефакты, каналы связи, сетевые сегменты.
Обычно их рисуют архитектор и DevOps, а аналитик читает — чтобы понимать, где живёт требование, какие интеграции возможны и что значат НФТ на практике.

</Brief>

## Когда применять

| Применять | Не нужно / лучше другое |
|---|---|
| Важны интерфейсы между модулями и зависимости | Общий обзор архитектуры для широкой аудитории → C4 |
| НФТ: отказоустойчивость, зоны безопасности, сетевые ограничения | Логика поведения → activity, sequence |
| Интеграция между сетевыми сегментами (маршруты, mTLS, firewall) | Одна система, один сервер — диаграмма лишняя |
| Подготовка к внедрению: окружения, узлы | — |

## Как делать

<Steps>

1. **Компоненты:** перечислите модули с одной ответственностью; для каждого — что он предоставляет (интерфейсы) и что требует.

2. **Соедините** требуемые интерфейсы с предоставляемыми; подпишите зависимости.

3. **Развёртывание:** узлы (физические или виртуальные), среды выполнения, развёрнутые артефакты.

4. **Каналы связи** между узлами — с протоколом (HTTPS, mTLS, TLS).

5. **Сетевые зоны** — группы узлов (сегменты, контуры безопасности).

6. **Отметьте резервирование:** сколько экземпляров, где балансировщик, кластеры — это ответ на НФТ по доступности.

</Steps>

## Нотация

| Элемент | Вид | Значение |
|---|---|---|
| Компонент | Прямоугольник со значком компонента | Модуль с интерфейсами |
| Предоставляемый интерфейс | «Леденец» — кружок на линии | Что компонент предоставляет |
| Требуемый интерфейс | «Гнездо» — полукруг / пунктирная стрелка к интерфейсу | Что компоненту нужно |
| Порт | Квадратик на границе компонента | Точка взаимодействия |
| Узел (node) | Объёмный параллелепипед | Сервер, ВМ, устройство, кластер |
| Среда выполнения | Узел со стереотипом `<<executionEnvironment>>` | JVM, контейнерная платформа, СУБД |
| Артефакт | Прямоугольник со значком листа | Развёртываемый файл: jar, образ, скрипт |
| Канал связи | Линия между узлами | С протоколом |

## Пример из кейса IDM-JOINER

В кейсе нет UML component и deployment: архитектура показана в C4 — <CaseRef href="/case/03-architecture/containers/" id="C4 L2">контейнеры решения</CaseRef>. Диаграммы выше построены по ней в учебных целях; развёртывание — **условное**.

Что из НФТ и ИБ кейса потребовало бы deployment-диаграммы:

- <CaseRef href="/case/02-requirements/non-functional-requirements/#nfr-04" id="NFR-04">NFR-04</CaseRef>: доступность 99,5% круглосуточно, RTO 4 часа, RPO 15 минут — сколько экземпляров, где резерв, как реплицируется БД (в документе НФТ сказано, что это требование потребовало кластерного развёртывания IdM);
- <CaseRef href="/case/02-requirements/non-functional-requirements/#nfr-07" id="NFR-07">NFR-07</CaseRef>: интеграции по TLS 1.2+, API — mTLS — какие каналы и между какими зонами;
- ограничение устава: доступ к АБС только через API адаптера, прямой доступ к БД запрещён — адаптер в сегменте АБС.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Компоненты без интерфейсов | Не видно, как они взаимодействуют | Предоставляемые и требуемые интерфейсы |
| Смешать логические компоненты и физические узлы | Непонятно, о чём диаграмма | Component — логика, deployment — физика |
| Каналы без протоколов | ИБ и сеть не могут проверить | Протокол и порт, если важно |
| Нет сетевых зон | Не видны ограничения доступа | Сегменты и границы |
| Одна копия всего на схеме при НФТ «99,5%» | Противоречие с требованиями | Показать резервирование |
