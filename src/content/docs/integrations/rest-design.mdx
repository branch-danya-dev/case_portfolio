<Brief>

Хороший REST API отличают не пути, а **договорённости**: единый формат ошибок (**Problem Details**, RFC 9457, ранее RFC 7807), понятные правила **версионирования и обратной совместимости**, предсказуемая **пагинация** и фильтры, **идемпотентность** создания.
Эти правила лучше записать один раз в стандарт API команды или компании и проверять на ревью контрактов.

</Brief>

## Когда применять

| Применять | Не нужно |
|---|---|
| Любой API, у которого больше одного клиента | Внутренний вызов внутри одного сервиса |
| Списки, которые растут (заявки, журнал) — пагинация обязательна | Справочник из 5 значений — пагинация лишняя |
| Изменения API при живых клиентах | — |
| Создание ресурсов с повторами при сбоях | — |

## Как делать

<Steps>

1. **Ошибки:** все ответы 4xx и 5xx — в `application/problem+json`; у каждого вида ошибки — свой `type`; ошибки полей — расширением.

2. **Совместимость:** перечислите, какие изменения считаются совместимыми, а какие требуют новой версии.

3. **Версия** — в пути (`/api/v1`), обычно мажорная; минорные изменения совместимы и версию не меняют.

4. **Коллекции:** пагинация (курсор для больших и меняющихся данных), лимит по умолчанию и максимальный, фильтры и сортировка параметрами.

5. **Создание:** `Idempotency-Key` или PUT по клиентскому идентификатору.

6. **Долгие операции:** `202 Accepted` + ресурс операции, статус которого можно опрашивать (или webhook по завершении).

7. **Всё это — в OpenAPI** с примерами.

</Steps>

## Нотация

<Tabs>
<TabItem label="Ошибки (RFC 9457)">

```http title="Ответ с ошибкой в формате Problem Details"
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.bank.local/problems/unknown-branch",
  "title": "Неизвестный код филиала",
  "status": 422,
  "detail": "Филиал с кодом 999 не найден в справочнике АБС",
  "instance": "/users",
  "branchCode": "999"
}
```

| Поле | Назначение |
|---|---|
| `type` | URI типа ошибки — по нему клиент различает ошибки (не по тексту) |
| `title` | Краткое описание типа, одинаковое для всех случаев этого типа |
| `status` | HTTP-код (дублирует код ответа для удобства) |
| `detail` | Описание конкретного случая для человека |
| `instance` | URI конкретного случая или запроса |
| расширения | Свои поля: `errors` (ошибки полей), `traceId`, бизнес-коды |

RFC 9457 (2023) заменил RFC 7807 (2016); формат совместим.

</TabItem>
<TabItem label="Версионирование">

| Изменение | Совместимое? |
|---|---|
| Новый необязательный параметр или поле ответа | Да |
| Новый ресурс или метод | Да |
| Новое значение перечисления в ответе | Осторожно: клиент должен уметь обработать неизвестное значение |
| Удалить или переименовать поле | **Нет** |
| Изменить тип или формат поля | **Нет** |
| Сделать поле запроса обязательным | **Нет** |
| Изменить смысл кода ответа или поля | **Нет** |

| Способ | Пример | Комментарий |
|---|---|---|
| В пути | `/api/v1/users` | Самый наглядный и распространённый |
| В заголовке / типе содержимого | `Accept: application/vnd.bank.v2+json` | «Чище» для REST, сложнее для отладки |
| Параметром | `?version=2` | Встречается реже |

Правила жизни версий: старая версия поддерживается объявленный срок, клиенты получают дату отключения, клиенты **игнорируют неизвестные поля** (tolerant reader).

</TabItem>
<TabItem label="Пагинация и фильтры">

```http title="Курсорная пагинация"
GET /api/v1/access-requests?status=ON_APPROVAL&sort=-createdAt&limit=50&cursor=eyJpZCI6MzAyfQ

200 OK
{
  "items": [ … ],
  "nextCursor": "eyJpZCI6MzUyfQ"
}
```

| Способ | Плюсы | Минусы |
|---|---|---|
| `offset` + `limit` / номер страницы | Просто; переход на страницу N | Медленно на больших смещениях; записи «плывут» при изменениях |
| Курсор / keyset (`after`, `cursor`) | Стабильно и быстро на больших данных | Нельзя прыгнуть на страницу N |

Договорённости: лимит по умолчанию и максимальный, единый синтаксис фильтров и сортировки (`sort=-createdAt`), стабильная сортировка (с уникальным полем в конце). Ссылки на страницы можно передавать и заголовком `Link` (RFC 8288).

</TabItem>
<TabItem label="Идемпотентность и 202">

```http title="Создание с ключом идемпотентности"
POST /users
Idempotency-Key: 6f1c2e9a-5b7d-4c11-9e4b-2a8f0d3c7e55
Content-Type: application/json

{ "login": "IVANOV.AP", "branchCode": "066", … }

→ 201 Created            первый вызов
→ 200 OK (тот же user)   повтор с тем же ключом
→ 409 Conflict           тот же логин, но другой ключ
```

```http title="Длительная операция"
POST /exports
→ 202 Accepted
  Location: /exports/8812

GET /exports/8812
→ 200 OK  { "status": "IN_PROGRESS" }
→ 200 OK  { "status": "DONE", "resultUrl": "/exports/8812/file" }
```

<Check id="int-01">
Заголовок `Idempotency-Key` для HTTP описывается черновиком IETF (draft-ietf-httpapi-idempotency-key-header); на момент написания — не RFC. Проверить актуальный статус документа в IETF Datatracker.
</Check>

</TabItem>

## Пример из кейса IDM-JOINER

- **Ошибки** IdM API и адаптера АБС — в формате RFC 7807, схема `Problem` в обоих OpenAPI (<CaseRef href="/case/04-integrations/api-idm/" id="IdM API">IdM API</CaseRef>, <CaseRef href="/case/04-integrations/api-abs-adapter/" id="INT-05">адаптер АБС</CaseRef>). Кейс ссылается на RFC 7807; формат совпадает с RFC 9457, поэтому в новых документах можно указывать новый номер.
- **Версия в пути:** серверы IdM API — `https://idm.bank.local/api/v1`.
- **Версия в событиях:** топик `hr.employee.events.v1`, поле `schemaVersion`; несовместимые изменения — в новый топик `.v2`.
- **Пагинация** нужна выгрузке полного среза HRMS (<CaseRef href="/case/04-integrations/integration-map/#int-02" id="INT-02">INT-02</CaseRef>): около 4 000 записей, «постранично».
- **Идемпотентность создания** — `Idempotency-Key = taskId` для `POST /users`, с правилом: повтор с тем же ключом → 200 и ранее созданный пользователь.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Свой формат ошибки в каждом методе | Клиенты пишут разбор под каждый случай | Единый Problem Details |
| Клиент различает ошибки по тексту `detail` | Ломается при правке текста | `type` и коды |
| Удалили поле «потому что никто не использует» | Падение клиентов в проде | Новая версия или период устаревания |
| Коллекция без пагинации | Таймауты и память при росте данных | Лимиты и курсор |
| Offset на быстро меняющихся данных | Пропуски и дубли при чтении | Курсор / keyset |
| Долгая операция синхронно | Тайм-ауты, повторы, дубли | 202 + ресурс операции |
