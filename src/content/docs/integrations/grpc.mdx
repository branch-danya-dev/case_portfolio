<Brief>

**gRPC** — фреймворк удалённого вызова процедур: контракт описывается в файле `.proto` (**Protocol Buffers**), по нему генерируется код клиента и сервера; передача — по **HTTP/2** в компактном бинарном формате.
Четыре типа вызовов: **унарный**, **серверный поток**, **клиентский поток**, **двунаправленный поток**.
Выбирают для **внутренних** вызовов между сервисами, где важны скорость, строгий контракт и потоки. Для внешних партнёров и браузеров чаще остаётся REST.

</Brief>

## Когда применять

| Применять | Не нужно / лучше другое |
|---|---|
| Высоконагруженные вызовы между внутренними сервисами | Публичный API для партнёров с разным стеком → REST |
| Потоковая передача (подписка на изменения, большие выгрузки частями) | Вызов из браузера без дополнительной инфраструктуры → REST (или gRPC-Web через прокси) |
| Строгий контракт и генерация клиентов на разных языках | Команда и эксплуатация не готовы к бинарному протоколу и HTTP/2 |
| Мобильные клиенты, где важен размер трафика | Асинхронные события с несколькими получателями → брокер |

## Как делать

<Steps>

1. **Опишите сервис в `.proto`:** методы (`rpc`), сообщения запросов и ответов, их поля с номерами.

2. **Выберите тип вызова** для каждого метода: унарный — как обычный запрос; поток — для подписок и больших объёмов.

3. **Ошибки — статусами gRPC** (`INVALID_ARGUMENT`, `NOT_FOUND`, `ALREADY_EXISTS`…) с деталями.

4. **Дедлайны:** у каждого вызова — максимальное время; клиент задаёт, сервер учитывает.

5. **Правила эволюции схемы:** номера полей не переиспользовать, новые поля — необязательные, удалённые номера резервировать (`reserved`).

6. **Наблюдаемость и отладка:** бинарный формат не прочитать «глазами» — нужны инструменты (grpcurl, Postman, Kreya и аналоги) и логирование.

</Steps>

## Нотация

```protobuf title="idm_users.proto — иллюстрация по мотивам API адаптера АБС"
syntax = "proto3";

package bank.abs.users.v1;

service UserAdmin {
  rpc CreateUser (CreateUserRequest) returns (User);               // унарный
  rpc WatchUserChanges (WatchRequest) returns (stream UserEvent);  // серверный поток
}

message CreateUserRequest {
  string idempotency_key = 1;
  string login = 2;
  string branch_code = 3;
  repeated string roles = 4;   // список
  optional string middle_name = 5;
}

message User {
  string login = 1;
  Status status = 2;
}

enum Status {
  STATUS_UNSPECIFIED = 0;     // нулевое значение — «не задано»
  STATUS_ACTIVE = 1;
  STATUS_BLOCKED = 2;
}

message WatchRequest { string branch_code = 1; }
message UserEvent { User user = 1; string change = 2; }
```

| Тип вызова | Описание | Пример |
|---|---|---|
| Унарный | Один запрос — один ответ | Создать пользователя |
| Серверный поток | Один запрос — поток ответов | Подписка на изменения пользователей |
| Клиентский поток | Поток запросов — один ответ | Загрузка большого пакета записей |
| Двунаправленный поток | Потоки в обе стороны | Чат, синхронизация в реальном времени |

| Статус gRPC | Аналог в HTTP (примерно) | Когда |
|---|---|---|
| `OK` | 200 | Успех |
| `INVALID_ARGUMENT` | 400 | Некорректные данные |
| `NOT_FOUND` | 404 | Нет объекта |
| `ALREADY_EXISTS` | 409 | Объект уже есть |
| `FAILED_PRECONDITION` | 409 / 422 | Неподходящее состояние для операции |
| `PERMISSION_DENIED` | 403 | Нет прав |
| `UNAUTHENTICATED` | 401 | Не аутентифицирован |
| `RESOURCE_EXHAUSTED` | 429 | Лимиты, квоты |
| `UNAVAILABLE` | 503 | Сервис временно недоступен — можно повторить |
| `DEADLINE_EXCEEDED` | 504 | Истёк дедлайн |
| `INTERNAL` | 500 | Внутренняя ошибка |

**Совместимость схем protobuf:** поля идентифицируются **номерами**, а не именами. Переименовать поле можно; поменять номер или тип, переиспользовать номер удалённого поля — нельзя.

## Пример из кейса IDM-JOINER

В кейсе gRPC нет: все синхронные интеграции — REST, потому что взаимодействуют системы разных команд (АБС, ServiceDesk, SMS-шлюз), а REST понятен всем и проще в сопровождении.

Где gRPC мог бы появиться: внутри самого IdM — между ядром и сервисом провижининга (<CaseRef href="/case/03-architecture/containers/" id="C4 L2">контейнеры решения</CaseRef>), если бы нагрузка выросла на порядки. При текущих объёмах — до 300 событий в день (<CaseRef href="/case/02-requirements/non-functional-requirements/#nfr-03" id="NFR-03">NFR-03</CaseRef>) — выигрыш в скорости не оправдывает усложнения.

Так выглядит правильная аргументация выбора технологии: **от требований и объёмов, а не от моды**.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Переиспользовать номер удалённого поля | Старые клиенты прочитают данные как другое поле | `reserved` для удалённых номеров |
| Нет дедлайнов | Зависшие вызовы, каскадные отказы | Дедлайн на каждом вызове |
| gRPC для внешних партнёров «потому что быстрее» | Партнёры не могут интегрироваться | REST наружу, gRPC внутри |
| Ошибки как `INTERNAL` на всё | Клиент не знает, повторять ли | Точные статусы |
| Не продумана отладка | Инциденты разбираются вслепую | Инструменты, логирование, трассировка |
