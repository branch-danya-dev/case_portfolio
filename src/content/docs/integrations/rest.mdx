<Brief>

**REST** — архитектурный стиль поверх HTTP: **ресурсы** с адресами (`/users/{login}`), **стандартные методы** (GET, POST, PUT, PATCH, DELETE) и **коды ответов**, сервер не хранит состояние клиента между запросами.
Ключевое для аналитика — **семантика методов**: какие безопасные, какие идемпотентные. От этого зависит, можно ли повторять запрос при тайм-ауте.
Хороший REST API читается без документации: существительные в путях, методы — действия, коды — результат.

</Brief>

## Когда применять

| Применять | Не нужно / лучше другое |
|---|---|
| Синхронная интеграция, нужен ответ сразу | Источник не должен ждать получателя → брокер сообщений |
| Публичный или межкомандный API — понятен всем, богатые инструменты | Высоконагруженные внутренние вызовы со строгим контрактом → gRPC |
| CRUD над ресурсами предметной области | Клиенту нужны гибкие выборки полей из многих сущностей → GraphQL |
| Webhook-уведомления | Партнёр требует SOAP и WS-Security → SOAP |

## Как делать

<Steps>

1. **Выделите ресурсы** — существительные предметной области: пользователи, роли, заявки. Коллекция — `/users`, элемент — `/users/{login}`, вложенный — `/users/{login}/roles/{roleCode}`.

2. **Сопоставьте операции методам:** чтение — GET, создание в коллекции — POST, установка по известному адресу — PUT, частичное изменение — PATCH, удаление — DELETE.

3. **Для каждой операции — успешный код и все ошибочные:** что вернётся при неверных данных, отсутствии ресурса, конфликте, недоступности.

4. **Идемпотентность:** где повтор безопасен по семантике (PUT, DELETE), а где нужен ключ идемпотентности (POST).

5. **Формат ошибок** — единый (RFC 9457), см. [Проектирование REST API](/integrations/rest-design/).

6. **Опишите контракт в OpenAPI** с примерами запросов и ответов.

</Steps>

## Нотация: методы, коды, заголовки

| Метод | Назначение | Тело запроса | Безопасный | Идемпотентный | Типичный успех |
|---|---|---|---|---|---|
| GET | Получить ресурс или коллекцию | нет | да | да | 200 |
| HEAD | Как GET, только заголовки | нет | да | да | 200 |
| POST | Создать в коллекции / выполнить действие | да | нет | **нет** | 201 + `Location`, 200, 202 |
| PUT | Заменить или создать по известному адресу | да | нет | да | 200, 204, 201 |
| PATCH | Изменить часть | да | нет | не гарантируется | 200, 204 |
| DELETE | Удалить | обычно нет | нет | да | 204, 200 |
| OPTIONS | Узнать возможности (используется в CORS) | нет | да | да | 204, 200 |

**Безопасный** — не меняет состояние на сервере. **Идемпотентный** — несколько одинаковых запросов дают тот же эффект на сервере, что и один (ответы при этом могут различаться: повторный DELETE может вернуть 404).

| Код | Когда возвращать |
|---|---|
| 200 OK | Успех с телом ответа |
| 201 Created | Ресурс создан; в `Location` — его адрес |
| 202 Accepted | Запрос принят, обработка асинхронная — дать способ узнать результат |
| 204 No Content | Успех без тела (PUT, DELETE) |
| 304 Not Modified | Ресурс не изменился с версии клиента (условный GET) |
| 400 Bad Request | Некорректный синтаксис или формат запроса |
| 401 Unauthorized | Нет или неверные учётные данные — «кто ты?» |
| 403 Forbidden | Аутентифицирован, но нет прав |
| 404 Not Found | Ресурса нет (или его существование скрывают) |
| 405 Method Not Allowed | Метод не поддерживается этим ресурсом |
| 409 Conflict | Конфликт с текущим состоянием: логин занят, объект в неподходящем статусе |
| 412 Precondition Failed | Не выполнено условие (`If-Match`) — ресурс изменился |
| 415 Unsupported Media Type | Не тот формат тела |
| 422 Unprocessable Content | Формат верный, но не проходит бизнес-проверку |
| 429 Too Many Requests | Превышен лимит; `Retry-After` |
| 500 Internal Server Error | Непредвиденная ошибка сервера |
| 502 / 504 | Ошибка / тайм-аут шлюза или прокси |
| 503 Service Unavailable | Временно недоступен; `Retry-After` |

Методы и коды определены в RFC 9110 (HTTP Semantics), PATCH — в RFC 5789, 429 — в RFC 6585.

| Заголовок | Назначение |
|---|---|
| `Content-Type` / `Accept` | Формат тела запроса / ожидаемый формат ответа |
| `Authorization` | Учётные данные (например, `Bearer <токен>`) |
| `Location` | Адрес созданного ресурса (201) |
| `ETag` / `If-Match` / `If-None-Match` | Версия ресурса; условные запросы и защита от потерянного обновления |
| `Retry-After` | Когда повторить (429, 503) |
| `Idempotency-Key` | Ключ идемпотентности для POST (распространённая практика) |
| `X-Request-Id` / `traceparent` | Сквозная трассировка запроса между сервисами |

## Пример из кейса IDM-JOINER

<CaseRef href="/case/04-integrations/api-abs-adapter/" id="INT-05">API адаптера АБС</CaseRef> — компактный образец правильного REST:

| Операция | Метод и путь | Коды | Почему так |
|---|---|---|---|
| Создать пользователя | `POST /users` + `Idempotency-Key` | 201 создан · **200 повтор с тем же ключом** · 409 логин занят другим ключом · 422 неизвестный `branchCode` · 503 АБС недоступна | POST не идемпотентен — ключ делает повтор безопасным |
| Изменить статус | `PATCH /users/{login}` | 200 изменён (или уже был таким) · 404 | Установка значения — повтор безопасен |
| Удалить неактивированного | `DELETE /users/{login}` | 204 удалён или уже отсутствовал · 409 есть операции | DELETE идемпотентен: «уже отсутствовал» — тоже успех |
| Назначить роль | `PUT /users/{login}/roles/{roleCode}` | 204 назначена (или уже была) · 404 | PUT по известному адресу — идемпотентен |
| Отозвать роль | `DELETE /users/{login}/roles/{roleCode}` | 204 отозвана (или не была назначена) | Повтор безопасен |

Обратите внимание: «уже было так» — это **успех**, а не ошибка. Именно это делает повторы безопасными в политике <CaseRef href="/case/02-requirements/functional-requirements/#fr-16" id="FR-16">FR-16</CaseRef>.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Глаголы в путях: `/createUser`, `/getUsers` | Это RPC поверх HTTP, методы теряют смысл | Существительные + методы: `POST /users` |
| Всё через POST | Нельзя кэшировать, неясно, что безопасно повторять | Методы по семантике |
| 200 с `{"error": …}` в теле | Клиенты и мониторинг не видят ошибку | Коды 4xx / 5xx + тело ошибки |
| 500 на ошибку клиента | Клиент будет повторять бессмысленный запрос | 400 / 409 / 422 |
| POST без ключа идемпотентности при повторах | Дубли при тайм-ауте | `Idempotency-Key` или PUT по клиентскому идентификатору |
| «Уже существует» как ошибка для PUT / DELETE | Повторы падают | Идемпотентный успех |
