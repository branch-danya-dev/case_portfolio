<Brief>

Системы обмениваются данными четырьмя основными способами: **файлы**, **общая база данных**, **удалённый вызов** (REST, SOAP, gRPC) и **обмен сообщениями** через брокер (Kafka, RabbitMQ).
Главные вопросы выбора: **нужен ли ответ сразу** (синхронно или асинхронно), **кто инициирует** (push или pull), **сколько получателей**, **кто должен пережить недоступность другого**.
Для каждого потока в карте интеграций фиксируют: кто, что, как, как часто, где контракт, **что при ошибке** и кто владелец на другой стороне.

</Brief>

## Когда применять

| Стиль | Подходит | Не подходит |
|---|---|---|
| Обмен файлами | Большие пакеты раз в сутки, отчётность, системы без API | Нужна реакция за секунды; сложная обработка ошибок построчно |
| Общая БД | Почти никогда для интеграции разных систем | Системы разных команд; требования ИБ |
| Удалённый вызов (API) | Нужен ответ сразу; команды, запросы данных | Источник не должен зависеть от доступности получателя |
| Сообщения (брокер) | События, несколько получателей, пики нагрузки, слабая связность | Нужен немедленный ответ пользователю |

## Как делать

<Steps>

1. **Нарисуйте контекст** — все системы, с которыми обмениваемся.

2. **Для каждого потока определите:** что передаётся, кто источник правды, как часто и сколько.

3. **Синхронно или асинхронно:** нужен ли результат сразу? Может ли источник ждать? Что, если получатель недоступен час?

4. **Push или pull:** кто знает о событии первым и кто должен инициировать обмен?

5. **Выберите стиль и протокол**, обоснуйте; спорный выбор — в ADR.

6. **Заполните карту интеграций**, особенно колонку «что при ошибке».

7. **Согласуйте с владельцами** смежных систем: у них свои сроки и ограничения.

</Steps>

## Нотация: сравнение и шаблон

| | Синхронно | Асинхронно |
|---|---|---|
| Вызывающий | Ждёт ответа | Не ждёт |
| Связность | Сильная: недоступность получателя ломает вызывающего | Слабая: брокер буферизует |
| Сложность | Проще отладка и обработка ошибок | Идемпотентность, порядок, дубли, мониторинг очередей |
| Примеры | REST, SOAP, gRPC | Kafka, RabbitMQ, webhook (условно) |

| Топология | Суть | Риски |
|---|---|---|
| Точка-точка | Каждая пара систем интегрирована напрямую | Число связей растёт быстро, «спагетти» |
| Интеграционная шина (ESB) | Централизованная маршрутизация и трансформация | Шина — узкое место и «монолит интеграций» |
| Событийная архитектура | Системы публикуют события, заинтересованные подписываются | Сложнее отследить сквозной процесс; нужны контракты событий |
| API-шлюз | Единая точка входа для внешних клиентов: аутентификация, лимиты, маршрутизация | Ещё один компонент на пути запроса |

```markdown title="Шаблон строки карты интеграций"
| ID | Источник → Приёмник | Что передаётся | Протокол / формат | Режим | Частота / объём | Контракт | Ошибки | Владелец на другой стороне |
|----|---------------------|----------------|-------------------|-------|-----------------|----------|--------|----------------------------|
| INT-NN | A → B | <данные> | REST, JSON | Синхронно, идемпотентно | <N в день, пики> | <ссылка> | <повторы, DLQ, алерт> | <команда> |
```

## Пример из кейса IDM-JOINER

<CaseRef href="/case/04-integrations/integration-map/" id="Карта">Карта интеграций кейса</CaseRef> показывает все стили сразу:

| Поток | Стиль | Почему |
|---|---|---|
| INT-01 HRMS → Kafka → IdM | Сообщения, push, асинхронно | HRMS не должна зависеть от доступности IdM; события могут читать другие системы |
| INT-02 IdM → HRMS | API, pull, раз в сутки | Страховка от потерянных событий — полная сверка |
| INT-03 IdM → AD | Удалённый вызов (LDAPS) | Нужен результат создания учётной записи |
| INT-05 IdM → Адаптер АБС | REST, синхронно, идемпотентно | Прямой доступ к БД АБС запрещён (ADR-003) |
| INT-06 ServiceDesk → IdM | Webhook | ServiceDesk сам сообщает о закрытии задачи |
| INT-09 IdM → Kafka → SIEM | Сообщения | Журнал аудита для ИБ, слабая связность |

Выбор способа получения кадровых событий оформлен как <CaseRef href="/case/03-architecture/adr/#adr-001" id="ADR-001">ADR-001</CaseRef>: рассмотрены REST-вызов от HRMS, опрос HRMS и публикация в Kafka. Выбрана Kafka плюс ежедневная сверка — асинхронная доставка и страховка pull-ом.

Запрет на общую БД записан в уставе и <CaseRef href="/case/03-architecture/adr/#adr-003" id="ADR-003">ADR-003</CaseRef>: прямой доступ к БД АБС запрещён политикой ИБ.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Синхронный вызов там, где источник не должен ждать | Недоступность получателя останавливает бизнес-процесс источника | Асинхронно через брокер |
| Интеграция через общую БД | Связность схем, нарушение ИБ, невозможно менять системы независимо | API или сообщения |
| Нет колонки «что при ошибке» | Сбои обнаруживаются в проде, никто не отвечает | Повторы, DLQ, алерт, ответственный |
| Нет объёмов и частоты | Неверный выбор технологии, сюрпризы на нагрузке | Объём, пики, рост |
| Не указан владелец на другой стороне | Некому согласовать контракт и разбирать инциденты | Владелец в карте интеграций |
| Только события без сверки | Потерянное событие = навсегда потерянные данные | Периодическая сверка как страховка |
