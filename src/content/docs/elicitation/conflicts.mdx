<Brief>

Конфликт требований — нормальная часть проекта: у стейкхолдеров разные цели. Опасен не конфликт, а **скрытый** конфликт, который всплывает на приёмке.
Алгоритм: **найти интересы за позициями → проверить факты и термины → предложить варианты → если не договорились, эскалировать владельцу требований → записать решение**.
Аналитик **готовит** решение и делает конфликт видимым, но **не принимает** решение за того, кто за него отвечает.

</Brief>

## Когда применять

| Применять | Не нужно |
|---|---|
| Два требования нельзя выполнить одновременно | Расхождение — следствие опечатки или устаревшей информации: просто уточнить |
| Стейкхолдеры настаивают на взаимоисключающих решениях | Спор о реализации внутри команды → архитектор и ADR |
| Требование противоречит ограничению (ИБ, регулятор, бюджет) | — |
| Новое требование ломает ранее согласованное | → анализ влияния и запрос на изменение |

## Как делать

<Steps>

1. **Зафиксируйте конфликт явно:** какие требования, чьи, в чём именно противоречие.

2. **Проверьте, не мнимый ли он.** Одинаково ли стороны понимают термины (глоссарий)? Актуальны ли данные? Половина «конфликтов» — разное понимание слова.

3. **Перейдите от позиций к интересам.** Позиция — «руководитель сам выбирает права». Интерес — «сотрудник работает с первого дня, без долгих согласований». За противоположными позициями часто стоят совместимые интересы.

4. **Соберите факты:** цифры, нормативные требования, стоимость вариантов.

5. **Предложите варианты** с плюсами, минусами, стоимостью и рисками. Хотя бы один — удовлетворяющий интересам обеих сторон.

6. **Если не договорились — эскалируйте** владельцу требований (A в RACI): заказчику, спонсору, управляющему комитету. С готовыми вариантами, а не с вопросом «что делать?».

7. **Запишите решение:** что решили, кто, почему, какие требования изменились. Сообщите всем участникам.

</Steps>

## Нотация: виды конфликтов и способы разрешения

| Вид конфликта | Пример | Обычный способ разрешения |
|---|---|---|
| Интересы стейкхолдеров | Удобство пользователя против контроля ИБ | Вариант, учитывающий оба интереса; эскалация владельцу |
| Ресурсы | Обе функции — Must, а времени на одну | Приоритизация (MoSCoW, WSJF), решение PO / заказчика |
| Терминология | «Роль» у HR и у ИБ — разные вещи | Глоссарий, согласованное определение |
| Данные и факты | «Это бывает редко» против «каждый день» | Выгрузка, статистика |
| Требование против ограничения | Хочется прямой записи в БД, ИБ запрещает | Ограничение побеждает; ищем решение внутри него |
| Новое против согласованного | Изменение ломает принятое ранее | Анализ влияния, запрос на изменение |

**Стратегии** (по модели Томаса — Килманна): соперничество, приспособление, избегание, компромисс, сотрудничество. Для требований лучший результат обычно даёт **сотрудничество** — поиск решения, которое удовлетворяет интересы обеих сторон, а не «пополам».

```markdown title="Шаблон записи в журнале решений"
## D-012. <Краткое название решения>

Дата: ДД.ММ.ГГГГ · Статус: принято
Конфликт: <требование A (источник)> против <требование B (источник)>
Интересы: <сторона A> — <что важно>; <сторона B> — <что важно>
Варианты:
1. <вариант> — плюсы / минусы / стоимость
2. <вариант> — плюсы / минусы / стоимость
Решение: <что выбрали>
Кто принял: <роль, ФИО>
Обоснование: <почему>
Изменения: <какие требования созданы / изменены / отложены>
```

## Пример из кейса IDM-JOINER

Классический конфликт из <CaseRef href="/case/cheatsheet/#ситуации-в-которых-аналитик-не-решает-сам" id="Шпаргалка">шпаргалки кейса</CaseRef>:

| | HRD (бизнес-заказчик) | CISO (ИБ) |
|---|---|---|
| **Позиция** | Пусть руководитель сам выбирает права новому сотруднику | Права — только по ролям |
| **Интерес** | Сотрудник работает с первого дня, без бюрократии | Минимальные привилегии, контроль, нет «копирования как у коллеги» |

**Решение** — не компромисс «пополам», а сочетание, которое закрывает оба интереса:

- роли по умолчанию: <CaseRef href="/case/01-business/business-requirements/#br-03" id="BR-03">доступы по должности и подразделению без ручного перечисления</CaseRef> — сотрудник получает нужное к первому дню, ИБ контролирует состав ролей;
- заявки сверх ролей: <CaseRef href="/case/01-business/business-requirements/#br-05" id="BR-05">руководитель запрашивает дополнительные доступы с согласованием владельца ресурса</CaseRef> — гибкость для исключений, но с согласованием.

Ещё два приёма из кейса:

- **Ограничение побеждает желание:** прямой доступ к БД АБС запрещён политикой ИБ, поэтому интеграция — только через API адаптера (<CaseRef href="/case/03-architecture/adr/#adr-003" id="ADR-003">ADR-003</CaseRef>).
- **Отложить явно, а не потерять:** требование про перевод и увольнение записано со статусом W — «не в этой волне» (<CaseRef href="/case/01-business/business-requirements/#br-12" id="BR-12">BR-12</CaseRef>), а риск принят CISO (<CaseRef href="/case/00-project/project-charter/#r-04" id="R-04">R-04</CaseRef>).

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Аналитик решает конфликт сам | Решение без полномочий оспорят; ответственность размыта | Подготовить варианты, решает A |
| «Пополам» вместо поиска интересов | Обе стороны недовольны, требования размыты | Интересы → вариант, закрывающий оба |
| Замолчать конфликт, надеясь «само рассосётся» | Всплывёт на приёмке, когда менять дорого | Сделать видимым сразу |
| Эскалировать без вариантов | Руководитель возвращает задачу аналитику | Варианты с последствиями и рекомендацией |
| Не записать решение | Через месяц спор начинается заново | Журнал решений, ссылка в требованиях |
| Удалить отклонённое требование | «А почему вы забыли про…?» | Статус W / «отклонено» с причиной |
