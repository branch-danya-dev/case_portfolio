<Brief>

**Анализ документов** (document analysis) даёт формальные правила, термины и ограничения; **анализ систем** (system / interface analysis) — то, что реально автоматизировано: функции, данные, интеграции, ошибки.
Оба делаются **до интервью**: так вы приходите с конкретными вопросами, а не тратите время людей на пересказ регламента.
Самые ценные находки — **расхождения**: регламент говорит одно, система делает другое, люди — третье.

</Brief>

## Когда применять

| Применять | Не нужно |
|---|---|
| Есть регламенты, нормативные требования, договоры, старые ТЗ | Документов нет и система новая — начинать с людей |
| Заменяем или дорабатываем существующую систему | Анализ ради анализа: изучать всё подряд без цели |
| Интегрируемся со смежной системой — нужны форматы и справочники | — |
| Миграция данных: что и в каком качестве лежит в источнике | — |

## Как делать

<Steps>

1. **Составьте перечень источников:** документы (с датой и версией), системы, доступы, кто может помочь.

2. **Документы — читайте с вопросами:** какие роли, шаги, правила, сроки, данные, исключения. Выписывайте термины в глоссарий, правила — с ссылкой на пункт документа.

3. **Система: интерфейс.** Пройдите основные сценарии под тестовой учётной записью, соберите поля, проверки, статусы, сообщения об ошибках.

4. **Система: данные.** Схема таблиц, ключи, справочники. Профилирование: объёмы, заполненность полей, уникальность, распределения, «странные» значения.

5. **Система: интеграции и логи.** Кто вызывает систему и кого вызывает она, форматы, частота, ошибки.

6. **Сверьте с практикой:** покажите находки пользователям — «тут написано так, а вы делаете иначе?».

7. **Оформите результат:** список функций и правил, которые нельзя потерять, модель данных, открытые вопросы.

</Steps>

## Нотация: что извлекать и шаблоны

| Источник | Что искать | Куда записать |
|---|---|---|
| Регламент, инструкция | Роли, шаги, сроки, правила, документы на входе и выходе | AS-IS, бизнес-правила, глоссарий |
| Нормативный акт, стандарт | Обязательные требования, сроки хранения, запреты | Требования ИБ / НФТ с ссылкой на пункт |
| Договор, SLA | Сроки, уровни сервиса, ответственность | НФТ, требования к интеграции |
| Интерфейс системы | Поля, обязательность, проверки, статусы, сообщения | ФТ, статусная модель, макеты |
| База данных | Сущности, связи, ключи, справочники, качество данных | Модель данных, маппинг, стратегия миграции |
| Логи и журналы | Частота операций, ошибки, пиковые нагрузки | НФТ, сценарии ошибок |
| API, файлы обмена | Форматы, обязательные поля, коды ошибок | Контракты, маппинг |
| Обращения в поддержку | Что ломается, что просят | Проблемы AS-IS, бэклог |

<TabItem label="SQL: профилирование данных">

```sql title="Профилирование таблицы перед миграцией или интеграцией"
-- 1. Объём
SELECT COUNT(*) AS total FROM employees;

-- 2. Заполненность ключевых полей
SELECT
  COUNT(*)                                  AS total,
  COUNT(employee_number)                    AS with_number,
  COUNT(*) - COUNT(employee_number)         AS without_number,
  COUNT(DISTINCT employee_number)           AS distinct_numbers
FROM employees;

-- 3. Дубликаты «уникального» поля
SELECT employee_number, COUNT(*) AS cnt
FROM employees
GROUP BY employee_number
HAVING COUNT(*) > 1;

-- 4. Распределение значений справочного поля
SELECT org_unit_code, COUNT(*) AS cnt
FROM employees
GROUP BY org_unit_code
ORDER BY cnt DESC;

-- 5. Записи без пары в другой системе («сироты»)
SELECT a.login
FROM ad_accounts a
LEFT JOIN employees e ON e.employee_number = a.employee_id
WHERE e.employee_number IS NULL;
```

## Пример из кейса IDM-JOINER

**Документы.** В AS-IS регламент «Предоставление логического доступа» (ред. 2021) использован как источник формального порядка — и прямо сказано, что AS-IS описывает процесс **как он работает на самом деле**, а расхождения с регламентом — отдельная находка. См. <CaseRef href="/case/01-business/as-is/" id="AS-IS">AS-IS</CaseRef>.

**Системы и данные.** Анализ существующих систем дал цифры, которые не получить из интервью:

- статистика ServiceDesk за 6 месяцев — средняя длительность 6,2 рабочих дня, 23% возвратов;
- выгрузка групп AD по 50 сотрудникам — у 31 есть права, не нужные по должности.

**Миграция.** Сопоставление существующих данных AD, АБС и HRMS — тот же анализ систем, только в масштабе всех записей. Он находит «сирот» — учётные записи без сотрудника — и даёт эффект для ИБ ещё до запуска. Критерий успеха — сопоставлено ≥ 98% учётных записей AD. См. <CaseRef href="/case/06-rollout/migration-strategy/" id="Миграция">стратегию миграции</CaseRef>.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Доверять регламенту как описанию реальности | Не видно реальных шагов и потерь | Сверять с интервью, наблюдением и данными |
| Не фиксировать версию и дату документа | Через месяц непонятно, на что опирались | Ссылка на документ, редакцию и пункт |
| Смотреть только интерфейс | Пропущены фоновые задания, интеграции, проверки в БД | Данные, логи, интеграции |
| Не профилировать данные перед миграцией | «Сюрпризы» на загрузке: дубликаты, пустые ключи | Запросы на заполненность и уникальность заранее |
| Потерять «тихие» функции старой системы | После замены пропадают уведомления, расчёты, проверки | Чек-лист и вопрос пользователям «что система делает сама» |
| Работать с продуктивными данными без согласования | Нарушение требований ИБ и ПДн | Тестовый стенд, обезличенные выгрузки, согласование с ИБ |
