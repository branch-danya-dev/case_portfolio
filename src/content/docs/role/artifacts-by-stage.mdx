<Brief>

Артефакты проекта складываются в **слои**: зачем (устав) → что меняется для бизнеса (AS-IS, TO-BE, БТ) → что делает система (ФТ, НФТ, use cases) → как устроено (данные, статусы, архитектура) → с кем обменивается (интеграции, контракты) → как защищено, внедрено и проверено.
**Требования идут вниз** (цель → БТ → ФТ → контракт → тест), **вопросы и противоречия — вверх**.
Набор артефактов зависит от проекта: на малом хватает семи, но цель с метрикой и границы нужны всегда.

</Brief>

## Когда применять

| Применять | Не нужно |
|---|---|
| Старт проекта: спланировать, какие документы нужны и к какой вехе | Писать все документы «по шаблону», даже если они никому не нужны |
| Аудит существующей документации: чего не хватает | Дублировать один и тот же смысл в трёх документах |
| Малый проект: решить, без чего можно обойтись | — |
| Собеседование: «какие документы вы писали и зачем» | — |

## Как делать

<Steps>

1. **Начните с вопроса, а не с шаблона.** Для каждого артефакта: на какой вопрос он отвечает и кто без него не сможет работать.

2. **Определите автора и утверждающего** (RACI). Артефакт без утверждающего — черновик навсегда.

3. **Привяжите к этапу и вехе.** Когда артефакт должен быть готов, чтобы следующий этап не простаивал.

4. **Свяжите артефакты трассировкой.** ID в каждом документе (BR-, FR-, UC-, TC-) и ссылки между ними.

5. **Проверьте полноту обратной трассировкой:** нет ли БТ без ФТ, ФТ без теста, интеграции без контракта.

</Steps>

## Нотация: слои и карточки артефактов

```text title="Слои проекта"
ЗАЧЕМ     Устав, стейкхолдеры, глоссарий          → цели, границы, участники
ЧТО       AS-IS, TO-BE, gap, БТ                   → что меняется для бизнеса
          Use case, ФТ, НФТ, справочники, бэклог  → что должна делать система
КАК       C4, данные, статусы, ADR                → из чего состоит, что хранит
          Карта интеграций, sequence, маппинг, API → с кем и как обменивается
ЗАЩИТА    Требования ИБ                           → ограничения безопасности
ЗАПУСК    Миграция, план внедрения                → как перейти от старого к новому
ПРОВЕРКА  ПМИ, тест-кейсы                         → как доказать, что работает
```

| Артефакт | На какой вопрос отвечает | Этап | Пишет | Утверждает | На малом проекте |
|---|---|---|---|---|---|
| Устав | Зачем, измеримые цели, границы | Инициация | РП | Спонсор, заказчик | Одна страница «цель + входит / не входит» — обязательно |
| Реестр стейкхолдеров | Кто влияет и кого затрагивает | Инициация | РП (СА, БА помогают) | РП | Список «кто заказчик, кто согласует, кого спросить» |
| Глоссарий | Что значит термин в этом проекте | С первых интервью | СА | — | 10–15 терминов |
| AS-IS | Как сейчас и что болит | Обследование | БА | Заказчик | 5–10 шагов и проблемы с цифрами |
| TO-BE | Как будет, бизнес-правила | Бизнес-анализ | БА | Заказчик | Если меняется работа людей |
| Gap-анализ | Что меняется: системы, данные, регламенты | Бизнес-анализ | БА | Заказчик | Колонка «что меняется» в TO-BE |
| БТ | Что нужно бизнесу и зачем | Бизнес-анализ | БА | Заказчик | Часто сливаются с ФТ или историями |
| Use cases | Кто и как пользуется системой, включая ошибки | Системный анализ | СА | Заказчик | Диаграмма + полные спецификации для сложных сценариев |
| ФТ | Что должна делать система | Системный анализ | СА | Заказчик + архитектор | Истории с точными критериями приёмки |
| НФТ | Насколько хорошо: скорость, надёжность, безопасность | Системный анализ | СА | Архитектор | 3–5 ключевых |
| Справочные данные (ролевая модель, тарифы…) | Данные, которые настраивают поведение системы | Системный анализ | СА | Владелец данных (в кейсе — ИБ) | Нужны всегда, если система ими управляется |
| Бэклог | Как требования режутся на работу | Перед разработкой | СА (PO владеет) | PO | Часто единственная форма требований |
| Трассировка | Как связаны цели, требования, тесты | С первых ФТ | СА | — | Связи задач в Jira |
| C4: контекст | Граница системы и соседи | Инициация → проектирование | Архитектор / СА | Архитектор | Почти всегда — 15 минут работы |
| Модель данных | Что хранится и как связано | Проектирование | СА (логическая) | Архитектор | Хотя бы концептуальная |
| Статусные модели | Как живут объекты | Системный анализ / проектирование | СА | Архитектор | Для каждого объекта со статусом |
| ADR | Почему принято решение | В момент решения | Архитектор | Архитектурный комитет | Пара абзацев на неочевидное решение |
| Карта интеграций, sequence, маппинг, API | С кем, как, в каком формате, что при ошибке | Проектирование | СА | Архитектор + владельцы смежных систем | Нужны, если есть внешние системы |
| Требования ИБ | Ограничения безопасности | Параллельно с ФТ | ИБ | ИБ | В банке — всегда: доступы, журналирование, ПДн |
| Миграция, план внедрения | Как перейти без потерь и как откатить | Проектирование → внедрение | СА / РП | РП, владельцы данных | «Как включаем, как откатываем, кого предупредить» |
| ПМИ, тест-кейсы | Как доказать, что работает | До испытаний | QA | Заказчик | Приёмочные сценарии |

### Минимальный набор для малого проекта

1. Цель с метрикой + «входит / не входит».
2. TO-BE, если меняется работа людей.
3. ФТ или истории с критериями приёмки.
4. Модель данных — хотя бы концептуальная.
5. Контекст + интеграции и контракты, если есть внешние системы.
6. Статусная модель для каждого объекта со статусами.
7. Приёмочные сценарии.

## Пример из кейса IDM-JOINER

Кейс устроен ровно по слоям: папки `00_project` … `07_testing` — см. <CaseRef href="/case/" id="Кейс">обзор и навигацию по слоям</CaseRef>.

Как одна потребность бизнеса проходит через все слои (трассировка из <CaseRef href="/case/cheatsheet/#4-трассировка-на-живом-примере" id="Шпаргалка">шпаргалки кейса</CaseRef>):

```text title="Цепочка «активация в 07:00»"
G-01   Сотрудник работает с первого дня (≥ 95% к 09:00)            устав
 └─ BR-04   Доступы готовы к первому дню и не активны до него      БТ
     ├─ FR-07   Создавать за 3 раб. дня в заблокированном состоянии ФТ
     └─ FR-08   Активировать в 07:00 по часовому поясу подразделения
          ├─ UC-02      Активировать доступы в день выхода          use cases
          ├─ ADR-002    Почему создаём заранее                      ADR
          ├─ org_unit.timezone                                      модель данных, маппинг
          ├─ CREATED_DISABLED → ACTIVE                              статусная модель
          ├─ SEQ-01, этап «День D, 07:00»                           sequence
          ├─ NFR-04     Доступность круглосуточно                   НФТ
          └─ TC-06      Активация в Москве, Екатеринбурге, Владивостоке  тест-кейсы
```

Пример «вопроса вверх»: при маппинге выяснилось, что код подразделения HRMS не совпадает с кодом филиала АБС. Понадобились справочник соответствия, владелец справочника и правило на случай отсутствия значения — см. <CaseRef href="/case/04-integrations/data-mapping/" id="Маппинг">маппинг данных</CaseRef>.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Писать документы «потому что так положено» | Тратится время, документы никто не читает | Для каждого артефакта — вопрос и читатель |
| Нет ID в требованиях | Невозможны трассировка и анализ влияния | ID с префиксом в каждом документе |
| Справочные данные «потом, это просто справочник» | Система не работает без ролей / тарифов / статусов; самое долгое согласование | Планировать как требование, назначить владельца данных |
| Интеграции без колонки «что при ошибке» | Сбои обнаруживаются в эксплуатации | Для каждой интеграции: ошибки, повторы, ответственный |
| Требования ИБ подключаются на приёмке | Переделка архитектуры перед запуском | ИБ — параллельно с ФТ |
| Трассировка заполнена один раз | Не помогает при изменениях | Обновлять при каждом изменении требований |
