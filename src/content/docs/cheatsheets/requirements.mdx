## Уровни

| Уровень | Вопрос | Кто → утверждает |
|---|---|---|
| БТ | Что нужно бизнесу и зачем? | БА → заказчик |
| Пользовательские | Что делают с системой? | БА/СА → заказчик |
| ФТ | Что делает система? | СА → заказчик + архитектор |
| НФТ | Насколько хорошо? (измеримо) | СА → архитектор |
| Бизнес-правила | Если…, то… | БА → заказчик |
| Ограничения | Что не обсуждается | источник |
| Переход | Миграция, обучение | СА/РП |

БТ без техники. ФТ: «Система должна \<действие\> \<объект\> \<условие\>». НФТ: метрика + значение + условия + способ проверки.

</section>

<section>

## Хорошее требование

Необходимое · однозначное · **атомарное** · **проверяемое** · выполнимое · корректное · трассируемое · «что», а не «как». Набор — полный и непротиворечивый.

**Размытые слова:** быстро, удобно, надёжно, и т. д., при необходимости, по возможности, должна поддерживать, обрабатывать, гибкий, все/всегда, и/или → число, условие, перечень, конкретное действие.

**Тест:** можно ли по требованию написать тест?

</section>

<section>

## User stories

«Как \<роль\>, я хочу \<действие\>, чтобы \<ценность\>» + критерии. **3C:** Card, Conversation, Confirmation.

**INVEST:** Independent · Negotiable · Valuable · Estimable · Small · Testable.

Эпик → история → задача; enabler — техническая история. Резать **вертикально**: по шагам, правилам, системам, сценариям, CRUD, качеству. **DoR** — готово к работе, **DoD** — готово к закрытию.

</section>

<section>

## Use case

Актор (внешний; система и таймер тоже) · цель «глагол + объект» · предусловия · триггер · постусловия **успеха и неуспеха** · основной поток (5–10 шагов) · альтернативы (3a) · исключения · связанные ФТ. Ценность — в **альтернативах**. Use case → несколько историй.

</section>

<section>

## Критерии приёмки и Gherkin

Пишутся **до** разработки; правила или сценарии. **Дано** (контекст) / **Когда** (действие) / **Тогда** (проверяемый результат) / **И**, **Но**. **Предыстория** — общие «Дано»; **Структура сценария** + **Примеры** — таблица данных. Поведение, а не клики; один сценарий — одно поведение; ошибки и границы.

</section>

## Приоритизация

**MoSCoW:** Must (без этого не запустимся) · Should (есть обход) · Could · Won't this time (записать, не удалять).

**RICE** = Reach × Impact × Confidence / Effort. Impact 3 / 2 / 1 / 0,5 / 0,25; Confidence 100 / 80 / 50%.

**WSJF** = Cost of Delay / Job Size; CoD = ценность + критичность по времени + снижение риска / возможности; ряд 1, 2, 3, 5, 8, 13, 20.

**Kano:** обязательные · одномерные · привлекательные · безразличные · обратные; анкета «если есть / если нет».

Решает владелец, аналитик готовит данные.

</section>

<section>

## Трассировка и изменения

Цель → БТ → ФТ → UC / INT → TC. **Прямая** (что реализует, чем проверено) · **обратная** (зачем, нет ли «сирот») · горизонтальная.

**Базовая линия** → изменения только через **CR**: анализ влияния по трассировке → оценка → решение владельца → новая версия → обновить связи и тесты.

**Кейс:** 07:00 → 08:30 затрагивает FR-08, BRL-02, UC-02, SEQ-01, NFR-02, TC-06.

</section>
