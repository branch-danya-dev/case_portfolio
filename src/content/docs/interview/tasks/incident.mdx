<Brief>

Задача на материале кейса IDM-JOINER — такие дают на собеседованиях middle-аналитикам и такие случаются в первый месяц сопровождения. Данные ниже — сокращённые; полный набор и хронология — в документе кейса <CaseRef href="/case/08-operations/incident-example/" id="INC-01">INC-01</CaseRef>.
Ответьте на шесть вопросов, рассуждая вслух: **где ошибка → что ожидалось → какая система источник → дефект или контракт → какие данные пострадали → нужен ли повторный запуск**. Метод — на странице [«Разбор инцидента»](/operations/incident-analysis/).

</Brief>

## Контекст

IdM создаёт учётные записи в АБС за 3 рабочих дня до выхода сотрудника, в 09:00, через REST-адаптер АБС (`POST /users`, заголовок `Idempotency-Key` = идентификатор задачи). По FR-16 технические ошибки (тайм-аут, 5xx, 429) повторяются: всего 3 попытки, повторы через 1 и 5 минут; после этого — задача администраторам АБС в ServiceDesk, задача провижининга — MANUAL, учётная запись — FAILED.

## Данные

**Алерт, понедельник 14.06, 09:07:** `[ALR-02] P2 · коннектор ABS · доля ошибок за час 21% (порог 5%)`.

**Лог сервиса провижининга** по одному сотруднику:

```text
09:00:04 WARN  traceId=7d1c…e9a1 personId=P-100611 taskId=t-90412 ABS CREATE attempt=1 http=503 → retry 09:01:04
09:01:04 WARN  traceId=7d1c…e9a1 personId=P-100611 taskId=t-90412 ABS CREATE attempt=2 http=503 → retry 09:06:04
09:06:04 ERROR traceId=7d1c…e9a1 personId=P-100611 taskId=t-90412 ABS CREATE attempt=3 http=503 → MANUAL, SD-8811
```

**Ответ адаптера:** `503 Service Unavailable`, `Retry-After: 120`, `detail: "Rate limit exceeded for client idm-provisioning: 30 requests per minute. Client blocked for 120 s"`.

**Очередь повторов по АБС:** 09:00 — отправлено 67, принято 30; 09:01 — отправлено 37, принято 0; 09:06 — отправлено 37, принято 30, 7 → MANUAL.

**DLQ** `hr.employee.events.v1.dlq`: новых сообщений нет.

**БД IdM:** 7 задач `ABS / CREATE / MANUAL / attempts = 3`, задачи SD-8811…SD-8817; учётные записи АБС этих сотрудников — FAILED, AD и Exchange — CREATED_DISABLED. К 09:20 администраторы АБС успели вручную выполнить SD-8812 и SD-8815.

**Контракт адаптера:** `'503': АБС недоступна (закрытие дня, регламентные работы)`; ответа 429 и описания лимитов нет.

**Заметки к релизу адаптера 1.4.0** (пятница, 11.06, 20:00): «Добавлено ограничение частоты запросов на клиента (30 в минуту). При превышении клиент блокируется на 120 секунд».

## Вопросы

<Exercise title="где ошибка и что ожидалось">

1. На каком шаге и в каком вызове ошибка?
2. Что должно было произойти по требованиям?

<Fragment slot="solution">

1. Шаг провижининга, вызов `POST /users` из сервиса провижининга IdM в адаптер АБС: три ответа 503 подряд. Кадровые события обработаны нормально — DLQ пуст, учётные записи AD и Exchange созданы.
2. По FR-07 — учётная запись АБС в статусе CREATED_DISABLED за 3 рабочих дня до выхода; по статусной модели — PLANNED → CREATING → CREATED_DISABLED.

</Fragment>

</Exercise>

<Exercise title="какая система — источник, дефект или контракт">

3. Какая система источник сбоя? Почему пострадали только 7 из 67?
4. Это дефект кода IdM? Если нет — что это?

<Fragment slot="solution">

3. Адаптер АБС 1.4.0: ограничение 30 запросов в минуту и блокировка клиента на 120 секунд. IdM отправила 67 запросов в 09:00 — 37 сверх лимита. Повтор через минуту попал в блокировку (120 секунд), повтор через 5 минут снова пришёл пачкой — 37 запросов при лимите 30. Семеро не уложились ни в одну из трёх попыток.
4. Не дефект IdM: она сделала ровно то, что требует FR-16. Это **нарушение контракта** — адаптер изменил поведение (ограничение частоты) без изменения контракта и использовал для превышения лимита код 503, который по контракту означает «АБС недоступна». И **пробел требований**: ни в контракте, ни в НФТ нет пропускной способности адаптера и правил для ограничения частоты (429, `Retry-After`).

</Fragment>

</Exercise>

<Exercise title="какие данные пострадали и нужен ли повторный запуск">

5. Какие данные пострадали и насколько это срочно?
6. Нужен ли повторный запуск? Для кого — да, для кого — нет?

<Fragment slot="solution">

5. 7 учётных записей АБС в FAILED, 7 задач MANUAL, 7 задач в ServiceDesk, 2 из них уже выполнены вручную. Порчи и потери данных нет. Срочность — выход сотрудников в четверг 17.06: доступы нужны до 07:00 этого дня, иначе нарушается цель «работает с первого дня». Приоритет P2.
6. Да, после устранения причины (временно поднять лимит адаптера):
   - для **5 сотрудников** — повторный запуск задач с тем же `Idempotency-Key`: повтор безопасен, дубля не будет; затем отменить их задачи в ServiceDesk;
   - для **2 сотрудников**, созданных вручную, повторять **нельзя**: адаптер вернёт 409 «логин занят другим пользователем» (у ручного пользователя другой ключ). Нужно закрыть их задачи в ServiceDesk с `externalId` — IdM получит webhook и переведёт учётные записи в CREATED_DISABLED (FR-17).

</Fragment>

</Exercise>

<Exercise title="как не допустить повторения">

Что вы предложите по итогам — в требованиях, контракте, системе, мониторинге и процессе?

<Fragment slot="solution">

- **Контракт адаптера:** при превышении лимита — 429 и `Retry-After`; лимит описан в контракте.
- **FR-16:** при 429 повторять не раньше `Retry-After` и не тратить на это 3 попытки; случайная задержка к интервалам повторов, чтобы повторы не приходили пачкой.
- **Планировщик:** ограничение скорости запросов по системам вместо пакета в 09:00.
- **Новое НФТ:** пропускная способность адаптера под пиковый приём.
- **Мониторинг:** алерт на рост ручных задач по системе.
- **Процесс:** изменения поведения адаптера — только через изменение контракта и уведомление потребителей.
- **Порядок выкатки:** сначала IdM учится обрабатывать 429, потом адаптер начинает его отдавать, — иначе 429 по старому FR-16 будет повторяться через 1 и 5 минут и инцидент повторится.

Так это оформлено в кейсе: <CaseRef href="/case/08-operations/problem-rca/" id="PRB-01">PRB-01</CaseRef> и <CaseRef href="/case/08-operations/change-request/" id="CHG-01">CHG-01</CaseRef>.

</Fragment>

</Exercise>

## Что оценивает интервьюер

- Начинает с масштаба и «что изменилось», а не с поиска бага в своём коде.
- Сравнивает поведение с требованиями и контрактом — и замечает, что IdM действовала по FR-16.
- Не забывает про ложные следы: проверяет DLQ и исключает его.
- Помнит про ручные действия за время сбоя и про идемпотентность при повторном запуске.
- Разделяет восстановление и устранение причины, предлагает изменения в нескольких слоях и порядок выкатки.
