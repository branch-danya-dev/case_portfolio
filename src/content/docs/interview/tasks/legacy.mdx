<Brief>

Проверяют, умеете ли вы **систематически** восстанавливать поведение по артефактам: интерфейсу, данным, API, логам, людям — и не принимаете ли случайность за правило. Сильный ответ даёт план, работу с данными (что можно выяснить запросами) и честную пометку, насколько каждый вывод подтверждён.
Сценарий придуман для задачи по мотивам кейса IDM-JOINER: старую систему заявок на доступ заменяет IdM. Метод — на странице [«Legacy без документации»](/onboarding/legacy/).

</Brief>

## Контекст

В банке 9 лет работает самописная система «Заявки ДИТ»: руководители заказывают доступы, администраторы исполняют. Автор системы уволился, документации нет. Через полгода её заменяет IdM, и до этого нужно понять, **что она на самом деле делает**: какие правила потеряются при переходе.

## Данные

**Интерфейс:** форма заявки (сотрудник, система, роль, комментарий); список «Мои заявки» с колонкой «Статус»; у администратора — кнопки «Взять в работу», «Выполнено», «Отклонить»; у некоторых заявок есть кнопка «Согласовать» для начальника управления.

**БД, таблица `request`:**

```sql
SELECT status, COUNT(*) FROM request GROUP BY status;
-- 1   48 112
-- 2      231
-- 3   41 870
-- 4    3 960
-- 5    1 044
-- 7       12
```

```sql
SELECT r.status, s.name, COUNT(*) FROM request r JOIN system s ON s.id = r.system_id
WHERE r.approved_by IS NOT NULL GROUP BY r.status, s.name;
-- согласование начальника встречается только у систем АБС и «Казначейство»
```

Ещё таблицы: `request_history` (id заявки, старый статус, новый статус, кто, когда), `system`, `role`, `user`. Есть ночной job `close_old` без описания.

**API:** `GET /api/requests?user=…` использует внутренний портал; `POST /api/requests/{id}/done` вызывает скрипт администраторов АБС.

## Вопросы

<Exercise title="план исследования">

С чего начнёте и в каком порядке? Какие источники используете?

<Fragment slot="solution">

1. **Люди — короткие интервью:** руководители (как заказывают, что раздражает), администраторы (как исполняют, обходные пути), владелец системы, сопровождение. Цель — не правила, а **гипотезы и подсказки**, где искать.
2. **Интерфейс** — пройти основные сценарии на тестовом стенде под разными ролями: заказ, согласование, исполнение, отказ.
3. **Данные** — главный источник фактов: справочники статусов и переходов по `request_history`, распределения, закономерности (у каких систем есть согласование).
4. **Интеграции и фоновые задачи** — API, кто его вызывает (логи), ночной `close_old` (код или SQL задания).
5. **Код** — точечно, чтобы подтвердить правило, найденное в данных (вместе с разработчиком).
6. **Оформить и подтвердить** — модель «как есть» с уровнем уверенности по каждому правилу, проверка с пользователями и на тестовом стенде.

</Fragment>

</Exercise>

<Exercise title="статусная модель по данным">

Как по данным восстановить, что значат статусы 1–7 и какие переходы допустимы? Какие запросы напишете?

<Fragment slot="solution">

**Переходы** — из истории:

```sql
SELECT old_status, new_status, COUNT(*) AS n
FROM request_history
GROUP BY old_status, new_status
ORDER BY n DESC;
```

Частые переходы — основной путь, редкие — исключения или ручные правки. Статус без исходящих переходов — конечный.

**Смысл статусов** — сопоставить с действиями в интерфейсе: кто переводит (роль пользователя в `request_history`), какая кнопка. Например, если в 3 переводят только администраторы после «Выполнено» — 3 = «Выполнена».

**Статус 6 отсутствует** — либо больше не используется (поискать в старых записях истории), либо его удаляли. **Статус 7 (12 заявок)** — подозрение на ручную правку или устаревший статус: посмотреть даты и кто переводил.

**Статус 2 (231 заявка)** — вероятно, «на согласовании». Проверить, сколько они там висят:

```sql
SELECT MIN(created_at), MAX(created_at) FROM request WHERE status = 2;
```

Заявки, висящие годами, — кандидаты на чистку перед миграцией.

**Ночной job:** сравнить `request_history` в ночные часы — кто (системный пользователь) и из какого статуса в какой переводит. Так находится скрытое правило, например «через 30 дней без исполнения заявка закрывается».

</Fragment>

</Exercise>

<Exercise title="правило или случайность">

Согласование начальника встречается только у АБС и «Казначейства». Это правило? Как это проверить и оформить результат?

<Fragment slot="solution">

**Это гипотеза, а не правило.** Варианты: признак у системы (`system.requires_approval`), правило в коде по списку систем, или руководители просто нажимали «Согласовать» только там. Проверка:
- есть ли у таблицы `system` поле, которое это определяет;
- создать на тестовом стенде заявку в АБС и в другую систему — появляется ли кнопка «Согласовать»;
- были ли заявки в АБС **без** согласования — если да, правило не жёсткое;
- спросить администраторов АБС и ИБ — это может быть требование ИБ, о котором никто не написал.

**Оформление:** модель «как есть» — статусы, переходы, роли, правила — и у каждого правила:
- источник (данные, код, интерфейс, интервью);
- уровень уверенности (подтверждено, вероятно, гипотеза);
- решение для IdM: переносим, отказываемся, нужно решение владельца.

Такое правило не должно потеряться при переходе: в IdM критичные полномочия согласует ИБ (FR-14). Значит, нужно сверить, что АБС и «Казначейство» там тоже окажутся критичными.

</Fragment>

</Exercise>

## Что оценивает интервьюер

- План с несколькими источниками, где люди дают гипотезы, а данные — факты.
- Умение получить статусную модель из истории переходов запросом.
- Внимание к аномалиям: пропавший статус, редкий статус, вечные заявки, ночной job.
- Различие между правилом и случайностью и проверка гипотез на тестовом стенде.
- Результат с уровнем уверенности и решением «переносим или нет» для новой системы.
