<Brief>

Проверяют, как вы действуете, когда «источник истины» раздвоился. Неправильные реакции — «API неправильный, переделать по ФТ» или «код главнее, поправлю ФТ». Правильная — **по каждому расхождению выяснить, что нужно бизнесу, и принять решение с тем, кто вправе его принять**.
Сценарий — заявки на доступ в кейсе IDM-JOINER. Фрагмент ФТ составлен для задачи; контракт — из <CaseRef href="/case/04-integrations/api-idm/" id="IdM API">API IdM</CaseRef>. Метод — на странице [«Середина реализации»](/onboarding/mid-project/).

</Brief>

## Контекст

Разработка портала и API заявок на доступ идёт третий месяц, спринт 6 из 10. Предыдущий аналитик ушёл. Фронтенд пишут по API, бэкенд — по API и устным договорённостям, тестировщики — по ФТ. На демо заказчик (руководитель розничной сети) сказал: «Это не то, что мы согласовывали».

## Данные

**ФТ, раздел «Заявка на доступ» (версия 1.2, согласована заказчиком и ИБ):**

1. Руководитель запрашивает для подчинённого **не более 5** полномочий в одной заявке.
2. Обоснование обязательно, **не короче 20 символов**.
3. Отказ согласующего — **только с комментарием**.
4. Руководитель может **отозвать** заявку, пока она на согласовании.
5. При SoD-конфликте руководитель видит предупреждение до отправки заявки.

**Контракт API (`idm-api.openapi.yaml`, в репозитории, меняли разработчики):**

```yaml
AccessRequestCreate:
  required: [employeeNumber, items, justification]
  properties:
    items: { type: array, minItems: 1, maxItems: 10 }
    justification: { type: string, minLength: 10, maxLength: 1000 }
Decision:
  required: [decision]
  properties:
    decision: { enum: [APPROVED, REJECTED] }
    comment: { type: string, description: "Обязателен при REJECTED" }
AccessRequest:
  properties:
    status: { enum: [DRAFT, ON_APPROVAL, APPROVED, REJECTED, PROVISIONING, COMPLETED, PARTIALLY_COMPLETED, CANCELLED] }
    sodConflicts: [ ... ]   # заполняется после создания заявки
# операции: POST /access-requests, GET /access-requests/{id}, POST …/decisions — операции отзыва нет
```

**Тестировщики:** завели 4 дефекта по ФТ, разработчики закрыли их с комментарием «по API так».

## Вопросы

<Exercise title="расхождения">

Найдите все расхождения ФТ и API и для каждого скажите, чем оно грозит.

<Fragment slot="solution">

| № | ФТ | API | Чем грозит |
|---|---|---|---|
| 1 | Не более 5 полномочий | `maxItems: 10` | Заявки на 6–10 полномочий пройдут; нагрузка на согласующих выше ожидаемой |
| 2 | Обоснование ≥ 20 символов | `minLength: 10` | Короткие обоснования вроде «для работы» — ИБ не сможет оценить заявку |
| 3 | Отказ только с комментарием | Обязательность — только в `description`, схема её не проверяет | Отказы без причины; правило зависит от того, проверит ли его код |
| 4 | Отзыв заявки | Статус CANCELLED есть, операции нет | Функция не реализована, хотя статус в модели есть |
| 5 | Предупреждение о SoD **до** отправки | `sodConflicts` — **после** создания | Руководитель узнаёт о конфликте уже после отправки; нужен отдельный метод проверки или изменение процесса |
| 6 | — | Статус DRAFT | В ФТ черновиков нет: либо нереализуемое лишнее, либо неописанная функция |

Отдельно — **процессное расхождение:** тестировщики работают по ФТ, разработчики — по API, и дефекты закрываются без решения. Это важнее любого отдельного пункта.

</Fragment>

</Exercise>

<Exercise title="кто прав и кто решает">

Как решить, какой вариант правильный, и кто принимает решение?

<Fragment slot="solution">

- **Не выбирать самому между документами.** ФТ согласованы заказчиком и ИБ — это базовая линия. Но API мог измениться по разумной причине: устная договорённость, техническое ограничение. Для каждого пункта — выяснить у разработчиков **почему** так сделано.
- **Разделить по типу:**
  - пункты 1–3 — параметры правил; решает владелец требования (заказчик, для 2–3 — ещё и ИБ);
  - пункт 4 — нереализованная функция; решает владелец продукта: делать в этом релизе или позже;
  - пункт 5 — изменение процесса или API; нужен вариант решения с оценкой;
  - пункт 6 — выяснить, нужен ли DRAFT, и либо описать его в ФТ, либо убрать.
- **Принять решение на одной встрече** владельца продукта, заказчика, ИБ и ведущего разработчика по подготовленной таблице с вариантами и стоимостью. Записать решения; изменения ФТ — через управление изменениями требований (новая версия и согласование).

</Fragment>

</Exercise>

<Exercise title="что делать со спринтом и процессом">

Что делать с текущей работой и как не допустить повторения?

<Fragment slot="solution">

**Сейчас:**
- переоткрыть 4 закрытых дефекта со статусом «требует решения», а не «по API так»;
- предупредить владельца продукта о риске для приёмки: ПМИ пишут по ФТ, и при приёмке эти расхождения всплывут как дефекты;
- до решения не брать в работу задачи, которые зависят от спорных пунктов.

**Процесс:**
- **один источник истины для контракта** — OpenAPI в репозитории. Изменения контракта — через ревью аналитика, со ссылкой на требование;
- **трассировка:** у каждого правила ФТ есть место в контракте или коде и тест; в контракте правило проверяется схемой, а не описанием (пункт 3 → условие в схеме или явное правило в ФТ с тестом);
- **устные договорённости фиксируются** в задаче и в ФТ в течение дня;
- **на демо** — показывать по сценариям ФТ, чтобы расхождения находились раньше.

</Fragment>

</Exercise>

## Что оценивает интервьюер

- Находит не только очевидные расхождения, но и тонкие: правило только в `description`, статус без операции, «до» и «после» отправки.
- Не объявляет правым ни ФТ, ни код, а выясняет причину и отдаёт решение тому, кто вправе его принять.
- Видит процессную причину: работа по разным источникам и закрытие дефектов без решения.
- Думает о приёмке: ПМИ по ФТ найдёт всё это в худший момент.
