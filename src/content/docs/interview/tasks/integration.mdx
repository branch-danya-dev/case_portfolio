<Brief>

Формулировка обычно короткая: «Система А должна передавать данные в систему Б. Спроектируйте». Правильного ответа нет — оценивают **вопросы, которые вы задаёте**, и то, **как вы обосновываете выбор**.
Порядок: **уточнить → выбрать стиль → описать контракт → ошибки и повторы → безопасность → мониторинг**.
Сильный кандидат сам говорит о дублях, недоступности и сверке данных.

</Brief>

## Чек-лист вопросов

| Группа | Вопросы |
|---|---|
| Бизнес | Зачем Б эти данные? Насколько быстро они нужны: секунды, минуты, раз в сутки? Что будет, если данные опоздают или потеряются? |
| Данные | Какие сущности и поля? Кто владелец данных (мастер-система)? Объём: сколько записей и как часто? Нужна ли история изменений? |
| Взаимодействие | Нужен ли ответ отправителю? Сколько получателей сейчас и потом? Кто инициатор? |
| Ошибки | Что делать при недоступности Б? Допустимы ли дубли? Важен ли порядок? |
| Безопасность | Есть ли ПДн или банковская тайна? Сеть, аутентификация, шифрование? |
| Ограничения | Что умеют системы (API, шина, только файлы)? Сроки и ресурсы смежных команд? |

## Как выбрать стиль

| Ситуация | Стиль |
|---|---|
| Нужен немедленный ответ, пользователь ждёт | Синхронный REST / gRPC |
| Событие интересно нескольким системам, важна слабая связность | Брокер сообщений (Kafka, RabbitMQ) |
| Большие объёмы раз в сутки, задержка допустима | Пакетная выгрузка, файловый обмен |
| Получатель не может обрабатывать поток | Очередь с ограничением скорости |
| Риск потерять событие | События + периодическая сверка полным срезом |

## Задача 1. Клиенты из CRM в АБС

<Exercise title="CRM → АБС">

В банке внедряют новую CRM. Менеджер заводит в CRM нового клиента — юрлицо, и клиент должен появиться в АБС, чтобы открыть ему счёт. Спроектируйте интеграцию.

<Fragment slot="solution">

**Уточнения (пример ответов интервьюера):** счёт открывают в тот же день, но не мгновенно; мастер клиентских данных — АБС (там проходит проверка «Знай своего клиента»); у АБС есть внутренний REST API; в CRM создаётся 50–200 клиентов в день.

**Решение:**

<Steps>

1. **Стиль:** синхронный вызов REST API АБС из CRM, потому что менеджеру нужен результат (клиент создан или ошибка) и идентификатор клиента в АБС. Если АБС не отвечает — заявка ставится в очередь повторов, менеджер видит статус «Передаётся в АБС».

2. **Контракт:** `POST /clients` с ключом идемпотентности (id клиента в CRM); ответ — `clientId` АБС, который сохраняется в CRM. Ошибки в формате RFC 9457 (ранее RFC 7807): ошибки валидации — сразу менеджеру, технические — в повтор.

3. **Дубли:** перед созданием АБС ищет клиента по ИНН; если клиент уже есть — возвращает существующий `clientId` (связать, а не создать).

4. **Обратный поток:** изменения статуса проверки клиента в АБС публикуются событием, CRM подписана — менеджер видит, что клиент прошёл проверку.

5. **Безопасность:** mTLS между системами, технический пользователь CRM с правом только на создание клиентов, журнал вызовов.

6. **Мониторинг и сверка:** метрики ошибок и очереди повторов; ежедневная сверка «клиенты CRM без `clientId` АБС».

</Steps>

**Что оценивает интервьюер:** определил мастер-систему; объяснил выбор синхронного вызова; подумал о дублях (ИНН, ключ идемпотентности); разделил бизнес- и технические ошибки; упомянул безопасность и сверку.

</Fragment>

</Exercise>

## Задача 2. Как IdM узнаёт о приёме (кейс IDM-JOINER)

<Exercise title="HRMS → IdM">

IdM должна как можно раньше узнавать о приёме сотрудника и не терять события. Команда HRMS может выделить не более двух спринтов. Предложите варианты и выберите один.

<Fragment slot="solution">

Это решение <CaseRef href="/case/03-architecture/adr/" id="ADR-001">ADR-001</CaseRef>:

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. HRMS вызывает REST API IdM | Просто, синхронный ответ | HRMS должна обрабатывать недоступность IdM и повторять вызовы; связность |
| B. IdM опрашивает HRMS по расписанию | Не нужна доработка публикации в HRMS | Задержка, нагрузка на HRMS, сложно выделить изменения |
| C. HRMS публикует события в Kafka | Слабая связность, гарантия доставки, события могут читать другие системы | Нужна идемпотентность в IdM, зависимость от шины |

**Выбор:** C плюс **ежедневная сверка полным срезом** (FR-05) — страховка от потерянных событий.

**Последствия, которые стоит назвать:** идемпотентность по `eventId` (FR-03), DLQ для некорректных событий (FR-02), контракт AsyncAPI, согласованный с командой интеграции.

</Fragment>

</Exercise>

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Сразу «сделаем REST» | Решение без понимания задачи | Сначала вопросы |
| Не определить мастер-систему | Конфликты данных, перезапись | Владелец каждого атрибута |
| Только успешный сценарий | Потери и дубли в эксплуатации | Повторы, идемпотентность, DLQ, сверка |
| Забыть про ПДн | Не пройдёт согласование ИБ | Шифрование, минимизация полей, журнал |
| Нет мониторинга | Сбои замечают пользователи | Метрики, алерты, сверка |
