<Brief>

В отличие от [задачи про INC-01](/interview/tasks/incident/), здесь ошибка в своей системе, и 500 говорит только «что-то упало на сервере». Проверяют, умеете ли вы **сузить проблему** (какой метод, у кого, с какого момента), **связать с изменением**, найти **закономерность в данных** — и заметить, что тот же дефект данных может ломать не только экран.
Сценарий построен на кейсе IDM-JOINER, релиз портала придуман для задачи. Метод — на странице [«Разбор инцидента»](/operations/incident-analysis/).

</Brief>

## Контекст

Портал IdM показывает руководителю статус подготовки доступов будущего сотрудника (FR-23). Во вторник вечером вышел релиз портала 2.4. В среду с утра в ServiceDesk пришли 9 обращений «страница сотрудника не открывается».

## Данные

**Метрика: ответы API IdM с кодом 500, по часам:**

| Метод | Вт 10–18 | Ср 09:00 | Ср 10:00 | Ср 11:00 |
|---|---|---|---|---|
| `GET /employees/{employeeNumber}/access` | 0–1 | 38 | 41 | 37 |
| `POST /access-requests` | 0 | 0 | 1 | 0 |
| Остальные | 0–2 | 1 | 0 | 2 |

Доля 500 по `GET /employees/…/access` — 6% запросов; остальные 94% отвечают 200.

**Заметки к релизу портала 2.4:** «На странице сотрудника показывается дата и время активации учётных записей по часовому поясу подразделения сотрудника».

**Лог API IdM** (три ответа 500 подряд):

```text
09:12:40 ERROR errorId=e-5b21 traceId=a41f… GET /employees/007731/access → 500 NullPointerException: OrgUnit.timezone is null (orgUnit=4120)
09:14:02 ERROR errorId=e-5b2c traceId=c903… GET /employees/007744/access → 500 NullPointerException: OrgUnit.timezone is null (orgUnit=4121)
09:15:55 ERROR errorId=e-5b30 traceId=0e7d… GET /employees/006102/access → 500 NullPointerException: OrgUnit.timezone is null (orgUnit=4120)
```

**БД IdM, справочник подразделений:**

```sql
SELECT code, name, timezone, created_at FROM org_unit WHERE timezone IS NULL;
-- 4120  Офис «Казань-Север»      NULL  2032-02-11
-- 4121  Офис «Казань-Юг»         NULL  2032-02-11
-- 4122  Кредитный центр Казань    NULL  2032-02-14
```

Подразделения приходят из HRMS, а часовой пояс заполняет вручную команда IdM — так было решено при миграции. Подразделения 4120–4122 созданы в феврале при открытии региона. На следующей неделе в этих подразделениях выходят 11 новых сотрудников.

## Вопросы

<Exercise title="масштаб и причина">

1. Каков масштаб проблемы и что изменилось?
2. Какова причина?

<Fragment slot="solution">

1. **Масштаб:** только один метод — `GET /employees/{employeeNumber}/access`, около 6% его вызовов; началось в среду утром, после вечернего релиза 2.4. Остальной API работает. Пользователи — руководители подразделений, для которых падает страница.
2. **Причина:** релиз 2.4 начал показывать время активации по часовому поясу подразделения. У трёх новых подразделений часовой пояс не заполнен (`NULL`), и код не обрабатывает пустое значение. Падают страницы сотрудников этих подразделений. Подтверждение: во всех логах `OrgUnit.timezone is null`, `orgUnit` — 4120 и 4121, а в справочнике пустые пояса ровно у 4120–4122.

</Fragment>

</Exercise>

<Exercise title="что делать сейчас и что ещё сломано">

1. Что сделать, чтобы восстановить работу?
2. Какие ещё последствия у этой же причины? Подсказка: что ещё в IdM зависит от часового пояса подразделения?

<Fragment slot="solution">

1. **Восстановление.** Самое быстрое и безопасное — **заполнить часовой пояс** трём подразделениям (данные, а не код: Казань — тот же пояс, что и Москва, но значение подтвердить у владельца справочника). Страницы откроются сразу, откат релиза не нужен. Параллельно — исправление кода: обработка пустого значения.
2. **Главное скрытое последствие — активация.** По FR-08 IdM активирует учётные записи в 07:00 **по часовому поясу подразделения**. С пустым поясом активация 11 сотрудников на следующей неделе тоже под угрозой: она упадёт или пройдёт не в то время. Экран сломался громко, а активация сломалась бы тихо, в день выхода. Проверить: как планировщик ведёт себя при пустом поясе, есть ли уже запланированные активации для 4120–4122, сработал бы ALR-05.

Поэтому заполнить пояса нужно **до** ближайших дат выхода — это важнее починки экрана.

</Fragment>

</Exercise>

<Exercise title="классификация и изменения">

Это дефект кода, требований или данных? Что изменить, чтобы не повторилось?

<Fragment slot="solution">

Причин несколько, и это нормально:

- **Данные:** часовой пояс обязателен для работы системы, но заполняется вручную, и новые подразделения появляются без него.
- **Пробел требований:** нигде не сказано, что делать с подразделением без пояса, и не описан процесс заполнения справочника для новых подразделений.
- **Дефект реализации:** код релиза 2.4 не обрабатывает пустое значение; тесты не покрывали подразделение без пояса.

Изменения:
- **Требование:** поведение при пустом поясе (показ без времени и предупреждение, а не падение; для активации — алерт и задача команде IdM).
- **Процесс и данные:** новое подразделение из HRMS без пояса → задача владельцу справочника; проверка справочника в ежедневной сверке; в идеале — пояс приходит из HRMS (вопрос к команде HRMS).
- **Мониторинг:** алерт на подразделения без пояса, у которых есть ближайшие даты выхода.
- **Тесты:** подразделение без пояса — в регрессионный набор.

</Fragment>

</Exercise>

## Что оценивает интервьюер

- Сужает проблему по метрикам: один метод, доля запросов, момент начала.
- Связывает начало проблемы с релизом и читает заметки к релизу.
- Ищет закономерность в данных (общее у упавших запросов), а не разбирает каждый запрос отдельно.
- Выбирает быстрый безопасный способ восстановления (данные) вместо отката.
- **Главное:** находит скрытое последствие — активацию в день выхода, — то есть думает о системе, а не о симптоме.
