## Алгоритм построения

<Steps>

1. **Граница системы** — прямоугольник с названием.
2. **Акторы:** пройдитесь по ролям людей, внешним системам и времени (таймер). Все — снаружи границы.
3. **Цели акторов** — прецеденты «глагол + объект». Один прецедент — один результат, ценный для актора.
4. **Связи актор — прецедент.**
5. **include** — только для действительно общих частей нескольких прецедентов; **extend** — для условных расширений.
6. **Проверка:** нет «кнопок», нет внутренних компонентов в роли акторов, каждый актор с чем-то связан.
7. **Когда остановиться:** все цели всех акторов на диаграмме, 5–15 прецедентов. Больше — разбейте по подсистемам.

</Steps>

## Синтаксис

**Mermaid не поддерживает use case диаграммы.** Используйте PlantUML или визуальный редактор.

<TabItem label="PlantUML: пример">

<TabItem label="PlantUML: шпаргалка">

```text title="PlantUML: элементы use case"
@startuml
left to right direction          ' раскладка слева направо
actor "Руководитель" as mgr      ' актор
actor "HRMS" as hrms <<система>> ' актор-система со стереотипом
rectangle "IdM" {                ' граница системы
  usecase "Запросить доступ" as UC1
  usecase "Проверить SoD" as SOD
  usecase "Рассмотреть конфликт" as UC4
}
mgr --> UC1                      ' ассоциация
UC1 ..> SOD : <<include>>        ' include: от базового к включаемому
UC4 ..> UC1 : <<extend>>         ' extend: от расширения к базовому
actor "Сотрудник" as emp
emp <|-- mgr                     ' обобщение актора
note right of UC1 : заметка      ' заметка
@enduml
```

</TabItem>
</Tabs>

## В визуальном редакторе

**draw.io:** включите библиотеку фигур UML — в ней есть актор, прецедент (эллипс) и рамка системы. Связи include и extend рисуются пунктирной стрелкой с подписью `<<include>>` / `<<extend>>`. Следите за направлением стрелок вручную — редактор его не проверяет.

**Enterprise Architect** и аналогичные CASE-инструменты хранят use case как элементы модели: один прецедент можно использовать на нескольких диаграммах и связать со спецификацией и требованиями.

Что изменилось:

- **Кнопки и экраны** («Открыть портал», «Нажать «Создать заявку»») заменены **целью**: «Запросить дополнительный доступ».
- **БД IdM убрана из акторов** — это часть системы, а не внешний участник.
- **Появилась граница системы** — видно, что внутри IdM, а что снаружи.
- **include «Согласовать с ИБ» заменён на extend «Рассмотреть SoD-конфликт»** с условием: ИБ участвует не всегда, а только при конфликте; и это отдельный актор со своей целью.

## Упражнение

<Exercise title="use case процесса Mover (перевод)">

В кейсе процесс перевода сотрудника отложен на волну 2 (BR-12). Нарисуйте use case для **Mover**: HRMS сообщает о переводе, IdM пересчитывает роли по новой должности и отзывает права прежней; прежний руководитель может подтвердить сохранение отдельных прав на переходный период; новый руководитель запрашивает дополнительные доступы.

<Fragment slot="solution">

<PlantUmlDiagram file="howto/use-case-mover-solution.puml" source="site" title="Mover — одно из возможных решений" />

- **HRMS и Таймер — акторы-системы:** событие о переводе и плановый отзыв прав.
- **include** «Пересчитать роли» — всегда при переводе.
- **extend** «Подтвердить сохранение прав» → «Отозвать права» — только если права нужны на переходный период.
- **Повторное использование:** «Запросить дополнительный доступ» и «Согласовать заявку» — те же прецеденты, что в Joiner (UC-03, UC-04).
