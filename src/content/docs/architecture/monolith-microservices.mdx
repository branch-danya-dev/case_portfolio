<Brief>

**Монолит** — одно разворачиваемое приложение, обычно с одной БД: просто разрабатывать и отлаживать, но релизы и масштабирование — целиком. **Микросервисы** — независимо разворачиваемые сервисы вокруг бизнес-возможностей, **каждый со своими данными**: независимые команды и релизы ценой сетевых вызовов, распределённых данных и сложной эксплуатации.
**Модульный монолит** — разумная середина и частый старт.
Для аналитика выбор архитектуры меняет требования: появляются контракты между сервисами, согласованность без общих транзакций, сверки и сценарии частичных отказов.

</Brief>

## Когда применять

| Подходит монолит / модульный монолит | Подходят микросервисы |
|---|---|
| Одна-две команды | Много команд, которые мешают друг другу общим релизом |
| Предметная область ещё изучается — границы неясны | Границы предметной области понятны и устойчивы |
| Нет зрелой автоматизации развёртывания и мониторинга | Есть CI/CD, мониторинг, трассировка, дежурства |
| Нагрузка и требования к частям системы похожи | Части с разной нагрузкой, доступностью, циклом изменений |

## Как делать

Роль аналитика при обсуждении архитектуры:

<Steps>

1. **Дайте вход:** объёмы и пики, требования к доступности по частям системы, частота изменений разных функций, ограничения ИБ.

2. **Разметьте предметную область:** какие данные и правила тесно связаны (один модуль), а какие можно разделить. Граница сервиса = граница данных, которыми он владеет.

3. **Для каждой границы — контракт:** API или события, владелец, совместимость.

4. **Для операций через несколько сервисов** — требования к согласованности: что допустимо видеть в промежутке, какие компенсации при ошибке, нужна ли сверка.

5. **Сценарии частичных отказов:** что работает, если один сервис недоступен.

6. **Решение — в ADR** с вариантами и последствиями.

</Steps>

## Нотация: сравнение

| | Монолит | Модульный монолит | Микросервисы |
|---|---|---|---|
| Развёртывание | Целиком | Целиком | Каждый сервис независимо |
| Данные | Общая БД | Общая БД, но модули владеют своими таблицами | БД на сервис |
| Транзакции | Локальные, ACID | Локальные, ACID | Между сервисами — саги, события, сверки |
| Вызовы между частями | Внутри процесса | Внутри процесса через интерфейсы модулей | По сети: тайм-ауты, повторы, версии API |
| Команды | Мешают друг другу на больших масштабах | Можно разделить по модулям | Независимы, если границы верны |
| Эксплуатация | Простая | Простая | Сложная: много развёртываний, мониторинг, трассировка |
| Риск | «Большой ком грязи» без границ | Нарушение границ модулей со временем | «Распределённый монолит»: сервисы, которые нельзя выпустить по отдельности |

**Закон Конвея:** структура системы повторяет структуру коммуникаций организации. Границы сервисов, которые не совпадают с границами команд, обычно со временем «съезжают».

## Пример из кейса IDM-JOINER

<CaseRef href="/case/03-architecture/containers/" id="C4 L2">Контейнеры решения кейса</CaseRef> — не классические микросервисы, а несколько отдельно разворачиваемых частей вокруг ядра:

| Контейнер | Почему отдельно |
|---|---|
| Обработчик кадровых событий | Своя ответственность (чтение топика, валидация, идемпотентность, DLQ), можно перезапускать независимо от ядра |
| Сервис провижининга | Коннекторы, повторы, ручные задачи — частые изменения при подключении новых систем (NFR-10) |
| Журнал аудита | Неизменяемое хранилище с особыми требованиями к хранению и доступу |
| Адаптер АБС | Другая команда — закон Конвея в действии (<CaseRef href="/case/03-architecture/adr/#adr-003" id="ADR-003">ADR-003</CaseRef>) |

Ядро IdM при этом остаётся единым: идентичности, роли, SoD и заявки тесно связаны данными и правилами, делить их на сервисы при объёмах кейса (до 300 событий в день) — лишняя сложность.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Микросервисы «потому что модно» | Сложность без выгоды | Аргументы от команд, нагрузки, изменений |
| Общая БД у «микросервисов» | Распределённый монолит: изменения схемы ломают всех | Сервис владеет своими данными |
| Границы по техническим слоям (сервис «БД», сервис «UI») | Любое изменение затрагивает все сервисы | Границы по бизнес-возможностям |
| Требования «транзакция между сервисами» | Невыполнимо или очень дорого | Саги, события, сверки |
| Не описаны частичные отказы | Каскадные сбои | Тайм-ауты, повторы, деградация функций |
| Цепочки синхронных вызовов через 5 сервисов | Доступность = произведение доступностей | Асинхронность, кэш, укрупнение границ |
