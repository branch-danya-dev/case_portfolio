<Brief>

**ADR** (Architecture Decision Record) — короткая запись об **одном** значимом архитектурном решении: **контекст** (почему вопрос возник), **варианты**, **решение** и **последствия**.
Через год никто не вспомнит, почему выбрали Kafka, а не REST. ADR отвечает «почему» и не даёт бесконечно пересматривать решённое.
Решение принимает архитектор; аналитик даёт контекст из требований и фиксирует последствия для требований.

</Brief>

## Когда применять

| Писать ADR | Не нужно |
|---|---|
| Решение дорого изменить позже: технология интеграции, модель данных, способ развёртывания | Мелкие решения внутри модуля, которые легко поменять |
| Были реальные альтернативы и спор | Решение очевидно и стандартно для компании |
| Решение влияет на несколько команд или на требования | Выбор библиотеки форматирования дат |
| Решение принято вопреки «очевидному» варианту | — |

## Как делать

<Steps>

1. **Контекст:** какие требования, ограничения и факты делают вопрос важным. Со ссылками на БТ, НФТ, требования ИБ, ограничения устава.

2. **Варианты** — минимум два реальных, с плюсами и минусами относительно требований.

3. **Решение** — одно предложение «Выбираем вариант … потому что …».

4. **Последствия** — что изменится: новые требования, статусы, интеграции, риски, работы. Это самая ценная для аналитика часть.

5. **Статус и дата;** при замене — ссылка на новый ADR, старый не удаляется.

6. **Храните рядом с документацией** (Confluence или git, docs-as-code), нумеруйте по порядку.

</Steps>

## Нотация: шаблон и статусы

```markdown title="Шаблон ADR"
## ADR-NNN. <Короткое название решения>

**Статус:** Предложено | Принято | Устарело | Заменено ADR-MMM
**Дата:** ДД.ММ.ГГГГ · **Участники:** <архитектор, СА, ИБ…>

**Контекст.** <Что требуется и почему вопрос возник. Ссылки: BR-…, NFR-…, SEC-…, ограничения.>

**Варианты.**

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| A. … | … | … |
| B. … | … | … |

**Решение.** <Выбираем вариант … потому что …>

**Последствия.** <Новые требования, компоненты, статусы, интеграции, риски, работы.>
```

| Статус | Смысл |
|---|---|
| Предложено (Proposed) | На обсуждении |
| Принято (Accepted) | Действует |
| Устарело (Deprecated) | Больше не применяется |
| Заменено (Superseded) | Есть новый ADR, ссылка на него |

Формат популяризовал Майкл Найгард (2011): название, статус, контекст, решение, последствия. Распространены расширенные шаблоны (например, MADR) с явным разделом вариантов.

## Пример из кейса IDM-JOINER

<CaseRef href="/case/03-architecture/adr/" id="ADR">Три ADR кейса</CaseRef>:

| ADR | Решение | Последствия для требований |
|---|---|---|
| <CaseRef href="/case/03-architecture/adr/#adr-001" id="ADR-001">ADR-001</CaseRef> Получение кадровых событий | Kafka + ежедневная сверка полным срезом | Идемпотентность (FR-03), DLQ (FR-02), AsyncAPI-контракт, сверка (FR-05) |
| <CaseRef href="/case/03-architecture/adr/#adr-002" id="ADR-002">ADR-002</CaseRef> Момент создания учётных записей | Заранее, за 3 рабочих дня, в заблокированном состоянии | Статус CREATED_DISABLED, плановая активация, удаление при отмене (FR-18), учёт часового пояса (FR-08) |
| <CaseRef href="/case/03-architecture/adr/#adr-003" id="ADR-003">ADR-003</CaseRef> Интеграция с АБС | REST-адаптер над внутренними функциями АБС | Отдельная команда в критическом пути (риск), контракт описывает СА проекта, адаптер переиспользуется в волнах 2–3 |

Что хорошо в ADR кейса:

- **Контекст ссылается на требования:** ADR-001 — BR-01, NFR-05 и ограничение «команда HRMS — не более 2 спринтов».
- **Отвергнутые варианты записаны** с минусами: REST от HRMS, опрос HRMS, прямая запись в БД АБС, RPA.
- **Последствия превращены в требования** — по ним видно, откуда взялись FR-02, FR-03, FR-18 и статус CREATED_DISABLED.

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Записано только решение | Через год непонятно, почему отказались от альтернатив | Варианты с плюсами и минусами |
| Нет последствий | Решение не превращается в требования и работы | Раздел «Последствия» со ссылками на ФТ, НФТ |
| Контекст без ссылок на требования | Нельзя проверить, актуально ли решение | Ссылки на BR, NFR, SEC, ограничения |
| Удалить устаревший ADR | Теряется история | Статус «Заменено», ссылка на новый |
| Один ADR на десять решений | Невозможно ссылаться и пересматривать | Один ADR — одно решение |
| ADR пишут после реализации «для галочки» | Нет обсуждения вариантов | В момент принятия решения |
