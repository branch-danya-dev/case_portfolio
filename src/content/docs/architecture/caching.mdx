<Brief>

**Кэш** хранит копию данных ближе к потребителю: ответ быстрее, источник разгружен. Цена — **данные могут быть устаревшими**.
Поэтому главный вопрос для аналитика не «какой кэш», а **«насколько данные могут устаревать и что тогда случится»**: справочник подразделений можно кэшировать на часы, права доступа и балансы — нельзя или очень осторожно.
Стратегии: **cache-aside** (самая распространённая), read-through, write-through, write-behind; сброс — по сроку (TTL) или по событию.

</Brief>

## Когда применять

| Кэшировать | Не кэшировать / осторожно |
|---|---|
| Справочники и настройки, которые редко меняются | Права доступа, статусы согласований — решения по устаревшим данным опасны |
| Тяжёлые вычисления и агрегаты для отчётов | Балансы, остатки, лимиты |
| Ответы медленных внешних систем, если допустима задержка | Персональные данные без контроля срока хранения |
| Статические ресурсы (файлы, страницы) — HTTP-кэш, CDN | Данные, где пользователь сразу проверяет результат своего действия |

## Как делать

<Steps>

1. **Найдите кандидатов:** что читается часто, меняется редко, дорого получать.

2. **Допустимое устаревание** для каждого: секунды, минуты, часы — это и есть TTL.

3. **Что сбрасывает кэш:** событие изменения в источнике, действие пользователя, время.

4. **Что видит пользователь** при устаревших данных и сразу после своего изменения («прочитать свою запись»).

5. **Поведение при недоступности источника:** отдавать устаревшее значение или ошибку.

6. **Ограничения ИБ:** что нельзя кэшировать, сколько можно хранить персональные данные.

</Steps>

## Нотация: стратегии и HTTP-кэш

| Стратегия | Как работает | Плюсы | Минусы |
|---|---|---|---|
| Cache-aside | Приложение ищет в кэше; при промахе читает источник и кладёт в кэш | Просто, кэшируется только нужное | Первый запрос медленный; инвалидация на приложении |
| Read-through | Кэш сам загружает данные из источника при промахе | Логика загрузки в одном месте | Нужна поддержка кэшем |
| Write-through | Запись в кэш и синхронно в источник | Кэш всегда актуален | Запись медленнее |
| Write-behind | Запись в кэш, в источник — позже асинхронно | Быстрая запись | Риск потери данных при сбое |

| Понятие | Смысл |
|---|---|
| TTL | Время жизни записи в кэше |
| Инвалидация | Принудительный сброс при изменении данных |
| Вытеснение (LRU и др.) | Какие записи удалять при нехватке памяти |
| Промах / попадание (miss / hit) | Нет данных в кэше / есть; доля попаданий — главная метрика |
| «Шторм» (thundering herd) | Одновременный промах многих запросов → нагрузка на источник |

```http title="HTTP-кэширование: заголовки"
Cache-Control: max-age=3600            кэшировать час
Cache-Control: no-store                не кэшировать вообще (чувствительные данные)
Cache-Control: no-cache                кэшировать, но перед использованием проверять
ETag: "v42"                            версия ресурса
If-None-Match: "v42"   →   304 Not Modified   данные не изменились, тело не передаётся
```

## Пример из кейса IDM-JOINER

В документации кейса кэш явно не описан — при объёмах до 300 событий в день он не нужен для производительности. Но если бы IdM кэшировал данные, требования выглядели бы так:

| Данные | Можно кэшировать? | Почему |
|---|---|---|
| Справочник подразделений (часовой пояс, OU, `abs_branch_code`) | Да, TTL часы + сброс по изменению | Меняется редко; см. <CaseRef href="/case/04-integrations/data-mapping/" id="Маппинг">маппинг</CaseRef> |
| Каталог полномочий для портала | Да, минуты | Пользователь выбирает из каталога; задержка в несколько минут допустима |
| SoD-правила при проверке перед выдачей | **Нет** или только со сбросом по изменению | Проверка по устаревшим правилам — нарушение <CaseRef href="/case/05-security/security-requirements/#sec-02" id="SEC-02">SEC-02</CaseRef> |
| Статус подготовки доступов на портале | Короткий TTL или без кэша | Руководитель проверяет результат (<CaseRef href="/case/02-requirements/functional-requirements/#fr-23" id="FR-23">FR-23</CaseRef>) |
| Ответы API для руководителя | `no-store` | Персональные данные и права (SEC-10) |

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| Кэш без требования к устареванию | Пользователи видят старые данные, никто не знает, допустимо ли это | Допустимое устаревание для каждого типа данных |
| Кэшировать права и проверки безопасности | Решения по устаревшим правилам | Без кэша или со сбросом по изменению |
| Нет сброса по событию изменения | Ждать истечения TTL после важного изменения | Инвалидация по событию |
| Пользователь не видит своё изменение | Повторные действия, жалобы | «Прочитать свою запись» мимо кэша |
| Кэш как источник правды | Потеря данных при сбросе | Источник правды — только БД / мастер-система |
