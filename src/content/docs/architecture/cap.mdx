<Brief>

**CAP**: распределённая система при **разделении сети** (Partition) не может одновременно быть **согласованной** (Consistency — все видят последнюю запись) и **доступной** (Availability — каждый запрос получает ответ). Во время сбоя связи приходится выбирать: отказать (CP) или ответить, возможно, устаревшими данными (AP).
Разделение сети не выбирают — оно случается. Поэтому «выбрать два из трёх» — упрощение.
Для аналитика практический вывод: где важна строгая согласованность, где допустима **согласованность в конечном счёте**, с какой задержкой и что видит пользователь в промежутке.

</Brief>

## Когда применять

| Задуматься о CAP и согласованности | Не нужно |
|---|---|
| Данные живут в нескольких системах или узлах | Одна система с одной БД — там ACID-транзакции |
| Интеграции асинхронные: данные «доезжают» с задержкой | — |
| Распределённые хранилища, кэши, реплики | — |
| Требования вида «везде сразу» к данным из разных систем | — |

## Как делать

<Steps>

1. **Для каждого вида данных** решите: что хуже — показать устаревшее или не показать ничего / отказать в операции.

2. **Строгая согласованность** нужна, где решение по устаревшим данным недопустимо: деньги, права, уникальность (логины).

3. **Согласованность в конечном счёте** — там, где задержка допустима: отчёты, статусы, справочники в смежных системах. Зафиксируйте допустимую задержку.

4. **Что видит пользователь** в промежутке: статус «в обработке», дата актуальности данных.

5. **Как сходятся данные:** события, повторы, сверка; кто разрешает конфликты.

</Steps>

## Нотация

| Буква | Свойство | Смысл |
|---|---|---|
| C | Consistency — согласованность | Любое чтение возвращает последнюю запись (линеаризуемость) |
| A | Availability — доступность | Каждый запрос к работающему узлу получает ответ (не ошибку) |
| P | Partition tolerance — устойчивость к разделению | Система продолжает работать при потере связи между узлами |

| Выбор при разделении | Поведение | Где уместно |
|---|---|---|
| CP | Часть запросов отклоняется, но данные не расходятся | Платежи, уникальность, права |
| AP | Отвечаем всегда, данные могут временно расходиться | Каталоги, ленты, статусы, кэши |

**PACELC** уточняет CAP: при разделении (P) — выбор между A и C; иначе (Else) — выбор между задержкой (Latency) и согласованностью (C). Даже без сбоев строгая согласованность стоит времени — синхронная репликация медленнее.

Теорему сформулировал Эрик Брюер (2000), формально доказали Сет Гилберт и Нэнси Линч (2002).

| Модель согласованности | Смысл для пользователя |
|---|---|
| Строгая | Сразу после записи все видят новое значение |
| Чтение своих записей (read-your-writes) | Я сразу вижу своё изменение, другие — чуть позже |
| В конечном счёте (eventual) | Через некоторое время все увидят одно и то же |

## Пример из кейса IDM-JOINER

IdM — система, где данные о доступах живут в нескольких местах одновременно: в реестре IdM, в AD, в АБС, в HRMS. Это **согласованность в конечном счёте** между системами:

- **Кадровые данные** приходят событиями — IdM узнаёт о приёме с задержкой; пропущенное событие подтянет **сверка** (<CaseRef href="/case/02-requirements/functional-requirements/#fr-05" id="FR-05">FR-05</CaseRef>).
- **Учётные записи** в целевых системах догоняют реестр IdM через задачи провижининга с повторами; пока задача в MANUAL, статус в IdM и в АБС расходится — и это видно по статусу задачи.
- **Строгая согласованность там, где нужна:** уникальность логина проверяется по действующим учётным записям AD и зарезервированным логинам до назначения (FR-06); SoD-проверка — до выдачи полномочия (<CaseRef href="/case/05-security/security-requirements/#sec-02" id="SEC-02">SEC-02</CaseRef>).
- **Журнал аудита для SIEM** — AP-подход: при недоступности шины события буферизуются и «догоняют» позже (<CaseRef href="/case/04-integrations/integration-map/#int-09" id="INT-09">INT-09</CaseRef>).

## Типичные ошибки

| Ошибка | Чем плохо | Как правильно |
|---|---|---|
| «Выбираем CA» для распределённой системы | Разделение сети всё равно случится, поведение не определено | Определить поведение при разделении |
| Требование «данные везде сразу» для разных систем | Невыполнимо без потери доступности | Допустимая задержка + сверка |
| Не показать пользователю, что данные в процессе | Повторные действия, дубли, жалобы | Статусы «в обработке», дата актуальности |
| Строгая согласованность для всего | Медленно и хрупко | Строгая — только для критичного |
| Нет механизма схождения | Расхождения накапливаются | События, повторы, сверка, владелец конфликтов |
