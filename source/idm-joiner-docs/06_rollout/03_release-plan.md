# План релиза 1.0

Версия 1.0 · Статус: Согласован · Автор: Руководитель проекта, СА (при участии ведущего разработчика IdM, команды АБС и сопровождения)

План внедрения (`02_rollout-plan.md`) отвечает на вопрос «кому и когда включаем автоматизацию». Этот документ отвечает на вопрос **«как выложить релиз в продуктив и не сломать то, что уже работает»**. В релиз 1.0 входят изменения IdM, новый адаптер АБС и новая публикация кадровых событий из HRMS. Выкладка — за неделю до пилота: так останется время на финальную загрузку данных и проверки, а включение пилотных подразделений будет отдельным решением.

## 1. Среды

| Среда | Зачем | Кто работает | Целевые системы | Данные |
|---|---|---|---|---|
| DEV | Разработка и отладка | Разработчики | Заглушки по контрактам (`04_integrations/api/`) | Синтетические |
| TEST | Интеграционное и системное тестирование | QA | Тестовые AD, Exchange, тестовый адаптер на тестовой АБС, тестовый топик Kafka; SMS — заглушка | Синтетические |
| UAT | Приёмочные испытания по ПМИ (`07_testing/01_test-program.md`) | QA, бизнес, ИБ | Как в TEST; SMS — только на номера участников испытаний | Обезличенный срез справочников и сотрудников |
| PREPROD | Нагрузочный тест (TC-19), репетиция выкладки, миграции и отката | Разработка, сопровождение | Отдельные экземпляры, конфигурация как в PROD | Обезличенный срез объёмом как в PROD |
| PROD | Промышленная работа | Сопровождение (L2), пользователи | Боевые системы | Реальные |

Правила:

- **Одна сборка на все среды.** На PROD выкладывается та же версия, что прошла UAT и PREPROD; среды отличаются только конфигурацией и секретами.
- **Реальные ПДн — только в PROD.** В UAT и PREPROD — обезличенный срез (NFR-09, SEC-09).
- **Стенд UAT заморожен** на время испытаний: доработки выкладываются туда только по решению руководителя испытаний.

## 2. Что отличается в конфигурации

| Параметр | DEV / TEST | UAT / PREPROD | PROD |
|---|---|---|---|
| Адреса целевых систем | Заглушки, тестовые системы | Тестовые системы | Боевые системы |
| Флаги подразделений | Включены все | Включены участники испытаний | Выключены все; включаются по решению go/no-go |
| Ежедневная сверка (FR-05) | Запуск вручную | 02:00 | 02:00 |
| SMS-шлюз (INT-07) | Заглушка | Номера участников испытаний | Боевой шлюз |
| Задачи в ServiceDesk (INT-06) | Заглушка | Тестовая очередь | Боевые очереди администраторов |
| Уровень логирования | DEBUG | INFO | INFO; без ПДн в логах |
| Получатели алертов | Нет | Команда разработки | Дежурный L2 (`08_operations/03_monitoring-alerting.md`) |

Конфигурация хранится в репозитории рядом с кодом, по файлу на среду. Изменение конфигурации PROD — такое же изменение, как код: через запрос на изменение и ревью.

## 3. Секреты

| Секрет | Для чего |
|---|---|
| Учётные данные сервисной учётной записи AD | Коннектор AD (INT-03) |
| Учётные данные для Exchange | Коннектор Exchange (INT-04) |
| Клиентский сертификат mTLS и `client_secret` | Вызовы адаптера АБС (INT-05) |
| Ключ API SMS-шлюза | Отправка OTP (INT-07) |
| Учётные данные БД IdM | Сервисы IdM |

- Секреты хранятся только в хранилище секретов (NFR-08, SEC-07), **отдельно для каждой среды**; в репозитории и конфигурации — только имя секрета.
- Секреты PROD заводит сопровождение; разработчики их не видят.
- Проверка перед выкладкой: все секреты PROD заведены, срок действия сертификата mTLS — не меньше 3 месяцев.

## 4. Скрипты миграции БД

Схема БД IdM меняется версионированными скриптами: каждый скрипт применяется один раз, номер последней применённой версии хранится в самой БД.

| Скрипт | Что делает | Совместим со старой версией IdM |
|---|---|---|
| V1.0.1 | Новые таблицы `hr_event_inbox` и `reserved_login` | Да — старая версия их не читает |
| V1.0.2 | Новые столбцы `org_unit.timezone`, `org_unit.abs_branch_code` (допускают пустое значение) | Да — старая версия их не видит |
| V1.0.3 | Индексы для сверки и поиска задач | Да |

- В релизе 1.0 скрипты **только добавляют**: ничего не удаляется и не переименовывается. Поэтому при откате приложения схему возвращать не нужно.
- Скрипты схемы и загрузка данных (`01_migration-strategy.md`) — разные вещи. Скрипты создают структуру при выкладке, загрузка заполняет её данными отдельным шагом.

## 5. Порядок выкладки

| Шаг | Что | Почему в этом месте |
|---|---|---|
| 1 | Скрипты миграции БД IdM | Новая версия IdM ожидает новые таблицы; старая их не замечает |
| 2 | Адаптер АБС 1.0 (команда АБС) | IdM вызывает адаптер: поставщик (provider) API выкладывается раньше потребителя (consumer) |
| 3 | Топик `hr.employee.events.v1` и DLQ (команда интеграции) | Обработчику событий нужно, откуда читать |
| 4 | Ядро IdM, сервис провижининга, планировщик, портал — при выключенных флагах | Код на месте, но для сотрудников ничего не меняется |
| 5 | Обработчик кадровых событий | Начинает читать топик; по выключенным подразделениям события сохраняются, провижининг не выполняется |
| 6 | Публикация кадровых событий в HRMS (команда HRMS) | События идут уже в готовую систему |
| 7 | Финальная загрузка данных и сверка (`01_migration-strategy.md`, шаг 4) | Нужны новые таблицы и работающая сверка |
| 8 | Проверка после выкладки (раздел 9) | — |

Обработчик событий (шаг 5) выкладывается раньше публикации в HRMS (шаг 6) по тому же правилу, что адаптер раньше IdM: **первым выкладывается тот, кто должен понимать новое**. Если HRMS начнёт публиковать раньше, события будут копиться в топике — это допустимо, только если срок хранения сообщений в топике больше, чем пауза между шагами.

## 6. Флаги и поэтапное включение

- Автоматизация включается флагом на уровне подразделения (`02_rollout-plan.md`, раздел 2). После выкладки все флаги выключены.
- Флаги пилотных подразделений включаются только после решения go/no-go (раздел 8).
- Флаги переключает сопровождение (L2) по заявке руководителя проекта (`08_operations/01_support-model.md`).
- Флаги удаляются из кода после промышленной эксплуатации — отдельным изменением.

## 8. Go/no-go

Решение принимают руководитель проекта, владелец продукта IdM, CISO и руководитель сопровождения — за день до включения пилотных подразделений.

| Критерий | Подтверждает |
|---|---|
| ПМИ: все тесты приоритета M пройдены, нет дефектов критичности 1–2 | QA |
| Нагрузочный тест TC-19 пройден на PREPROD | QA |
| Выкладка и откат отрепетированы на PREPROD | Разработка |
| Финальная загрузка: ≥ 98% учётных записей AD сопоставлены | СА, администраторы |
| Проверка после выкладки на PROD пройдена | Разработка, сопровождение |
| Алерты настроены, runbook опубликован, дежурный L2 назначен | Сопровождение |
| L1 и администраторы обучены, release notes разосланы | БА |
| Нет открытых инцидентов P1 и P2 по смежным системам (AD, АБС, HRMS) | Сопровождение |

Если хотя бы один критерий не выполнен — no-go: включение переносится, а не выполняется «с оговорками».

## 9. Проверка после выкладки (smoke test)

Короткая проверка того, что система жива и связана с соседями. Учётные записи реальных сотрудников при проверке не создаются.

1. Все компоненты IdM запущены, версии совпадают с release notes.
2. Скрипты БД применены: версия схемы — V1.0.3.
3. Коннекторы подключаются к AD, Exchange и адаптеру АБС: чтение существующей служебной учётной записи (`GET /users/{login}` для АБС).
4. Обработчик событий подключён к топику, отставание группы потребителей не растёт.
5. Тестовое событие HIRE для служебного тестового подразделения с включённым флагом проходит до задач провижининга; созданные учётные записи заблокированы и удаляются по процедуре сопровождения.
6. Алерт доходит до дежурного L2 (тестовое срабатывание).
7. Портал открывается через SSO, руководитель видит только подчинённых (SEC-10).

## 10. Откат

| Ситуация | Действие | Сколько времени |
|---|---|---|
| Ошибки после включения флагов, но система работает | Выключить флаги, вернуться к заявкам в ServiceDesk (`02_rollout-plan.md`) | Минуты |
| Новая версия IdM неработоспособна | Вернуть предыдущую версию приложений IdM; схему БД не трогать — скрипты аддитивные | До 1 часа |
| Адаптер АБС неработоспособен | Команда АБС возвращает свою версию; задачи по АБС уходят в RETRY_WAIT и MANUAL по FR-16 | По регламенту команды АБС |

Что откатом не возвращается: созданные учётные записи (остаются и сверяются вручную), отправленные SMS и письма, загруженные данные. Поэтому основной способ отката — **флаг, а не возврат версии**.

## 11. Мониторинг после релиза

Первые две недели пилота — **усиленное сопровождение (hypercare)**: команда проекта и сопровождение вместе разбирают каждое отклонение.

| Что смотрим | Когда | Норма |
|---|---|---|
| Готовность доступов к 09:00 первого дня (NFR-02) | Каждое утро по поясам пилота | ≥ 95% |
| Задачи MANUAL и RETRY_WAIT по системам | Ежедневно | Каждая задача MANUAL разобрана |
| DLQ кадровых событий | Ежедневно | Пусто или разобрано |
| Расхождения ежедневной сверки | Ежедневно | Разобраны |
| Обращения в ServiceDesk по пилотным подразделениям | Ежедневно | Нет повторяющихся |

Hypercare завершается, когда метрики пилота держатся неделю без отклонений; дальше — обычная модель сопровождения.
