# Функциональные требования (ФТ)

Версия 1.0 · Статус: Согласован · Автор: Системный аналитик · Утверждает: HRD (бизнес-смысл), архитектор (реализуемость)

Функциональное требование описывает, **что должна делать система**. Хорошее ФТ атомарно (одно действие), проверяемо (можно написать тест), однозначно и трассируемо (есть ссылка на БТ).

Формулировка-шаблон: «Система должна <действие> <объект> <условие/ограничение>».

## 2. Детализация

### 2.1. Правило генерации логина (FR-06)

1. Фамилия, имя и отчество транслитерируются по ICAO Doc 9303 (как в загранпаспорте РФ): ж → zh, х → kh, ц → ts, ч → ch, ш → sh, щ → shch, ы → y, ъ → ie, ь → не передаётся, ю → iu, я → ia, й → i, ё → e.
2. Формат: `<фамилия>.<первая буква имени><первая буква отчества>` в нижнем регистре. Без отчества — `<фамилия>.<первая буква имени>`.
3. Дефис в фамилии сохраняется, пробелы и апострофы удаляются.
4. Длина — не более 20 символов (ограничение `sAMAccountName` в AD). При превышении усекается фамилия.
5. Логин проверяется на уникальность среди действующих учётных записей AD и зарезервированных логинов. Логины уволенных резервируются на 12 месяцев и могут быть переиспользованы только тем же `personId` (BRL-05).
6. При совпадении добавляется суффикс 2…9: `ivanov.ap2`. Если все суффиксы заняты — задача в ServiceDesk администратору AD.

| ФИО | Логин | Комментарий |
|---|---|---|
| Иванов Алексей Петрович | `ivanov.ap` | Базовый случай |
| Иванов Андрей Павлович | `ivanov.ap2` | Коллизия |
| Щукина Юлия | `shchukina.i` | Нет отчества; Ю → iu → «i» |
| Константинопольский Ярослав Юрьевич | `konstantinopolski.ii` | Усечение до 20 символов |
| Римский-Корсаков Николай Андреевич | `rimskii-korsakov.na` | Дефис сохраняется |

### 2.2. Расчёт сроков (FR-07, FR-08)

- Рабочие дни считаются по производственному календарю банка (справочник в IdM, обновляется ежегодно).
- Часовой пояс берётся из справочника подразделений (`orgUnit.timezone`).
- Пример: дата выхода — понедельник 15.03.2027, офис в Екатеринбурге (UTC+5). Создание — среда 10.03.2027; активация — 15.03.2027 в 07:00 по Екатеринбургу (05:00 МСК).

### 2.3. Политика повторов (FR-16)

| Тип ошибки | Примеры | Повторять? | Действие после неудачи |
|---|---|---|---|
| Техническая | Таймаут, HTTP 5xx, 429, недоступность сети | Да: всего 3 попытки — первая и 2 повтора через 1 и 5 минут | Задача в ServiceDesk группе администраторов системы |
| Бизнес-ошибка | HTTP 4xx (кроме 429): неверные данные, нет подразделения в справочнике АБС | Нет | Сразу задача в ServiceDesk с текстом ошибки |

Каждая операция провижининга передаёт ключ идемпотентности (`provisioningTaskId`), поэтому повтор после таймаута не создаёт дублей в целевой системе.

### 2.4. Реакции на изменения до выхода (FR-18)

| Событие | Состояние учётных записей | Реакция IdM |
|---|---|---|
| `HIRE_CHANGED`: изменена дата выхода | Ещё не созданы | Перепланировать создание |
| | Созданы, заблокированы | Перепланировать активацию; если новая дата ближе 3 дней — ничего больше |
| | Уже активированы | Отклонить событие, создать инцидент HR (сотрудник уже вышел) |
| `HIRE_CHANGED`: изменены должность или подразделение | Ещё не созданы | Пересчитать роли |
| | Созданы, заблокированы | Пересчитать роли, выдать недостающие и отозвать лишние полномочия |
| `HIRE_CANCELLED` | Ещё не созданы | Отменить план; идентичность → `CANCELLED` |
| | Созданы, заблокированы | Удалить учётные записи, отменить задачи ServiceDesk; идентичность → `CANCELLED` |
| | Уже активированы | Отклонить событие, создать инцидент (это увольнение, процесс Leaver — волна 2) |
