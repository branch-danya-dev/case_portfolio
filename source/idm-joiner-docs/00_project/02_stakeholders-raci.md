# Реестр стейкхолдеров и матрица ответственности (RACI)

Версия 1.0 · Статус: Согласован · Владелец: Руководитель проекта

## 1. Реестр стейкхолдеров

| Стейкхолдер | Интерес в проекте | Влияние | Интерес | Как работаем |
|---|---|---|---|---|
| Директор по ИТ (спонсор) | Снижение нагрузки на ИТ, сроки и бюджет | Высокое | Высокий | Управляющий комитет раз в месяц |
| Директор по персоналу (бизнес-заказчик) | Опыт нового сотрудника в первый день | Высокое | Высокий | Согласование БТ и TO-BE, демо |
| CISO / Департамент ИБ | Минимальные привилегии, SoD, аудит | Высокое | Высокий | Согласование ролевой модели, требований ИБ, архитектуры |
| HR-специалисты (кадровое администрирование) | Не добавить себе работы, своевременные приказы | Среднее | Средний | Интервью, обучение, регламент |
| Руководители подразделений | Сотрудник работает с первого дня | Среднее | Высокий | Интервью, пилот, обратная связь |
| Владельцы ресурсов (АБС, СЭД) | Контроль над тем, кто получает права в их системах | Высокое | Средний | Согласование ролей и каталога полномочий |
| Администраторы AD / Exchange | Меньше рутины, но контроль над коннекторами | Среднее | Высокий | Технические требования, тестирование |
| Администраторы АБС | Безопасность адаптера, нагрузка на АБС | Высокое | Средний | Согласование API адаптера |
| Команда HRMS (1С) | Доработка публикации событий | Среднее | Низкий | Интеграционные требования, ограниченное окно |
| Команда интеграции (шина Kafka) | Стандарты топиков и схем | Среднее | Низкий | Согласование AsyncAPI-контракта |
| Внутренний аудит | Проверяемость выдачи прав | Среднее | Средний | Требования к журналу и отчётам |
| Архитектурный комитет | Соответствие целевой архитектуре банка | Высокое | Низкий | Защита архитектуры и ADR |
| Новые сотрудники | Работать с первого дня | Низкое | Высокий | Через HR и руководителей |

> Колонки «Влияние» и «Интерес» — это матрица Менделоу: высокое влияние + высокий интерес → управлять плотно; высокое влияние + низкий интерес → держать удовлетворёнными (архитектурный комитет); низкое влияние + высокий интерес → информировать.

## 2. Роли проектной команды

| Роль | Зона ответственности |
|---|---|
| Руководитель проекта (РП) | Сроки, бюджет, риски, коммуникация, устав |
| Бизнес-аналитик (БА) | AS-IS, TO-BE, бизнес-требования, регламент |
| Системный аналитик (СА) | ФТ, НФТ, use case, ролевая модель (техническая часть), модель данных, статусы, интеграции, API, маппинг, трассировка |
| Архитектор решения | Контейнеры и компоненты, ADR, НФТ совместно с СА |
| Инженер ИБ | Требования ИБ, SoD-правила, участие в ролевой модели |
| Разработка (команда IdM, команда адаптера АБС) | Реализация, технический дизайн |
| QA | ПМИ, тест-кейсы, приёмочные испытания |
| DevOps / эксплуатация | Стенды, развёртывание, мониторинг |

> На малом проекте роли БА, СА и иногда РП совмещает один человек. Роль «СА» в банках часто включает и бизнес-анализ.

## 3. Матрица RACI по артефактам

R — делает, A — утверждает и отвечает за результат (один на строку), C — консультирует, I — информируется.

| Артефакт | РП | БА | СА | Архитектор | ИБ | Разработка | QA | Заказчик |
|---|---|---|---|---|---|---|---|---|
| Устав | R | C | C | C | C | I | I | A |
| Реестр стейкхолдеров | R/A | C | C | I | I | I | I | I |
| AS-IS / TO-BE | I | R | C | I | C | I | I | A |
| Бизнес-требования | I | R | C | I | C | I | I | A |
| Функциональные требования | I | C | R | C | C | C | C | A |
| Нефункциональные требования | I | I | R | A | C | C | C | I |
| Use case / бэклог | I | C | R | I | I | C | C | A |
| Ролевая модель | I | C | R | I | A | I | I | C |
| Модель данных, статусные модели | I | I | R | A | I | C | I | I |
| Контекст и контейнеры (C4) | I | I | C | R/A | C | C | I | I |
| Интеграции, API, маппинг | I | I | R | A | C | C | C | I |
| ADR | I | I | C | R/A | C | C | I | I |
| Требования ИБ | I | I | C | C | R/A | I | I | I |
| Стратегия миграции, план внедрения | A | C | R | C | C | C | C | I |
| ПМИ и тест-кейсы | I | I | C | I | C | I | R | A |
