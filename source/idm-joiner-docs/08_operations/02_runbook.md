# Runbook сопровождения IdM

Инструкции L2 для типовых ситуаций. Формат каждой процедуры: признаки → что проверить → действия → когда эскалировать. Если ситуация не описана — инцидент на L3 и отметка «дополнить runbook».

Общие правила:
- Любое действие в продуктиве — с записью в инциденте: что сделано, когда, кем.
- В логах и обращениях используем идентификаторы (`personId`, `taskId`, `eventId`, `traceId`), а не ФИО.
- Повторный запуск задач (replay) — только по RB-03.

### RB-01. Кадровое событие в DLQ

- **Признаки:** алерт ALR-03; инцидент от IdM группе сопровождения HRMS (FR-02).
- **Проверить:** сообщение в `hr.employee.events.v1.dlq` по `eventId`; причину отклонения в логах обработчика событий; дату выхода сотрудника.
- **Действия:** передать команде HRMS, какое поле некорректно. После исправления HRMS публикует событие заново с **новым** `eventId` — повторная публикация старого сообщения будет отброшена как дубль (FR-03).
- **Эскалация:** если до выхода сотрудника меньше 3 рабочих дней — P2.

### RB-02. Задачи провижининга в статусе MANUAL

- **Признаки:** алерт ALR-04 (рост MANUAL) или ALR-02 (ошибки коннектора); задачи в ServiceDesk у администраторов целевой системы.
- **Проверить:** сколько задач и по каким системам (`SELECT system, COUNT(*) … WHERE status = 'MANUAL' GROUP BY …`); тип ошибки в последней попытке — технический (5xx, 429, тайм-аут) или бизнес (4xx); единичный случай или массовый; доступна ли целевая система сейчас.
- **Действия:**
  - Единичная бизнес-ошибка — администратор выполняет задачу в ServiceDesk и закрывает её с `externalId` (FR-17), IdM получит webhook.
  - Массовая техническая ошибка — это не «много единичных задач», а инцидент P2: остановить создание новых ручных задач администраторами до выяснения причины, эскалировать на L3, после устранения причины — RB-03.
- **Эскалация:** более 3 задач MANUAL по одной системе за час — P2.

### RB-03. Повторный запуск задач (replay)

- **Когда:** причина технической ошибки устранена, задачи в MANUAL, а целевая система снова доступна.
- **Проверить до запуска:**
  1. Не выполнил ли администратор задачу вручную. Если выполнил — **не перезапускать**, а закрыть задачу в ServiceDesk с `externalId`: повтор с тем же `Idempotency-Key` для пользователя, созданного вручную, адаптер АБС вернёт 409 «логин занят другим пользователем».
  2. Не отменён ли приём (`HIRE_CANCELLED`) за время сбоя.
  3. Совпадает ли ключ идемпотентности: replay идёт с прежним `taskId`, а не с новой задачей.
- **Действия:** перевести задачи из MANUAL в SCHEDULED с обнулением счётчика попыток (функция сопровождения IdM), отменить соответствующие задачи в ServiceDesk, проверить результат через 10 минут.
- **Эскалация:** повторная ошибка после replay — L3.

### RB-04. Учётные записи не активированы в 07:00

- **Признаки:** алерт ALR-05; обращение руководителя «сотрудник не может войти».
- **Проверить:** статус задач ENABLE по сотруднику; часовой пояс подразделения (`orgUnit.timezone`, FR-08); работал ли планировщик.
- **Действия:** если планировщик не отработал — запустить активацию вручную функцией сопровождения; если задача ENABLE в MANUAL — RB-02.
- **Эскалация:** сотрудник уже на рабочем месте — P2 немедленно.

### RB-05. Сверка с HRMS нашла расхождение

- **Признаки:** алерт ALR-06; отчёт ежедневной сверки (FR-05).
- **Проверить:** тип расхождения — сотрудник есть в HRMS, нет в IdM (потеряно событие) или наоборот; есть ли событие в DLQ (RB-01).
- **Действия:** для потерянных событий сверка сама запускает обработку (FR-05); прочие расхождения — команде HRMS.
- **Эскалация:** более 5 расхождений за сутки — проблема (`05_problem-rca.md`).

### RB-06. Откат автоматизации для подразделения

- **Когда:** решение владельца продукта или дежурного руководителя по инциденту P1.
- **Действия:** выключить флаг автоматизации подразделения; сообщить руководителям, что заявки снова создаются в ServiceDesk по старому регламенту; уже созданные учётные записи сверить вручную (`06_rollout/02_rollout-plan.md`, раздел 2).
