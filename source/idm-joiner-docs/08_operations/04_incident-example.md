# Инцидент: учётные записи АБС не создаются

Учебный разбор инцидента после выхода в промышленную эксплуатацию. Сначала — данные, которые были у команды; затем — разбор так, как его делает СА: где ошибка → что ожидалось → какая система → дефект или контракт → какие данные пострадали → нужен ли повторный запуск.

## 2. Разбор

| Вопрос | Ответ | На чём основан |
|---|---|---|
| **Где ошибка** | Вызов `POST /users` из сервиса провижининга IdM в адаптер АБС: ответ 503 на три попытки подряд | Логи по `traceId`, ответ адаптера |
| **Что ожидалось** | Учётная запись АБС в статусе CREATED_DISABLED за 3 рабочих дня до выхода (FR-07) | ФТ, статусная модель учётной записи |
| **Что сделала IdM** | Ровно то, что требует FR-16: технические ошибки (503) повторила 3 раза через 1 и 5 минут, затем создала задачу в ServiceDesk. Дефекта кода IdM нет | FR-16, раздел 2.3 ФТ |
| **Какая система — источник** | Адаптер АБС 1.4.0: ограничение 30 запросов в минуту с блокировкой клиента на 120 секунд. IdM отправила 67 запросов в 09:00 (пакетное создание); повтор через минуту попал в блокировку, повтор через 5 минут — снова 37 запросов одновременно, больше лимита | Заметки к релизу, `detail` в ответе, таблица очереди |
| **Дефект или контракт** | Нарушен процесс изменения контракта: адаптер ввёл ограничение и стал использовать 503 (по контракту — «АБС недоступна») для превышения лимита, не изменив контракт и не предупредив потребителя. Плюс пробел в требованиях: нет НФТ на пропускную способность адаптера и правила учитывать `Retry-After` | Контракт, NFR, FR-16 |
| **DLQ** | Не участвует: события HIRE обработаны, проблема — на шаге провижининга. Проверено, чтобы исключить | DLQ, ALR-03 |
| **Какие данные пострадали** | 7 учётных записей АБС в FAILED, 7 задач MANUAL и 7 задач в ServiceDesk у администраторов АБС. Порчи или потери данных нет. Риск — сотрудники без АБС в первый день (цель G-01) | Запрос к БД |
| **Нужен ли повторный запуск** | Да, для тех, кого не создали вручную. Безопасен: повтор идёт с тем же `Idempotency-Key = taskId`. Для 2 сотрудников администраторы уже создали пользователей вручную — их не перезапускать (адаптер вернёт 409 «логин занят другим пользователем»), а закрыть задачи ServiceDesk с `externalId` (FR-17) | RB-03, контракт адаптера |

## 3. Хронология восстановления

| Время | Действие |
|---|---|
| 09:07 | ALR-02. Дежурный L2 по RB-02: 7 задач MANUAL по одной системе — массовый сбой, P2 |
| 09:20 | Администраторам АБС: задачи SD-8811…SD-8817 вручную не выполнять до выяснения. SD-8812 и SD-8815 уже выполнены |
| 09:45 | СА: поведение IdM соответствует FR-16; по `detail` и заметкам к релизу — ограничение частоты в адаптере 1.4.0. Эскалация на команду АБС (L3) |
| 10:40 | Команда АБС временно подняла лимит до 120 запросов в минуту |
| 11:00 | L2 по RB-03: 5 задач — повторный запуск; SD-8812 и SD-8815 закрыты с `externalId` (webhook принят, задачи DONE) |
| 11:20 | Все 7 учётных записей АБС — CREATED_DISABLED. Задачи SD-8811, SD-8813, SD-8814, SD-8816, SD-8817 отменены. Инцидент восстановлен |
| 11:30 | Открыта проблема PRB-01; HR и руководители уведомлены, что доступы будут к 17.06 |

## 4. Что вынесено в проблему

- Почему изменение адаптера не прошло через изменение контракта.
- Почему IdM создаёт все учётные записи одним пакетом в 09:00 и не учитывает `Retry-After`.
- Почему рост MANUAL не стал отдельным сигналом (алерта ALR-04 тогда не было).
