# Перевод между собственными счетами клиента

**Портфолио-кейс системного анализа банковской функциональности**

Самостоятельная концептуальная проработка функциональности перевода денежных средств между собственными счетами клиента мобильного банка.

Кейс демонстрирует подход к анализу требований, проектированию интеграционного взаимодействия, REST API, обработке ошибок, моделированию данных и формализации нефункциональных требований.

---

## 1. Контекст и задача

В мобильном банке необходимо предоставить клиенту возможность переводить денежные средства между принадлежащими ему счетами.

Пример сценария:

> Клиент переводит 10 000 ₽ с дебетового счёта на накопительный счёт.

Решение должно обеспечивать:

- получение доступных счетов клиента;
    
- проверку возможности проведения операции;
    
- создание перевода;
    
- выполнение списания и зачисления;
    
- защиту от повторной обработки запроса;
    
- получение актуального статуса;
    
- обработку ошибок;
    
- аудит операции.
    

---

## 2. Цель решения

Обеспечить безопасный и предсказуемый перевод денежных средств между счетами одного клиента без участия сотрудника банка.

Система должна:

- показывать только доступные клиенту счета;
    
- проверять бизнес-ограничения до создания операции;
    
- исключать повторное списание;
    
- обеспечивать выполнение операции в банковской АБС;
    
- предоставлять клиенту актуальный статус перевода;
    
- сохранять данные, необходимые для аудита и диагностики.

### В рамках решения

- проверка доступного остатка;
    
- проверка статуса счетов;
    
- проверка лимитов;
    
- создание и выполнение перевода;

## 4. Участники и системы

### Клиент

Авторизованный пользователь мобильного банка, инициирующий перевод.

### Mobile App

Клиентское приложение банка.

Отвечает за:

- отображение счетов;
    
- ввод параметров операции;
    
- подтверждение перевода;
    
- отображение результата.
    

### Banking Backend

Точка взаимодействия мобильного приложения с внутренними банковскими сервисами.

Отвечает за:

- авторизацию запроса;
    
- оркестрацию взаимодействия сервисов;
    
- возврат результата клиентскому приложению.
    

### Account Service

Предоставляет информацию о счетах:

- принадлежность клиенту;
    
- статус;
    
- валюту;
    
- доступный остаток;
    
- допустимые операции.
    

### Transfer Service

Управляет жизненным циклом перевода:

- регистрацией;
    
- идемпотентностью;
    
- статусами;
    
- взаимодействием с Core Banking;
    
- фиксацией результата.
    

### Core Banking System

Выполняет финансовую операцию списания и зачисления денежных средств.

---

## 5. Основной сценарий

1. Клиент открывает раздел перевода между своими счетами.
    
2. Mobile App запрашивает доступные счета.
    
3. Клиент выбирает счёт списания.
    
4. Клиент выбирает счёт зачисления.
    
5. Клиент вводит сумму.
    
6. Система выполняет предварительную проверку операции.
    
7. Клиент подтверждает перевод.
    
8. Banking Backend получает запрос на создание операции.
    
9. Transfer Service регистрирует перевод.
    
10. Core Banking выполняет списание и зачисление.
    
11. Transfer Service получает результат выполнения.
    
12. Перевод получает статус `COMPLETED`.
    
13. Клиентское приложение получает результат.
    
14. Клиенту отображаются актуальные остатки.
    

---

## 6. Бизнес-правила

**BR-01.** Счёт списания должен принадлежать авторизованному клиенту.

**BR-02.** Счёт зачисления должен принадлежать тому же клиенту.

**BR-03.** Счёт списания и счёт зачисления не могут совпадать.

**BR-04.** Оба счёта должны находиться в статусе, допускающем проведение операции.

**BR-05.** Сумма перевода должна быть больше нуля.

**BR-06.** Доступный остаток на счёте списания должен быть не меньше суммы перевода.

**BR-07.** Оба счёта должны быть открыты в валюте `RUB`.

**BR-08.** Сумма перевода не должна превышать установленный лимит.

**BR-09.** Повторная обработка одного пользовательского запроса не должна приводить к созданию второго перевода.

**BR-10.** Каждая зарегистрированная операция должна иметь уникальный идентификатор.

---

## 7. Функциональные требования

### FR-01. Получение счетов

Система должна возвращать список счетов авторизованного клиента, доступных для проведения перевода.

Для каждого счёта передаются:

- `accountId`;
    
- отображаемое название;
    
- маскированный номер;
    
- валюта;
    
- доступный остаток;
    
- статус.
    

### FR-02. Проверка перевода

Перед созданием операции система должна проверить:

- принадлежность счетов клиенту;
    
- доступность счетов;
    
- валюту;
    
- корректность суммы;
    
- доступный остаток;
    
- установленные лимиты.
    

### FR-03. Создание перевода

После подтверждения операции система должна создать перевод и присвоить ему уникальный `transferId`.

### FR-04. Идемпотентность

Повторный запрос с тем же `Idempotency-Key` не должен создавать новую операцию.

### FR-05. Выполнение перевода

Transfer Service должен передать операцию в Core Banking System.

### FR-06. Получение статуса

Система должна предоставлять возможность получить состояние операции по `transferId`.

### FR-07. История операций

Завершённый перевод должен быть доступен клиенту в истории операций.

## 8. REST API

### 8.1. Проверка возможности перевода

`POST /api/v1/transfers/validate`

#### Request

```
{
  "sourceAccountId": "acc-10001",
  "destinationAccountId": "acc-20002",
  "amount": 10000.00,
  "currency": "RUB"
}
```

#### Response

```
{
  "allowed": true,
  "currency": "RUB"
}
```

---

### 8.2. Создание перевода

`POST /api/v1/transfers`

#### Headers

```
Authorization: Bearer <token>
Idempotency-Key: 8d2e4c9a-58fc-4a1a-9dad-7bc7b4717352
```

#### Request

```
{
  "sourceAccountId": "acc-10001",
  "destinationAccountId": "acc-20002",
  "amount": 10000.00,
  "currency": "RUB"
}
```

#### Response

HTTP `202 Accepted`

```
{
  "transferId": "tr-987654",
  "status": "PROCESSING",
  "amount": 10000.00,
  "currency": "RUB",
  "createdAt": "2026-10-01T18:41:12Z"
}
```

---

### 8.3. Получение статуса операции

`GET /api/v1/transfers/{transferId}`

#### Response

```
{
  "transferId": "tr-987654",
  "status": "COMPLETED",
  "sourceAccountId": "acc-10001",
  "destinationAccountId": "acc-20002",
  "amount": 10000.00,
  "currency": "RUB",
  "createdAt": "2026-10-01T18:41:12Z",
  "completedAt": "2026-10-01T18:41:13Z"
}
```

## 9. Жизненный цикл операции

|Статус|Описание|
|---|---|
|`CREATED`|Перевод зарегистрирован|
|`PROCESSING`|Выполняется в банковской системе|
|`COMPLETED`|Успешно завершён|
|`FAILED`|Выполнение завершилось ошибкой|

Основной сценарий:

```
CREATED
   ↓
PROCESSING
   ↓
COMPLETED
```

Неуспешный сценарий:

```
CREATED
   ↓
PROCESSING
   ↓
FAILED
```

## 10. Обработка ошибок

### Недостаточно средств

HTTP `422 Unprocessable Entity`

```
{
  "code": "INSUFFICIENT_FUNDS",
  "message": "Недостаточно средств для выполнения перевода"
}
```

### Счёт недоступен

HTTP `422 Unprocessable Entity`

```
{
  "code": "ACCOUNT_UNAVAILABLE",
  "message": "Операции по счету недоступны"
}
```

### Нет доступа к счёту

HTTP `403 Forbidden`

```
{
  "code": "ACCOUNT_ACCESS_DENIED",
  "message": "Нет доступа к указанному счету"
}
```

### Превышен лимит

HTTP `422 Unprocessable Entity`

```
{
  "code": "TRANSFER_LIMIT_EXCEEDED",
  "message": "Превышен допустимый лимит операции"
}
```

### Некорректная сумма

HTTP `400 Bad Request`

```
{
  "code": "INVALID_AMOUNT",
  "message": "Сумма перевода должна быть больше нуля"
}
```

### Внутренняя ошибка

HTTP `500 Internal Server Error`

```
{
  "code": "INTERNAL_ERROR",
  "message": "Не удалось выполнить операцию"
}
```

## 11. Идемпотентность

Для создания перевода используется заголовок:

```
Idempotency-Key
```

Ключ генерируется клиентским приложением для каждой новой операции.

При повторном запросе с тем же ключом:

- новый перевод не создаётся;
    
- повторного списания не происходит;
    
- API возвращает существующую операцию.
    

Механизм защищает систему от повторного выполнения операции при:

- нестабильном соединении;
    
- HTTP retry;
    
- таймауте ответа;
    
- повторном действии пользователя.

## 12. Нефункциональные требования

### NFR-01. Безопасность

Операции должны быть доступны только авторизованному клиенту.

Принадлежность счетов должна проверяться серверной частью независимо от данных Mobile App.

### NFR-02. Целостность

Система не должна допускать неконтролируемое состояние, при котором списание выполнено, а зачисление не зарегистрировано.

### NFR-03. Идемпотентность

Повторная обработка одного пользовательского запроса не должна приводить к повторному движению денежных средств.

### NFR-04. Аудит

Для каждой операции должны сохраняться:

- `transferId`;
    
- `clientId`;
    
- `sourceAccountId`;
    
- `destinationAccountId`;
    
- сумма;
    
- валюта;
    
- статус;
    
- `Idempotency-Key`;
    
- время создания;
    
- время завершения;
    
- код ошибки при неуспешном выполнении.
    

### NFR-05. Производительность

API создания операции должно подтверждать принятие запроса не более чем за 2 секунды при штатной нагрузке.

### NFR-06. Наблюдаемость

Все основные этапы обработки операции должны логироваться с использованием `transferId` как корреляционного идентификатора.

## 13. Acceptance Criteria

### AC-01. Успешный перевод

**Given** клиент имеет два активных рублёвых счёта  
**And** на счёте списания достаточно средств  
**When** клиент создаёт перевод на 10 000 ₽  
**Then** операция получает статус `COMPLETED`  
**And** остаток исходного счёта уменьшается на 10 000 ₽  
**And** остаток целевого счёта увеличивается на 10 000 ₽.

### AC-02. Недостаточно средств

**Given** доступный остаток составляет 5 000 ₽  
**When** клиент пытается перевести 10 000 ₽  
**Then** операция не выполняется  
**And** система возвращает `INSUFFICIENT_FUNDS`.

### AC-03. Недоступный счёт

**Given** один из счетов недоступен для проведения операций  
**When** клиент инициирует перевод  
**Then** операция не выполняется  
**And** система возвращает `ACCOUNT_UNAVAILABLE`.

### AC-04. Повторный запрос

**Given** перевод уже создан с определённым `Idempotency-Key`  
**When** система получает повторный запрос с тем же ключом  
**Then** новая операция не создаётся  
**And** повторного списания не происходит  
**And** возвращается существующий перевод.
