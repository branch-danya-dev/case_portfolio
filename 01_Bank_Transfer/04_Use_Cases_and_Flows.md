# 04. Use Cases и сценарии

## 1. Назначение документа

Документ описывает пользовательские и системные сценарии функциональности перевода между собственными счетами.

---

## 2. Акторы

### Клиент

Авторизованный пользователь мобильного банка.

### Mobile App

Клиентское приложение, инициирующее запросы от имени пользователя.

### Banking Backend

Backend мобильного банка, предоставляющий внешний для приложения API.

### Account Service

Источник актуальной информации о счетах.

### Transfer Service

Компонент, отвечающий за жизненный цикл перевода.

### Core Banking System

Система, выполняющая финансовое отражение операции.

---

## 3. UC-01. Получение доступных счетов

**Основной актор:** Клиент  
**Цель:** получить перечень счетов, доступных для перевода.  
**Предусловия:** клиент авторизован.

### Основной сценарий

1. Клиент открывает экран перевода между своими счетами.
2. Mobile App запрашивает список счетов.
3. Banking Backend определяет идентификатор клиента.
4. Account Service возвращает счета клиента.
5. Система определяет доступность каждого счёта для списания и зачисления.
6. Mobile App отображает доступные счета.

### Альтернативы

**A1. Нет подходящих счетов**

Система возвращает пустой список либо соответствующий бизнес-результат. Mobile App сообщает, что перевод недоступен.

**A2. Account Service недоступен**

Запрос завершается технической ошибкой. Пользователю предлагается повторить попытку позднее.

---

## 4. UC-02. Предварительная проверка перевода

**Основной актор:** Клиент  
**Цель:** определить, может ли операция быть выполнена до подтверждения.

### Предусловия

- клиент авторизован;
- выбраны два счёта;
- указана сумма.

### Основной сценарий

1. Mobile App передаёт параметры операции.
2. Banking Backend проверяет формат запроса.
3. Система проверяет принадлежность счетов клиенту.
4. Проверяет различие счетов.
5. Проверяет статус и валюту счетов.
6. Проверяет сумму.
7. Проверяет доступный остаток.
8. Проверяет лимит.
9. Возвращает `allowed=true`.

### Альтернативные сценарии

При нарушении бизнес-правила возвращается `allowed=false` и соответствующий код причины.

Примеры:

- `INSUFFICIENT_FUNDS`;
- `ACCOUNT_ACCESS_DENIED`;
- `SAME_ACCOUNT`;
- `TRANSFER_LIMIT_EXCEEDED`.

---

## 5. UC-03. Создание и выполнение перевода

**Основной актор:** Клиент  
**Цель:** перевести денежные средства между собственными счетами.

### Предусловия

- клиент авторизован;
- параметры операции валидны;
- клиент подтвердил перевод.

### Триггер

Mobile App отправляет запрос создания перевода.

### Основной сценарий

1. Mobile App генерирует новый `Idempotency-Key`.
2. Mobile App отправляет запрос на создание перевода.
3. Banking Backend определяет авторизованного клиента.
4. Система повторно выполняет обязательные серверные проверки.
5. Transfer Service проверяет наличие операции с тем же idempotency key.
6. Transfer Service создаёт запись перевода со статусом `CREATED`.
7. Перевод переводится в `PROCESSING`.
8. Transfer Service инициирует выполнение в Core Banking System.
9. Core Banking System подтверждает успешное выполнение.
10. Transfer Service фиксирует `COMPLETED`.
11. Mobile App получает результат.
12. Клиенту отображается успешное завершение операции.

### Постусловия

- перевод имеет уникальный `transferId`;
- операция выполнена один раз;
- итоговый статус сохранён;
- сведения доступны для аудита.

---

## 6. UC-03-A1. Повторный запрос

1. Mobile App повторно отправляет запрос с тем же `Idempotency-Key`.
2. Transfer Service обнаруживает ранее зарегистрированную операцию.
3. Новая операция не создаётся.
4. Повторное финансовое движение не инициируется.
5. Система возвращает существующий перевод.

---

## 7. UC-03-A2. Недостаточно средств

1. При серверной проверке выявляется недостаточный доступный остаток.
2. Финансовая операция не создаётся или не передаётся на исполнение.
3. Система возвращает `INSUFFICIENT_FUNDS`.

---

## 8. UC-03-A3. Недоступный счёт

1. Система определяет, что один из счетов не допускает требуемую операцию.
2. Перевод не передаётся в Core Banking System.
3. Возвращается соответствующий код недоступности.

---

## 9. UC-03-A4. Timeout после передачи в Core Banking

Это принципиально отличный случай от обычного технического отказа.

1. Transfer Service передал операцию в Core Banking System.
2. Ответ не получен в установленное время.
3. Система не должна автоматически считать операцию неуспешной, если неизвестно, была ли она фактически исполнена.
4. Перевод остаётся в состоянии, требующем уточнения результата.
5. Выполняется повторное получение статуса или reconciliation согласно интеграционному контракту.

В минимальной модели статусов кейса отдельное состояние для данного сценария не вводится. Для production-решения рекомендуется согласовать состояние типа `UNKNOWN` / `PENDING_CONFIRMATION`.

---

## 10. UC-04. Получение статуса

**Основной актор:** Клиент  
**Цель:** определить текущее состояние ранее созданной операции.

### Основной сценарий

1. Mobile App передаёт `transferId`.
2. Backend определяет клиента.
3. Transfer Service находит операцию.
4. Система проверяет право клиента на просмотр операции.
5. Возвращает текущее состояние.

### Альтернативы

- перевод не найден — `TRANSFER_NOT_FOUND`;
- операция принадлежит другому клиенту — ответ без раскрытия существования чужой операции;
- временная техническая ошибка — `INTERNAL_ERROR` / `SERVICE_UNAVAILABLE`.

---

## 11. Жизненный цикл операции

Базовая модель:

```text
CREATED
   |
   v
PROCESSING
  /     \
 v       v
COMPLETED FAILED
```

Для реальной асинхронной интеграции рекомендуется дополнительно проработать состояния неопределённого результата и механизм reconciliation.

---

## 12. Спецификация диаграмм

### BPMN

Диаграмма должна показать:

- действия клиента;
- Mobile App;
- backend;
- проверки;
- выполнение в Core Banking;
- успешный и неуспешный исход.

### Sequence Diagram

Участники:

```text
Client
Mobile App
Banking Backend
Account Service
Transfer Service
Core Banking System
```

Основная последовательность соответствует UC-03.

### State Diagram

Необходимо отразить базовые состояния и разрешённые переходы из раздела 11.
