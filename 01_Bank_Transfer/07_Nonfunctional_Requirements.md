# 07. Нефункциональные требования

## 1. Назначение документа

Документ описывает нефункциональные требования к концептуальному решению перевода между собственными счетами клиента.

Указанные численные значения являются целевыми параметрами портфолио-кейса и в реальном проекте должны подтверждаться владельцем продукта, архитектором, эксплуатацией и информационной безопасностью.

---

## 2. Безопасность

### NFR-SEC-01. Аутентификация

Все пользовательские API должны быть доступны только в контексте аутентифицированной сессии.

### NFR-SEC-02. Авторизация на уровне объекта

Для каждого запроса, содержащего `accountId` или `transferId`, система должна проверять право клиента на доступ к соответствующему объекту.

### NFR-SEC-03. Недоверие к клиентскому приложению

`clientId`, права на счёт, доступный остаток и статус счёта должны определяться серверной частью либо доверенными внутренними системами.

### NFR-SEC-04. Transport security

Передача пользовательских и финансовых данных должна выполняться только по защищённому соединению.

### NFR-SEC-05. Минимизация раскрытия

API не должен раскрывать:

- наличие чужого счёта;
- внутреннюю топологию;
- stack trace;
- SQL;
- секреты;
- внутренние токены.

### NFR-SEC-06. Секреты

Access token и иные секреты не должны записываться в application logs.

---

## 3. Целостность финансовой операции

### NFR-REL-01. Однократность пользовательской команды

Один пользовательский запрос не должен приводить к повторному финансовому движению.

### NFR-REL-02. Неопределённый результат

Timeout после передачи операции в Core Banking не должен автоматически трактоваться как отсутствие исполнения.

### NFR-REL-03. Reconciliation

Для операций без подтверждённого финального статуса должен существовать способ определить фактический результат через повторный status check или reconciliation.

### NFR-REL-04. State consistency

Изменение статуса должно выполняться атомарно относительно записи соответствующего факта выполнения в пределах Transfer Service.

---

## 4. Производительность

### NFR-PERF-01. Чтение счетов

При штатной нагрузке 95-й перцентиль ответа API получения счетов должен быть не более 1 секунды без учёта деградации внешних зависимостей.

### NFR-PERF-02. Валидация

95-й перцентиль предварительной валидации — не более 1 секунды.

### NFR-PERF-03. Принятие перевода

API создания перевода должен подтвердить принятие запроса не более чем за 2 секунды в 95% запросов при штатной нагрузке.

Требование относится к регистрации/принятию, а не обязательно к фактическому завершению проводки.

---

## 5. Доступность и устойчивость

### NFR-AVL-01

Недоступность истории или аналитических компонентов не должна приводить к повторному выполнению уже принятой финансовой операции.

### NFR-AVL-02

Временная недоступность зависимого сервиса должна приводить к контролируемой ошибке или отложенной обработке в зависимости от этапа операции.

### NFR-AVL-03

Retry должен применяться только к операциям, для которых подтверждена безопасная повторяемость.

---

## 6. Наблюдаемость

### NFR-OBS-01. Correlation

Каждый технический запрос должен иметь `traceId`.

### NFR-OBS-02. Business correlation

Все события жизненного цикла перевода должны быть доступны для поиска по `transferId`.

### NFR-OBS-03. Логи

Минимально логируются:

- получение команды;
- результат валидации;
- создание перевода;
- передача в Core Banking;
- изменение статуса;
- ошибка;
- результат reconciliation.

### NFR-OBS-04. Метрики

Рекомендуемые метрики:

- количество создаваемых переводов;
- success/failure rate;
- latency;
- количество timeout;
- количество повторных idempotent requests;
- операции без финального статуса;
- распределение ошибок по code.

### NFR-OBS-05. Alerting

Должны быть предусмотрены алерты на аномальный рост:

- `FAILED`;
- timeout;
- latency;
- операций без подтверждённого результата.

---

## 7. Аудит

### NFR-AUD-01

Для каждой зарегистрированной операции должна быть возможность определить:

- кто инициировал;
- когда;
- параметры операции;
- изменения статуса;
- итоговый результат.

### NFR-AUD-02

Audit trail не должен изменяться обычными пользовательскими операциями.

### NFR-AUD-03

Сроки хранения должны быть определены внутренними нормативами банка и применимыми требованиями законодательства. Конкретный срок в кейсе не задаётся.

---

## 8. Конфиденциальность данных

### NFR-PRV-01

В пользовательских ответах номера счетов отображаются в маскированном виде, если полный реквизит не требуется бизнес-сценарием.

### NFR-PRV-02

Логи не должны содержать избыточные персональные и платёжные данные.

### NFR-PRV-03

Доступ сотрудников поддержки к операционным данным должен соответствовать ролевой модели.

---

## 9. Масштабируемость

### NFR-SCL-01

Компоненты чтения счетов и получения статуса должны допускать горизонтальное масштабирование при условии сохранения консистентности операций.

### NFR-SCL-02

Идемпотентность не должна зависеть от локальной памяти одного экземпляра приложения.

---

## 10. Сопровождаемость

### NFR-MNT-01

Коды ошибок API должны быть стабильными и документированными.

### NFR-MNT-02

OpenAPI-контракт должен храниться версионно вместе с документацией решения.

### NFR-MNT-03

Breaking changes внешнего API должны приводить к выпуску новой major-версии.

### NFR-MNT-04

Бизнес-правила должны быть трассируемы до stakeholder/system requirements.

---

## 11. Тестируемость

Для каждого Must-requirement должны существовать:

- ожидаемый результат;
- негативный сценарий, если применимо;
- способ определить соответствие.

Критерии приёмки представлены в `08_Traceability_and_Acceptance.md`.
