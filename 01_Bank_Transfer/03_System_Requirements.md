# 03. Системные требования

## 1. Назначение документа

Документ содержит формализованные системные требования к функциональности перевода денежных средств между собственными счетами клиента.

Требования декомпозированы из stakeholder requirements, целей и Scope, зафиксированных в документах `01_Context_and_Stakeholder_Requirements.md` и `02_Goals_and_Scope.md`.

---

## 2. Принципы формулирования требований

Каждое требование:

- имеет уникальный идентификатор;
- описывает одно проверяемое свойство системы;
- не привязано к конкретной реализации, если это не требуется;
- должно быть однозначно проверяемым;
- имеет связь с источником или бизнес-правилом.

Приоритеты:

- **Must** — обязательное требование первой версии;
- **Should** — желательно реализовать в первой версии;
- **Could** — допустимо перенести на последующие итерации.

---

## 3. Бизнес-правила

### BR-01. Принадлежность счетов

Счёт списания и счёт зачисления должны принадлежать авторизованному клиенту.

### BR-02. Разные счета

Счёт списания и счёт зачисления не могут совпадать.

### BR-03. Допустимый статус счёта

Каждый счёт должен находиться в состоянии, допускающем соответствующую операцию списания или зачисления.

### BR-04. Валюта

В рамках первой версии оба счёта должны быть открыты в RUB.

### BR-05. Положительная сумма

Сумма перевода должна быть больше нуля.

### BR-06. Достаточность средств

Доступный остаток счёта списания должен быть не меньше суммы перевода.

### BR-07. Лимит операции

Сумма перевода не должна превышать применимый лимит.

### BR-08. Уникальность пользовательской операции

Повторная передача одного пользовательского действия не должна создавать новый перевод.

### BR-09. Уникальность перевода

Каждый зарегистрированный перевод должен иметь уникальный `transferId`.

### BR-10. Аудируемость

Для каждого зарегистрированного перевода должны сохраняться сведения, достаточные для идентификации операции и её итогового состояния.

---

## 4. Функциональные требования

### FR-01. Получение счетов клиента

**Приоритет:** Must  
**Источник:** SR-01, SR-02

Система должна предоставлять авторизованному клиенту перечень принадлежащих ему счетов, доступных для участия в переводе.

Для каждого счёта должны быть доступны как минимум:

- `accountId`;
- отображаемое название;
- маскированный номер;
- валюта;
- доступный остаток;
- статус;
- признак доступности списания;
- признак доступности зачисления.

---

### FR-02. Фильтрация доступных счетов

**Приоритет:** Must  
**Источник:** SR-02

Система не должна предлагать клиенту счёт как источник или получатель перевода, если соответствующая операция по счёту запрещена.

---

### FR-03. Проверка принадлежности счетов

**Приоритет:** Must  
**Источник:** SR-04, BR-01

Система должна проверять принадлежность обоих счетов авторизованному клиенту на серверной стороне.

Проверка не должна основываться только на данных, переданных клиентским приложением.

---

### FR-04. Проверка параметров перевода

**Приоритет:** Must  
**Источник:** SR-03

До передачи операции на исполнение система должна проверить:

- наличие обоих счетов;
- различие счетов;
- статус счетов;
- валюту;
- сумму;
- доступный остаток;
- применимый лимит.

---

### FR-05. Предварительная валидация

**Приоритет:** Should  
**Источник:** SR-03

Система должна предоставлять возможность проверить параметры перевода до окончательного создания операции.

Результат должен содержать признак допустимости операции и, при отказе, машиночитаемую причину.

---

### FR-06. Создание перевода

**Приоритет:** Must  
**Источник:** SR-01

После подтверждения клиентом система должна зарегистрировать перевод и присвоить ему уникальный `transferId`.

На момент регистрации должны быть зафиксированы:

- клиент;
- счёт списания;
- счёт зачисления;
- сумма;
- валюта;
- время создания;
- idempotency key.

---

### FR-07. Идемпотентность создания

**Приоритет:** Must  
**Источник:** SR-05, BR-08

Повторный запрос на создание перевода с тем же `Idempotency-Key` в рамках одного клиента не должен создавать новую операцию.

Система должна вернуть результат ранее зарегистрированной операции.

---

### FR-08. Передача операции на исполнение

**Приоритет:** Must  
**Источник:** SR-01

После успешной регистрации Transfer Service должен инициировать выполнение финансовой операции в Core Banking System.

---

### FR-09. Управление статусом

**Приоритет:** Must  
**Источник:** SR-06

Система должна хранить текущее состояние перевода.

Базовые состояния:

- `CREATED`;
- `PROCESSING`;
- `COMPLETED`;
- `FAILED`.

---

### FR-10. Получение статуса перевода

**Приоритет:** Must  
**Источник:** SR-06

Система должна предоставлять возможность получить текущее состояние перевода по `transferId`.

Доступ к операции разрешён только владельцу соответствующего перевода или авторизованным внутренним системам.

---

### FR-11. Фиксация успешного результата

**Приоритет:** Must  
**Источник:** SR-06, SR-08

После подтверждения успешного выполнения Core Banking System перевод должен получить статус `COMPLETED` с фиксацией времени завершения.

---

### FR-12. Фиксация неуспешного результата

**Приоритет:** Must  
**Источник:** SR-07, SR-08, SR-09

При невозможности выполнить перевод система должна:

- установить состояние `FAILED`, если операция уже была зарегистрирована;
- сохранить код причины;
- сохранить техническую информацию, достаточную для диагностики;
- вернуть клиентскому приложению безопасное для отображения сообщение.

---

### FR-13. История операции

**Приоритет:** Should  
**Источник:** SR-06, SR-08

Завершённая операция должна быть доступна в истории операций клиента.

---

### FR-14. Корреляция технических событий

**Приоритет:** Must  
**Источник:** SR-09

Все технические события, относящиеся к переводу, должны быть связаны с `transferId` либо другим однозначно сопоставимым correlation identifier.

---

## 5. Правила валидации

| ID | Проверка | Результат при нарушении |
|---|---|---|
| VAL-01 | sourceAccountId существует | ACCOUNT_NOT_FOUND |
| VAL-02 | destinationAccountId существует | ACCOUNT_NOT_FOUND |
| VAL-03 | оба счёта принадлежат клиенту | ACCOUNT_ACCESS_DENIED |
| VAL-04 | счета различаются | SAME_ACCOUNT |
| VAL-05 | счёт списания доступен | SOURCE_ACCOUNT_UNAVAILABLE |
| VAL-06 | счёт зачисления доступен | DESTINATION_ACCOUNT_UNAVAILABLE |
| VAL-07 | обе валюты RUB | UNSUPPORTED_CURRENCY |
| VAL-08 | amount > 0 | INVALID_AMOUNT |
| VAL-09 | availableBalance >= amount | INSUFFICIENT_FUNDS |
| VAL-10 | сумма в пределах лимита | TRANSFER_LIMIT_EXCEEDED |

---

## 6. Требования к состояниям

Разрешённые переходы:

```text
CREATED -> PROCESSING
PROCESSING -> COMPLETED
PROCESSING -> FAILED
```

Переход из `COMPLETED` в другое состояние в рамках текущего Scope не допускается.

Повторное выполнение операции в состоянии `COMPLETED` не допускается.

---

## 7. Требования к ошибкам

Каждый бизнес- или технический отказ API должен содержать:

- стабильный машиночитаемый `code`;
- пользовательски безопасное `message`;
- `traceId` или иной идентификатор запроса, если ошибка требует диагностики.

Внешний API не должен возвращать stack trace, внутренние адреса сервисов, SQL-текст или иные детали внутренней реализации.

---

## 8. Открытые вопросы

Перед production-реализацией необходимо согласовать:

- набор разрешённых типов счетов;
- правила лимитов;
- необходимость дополнительного подтверждения;
- модель синхронного или асинхронного исполнения;
- правила retry и reconciliation;
- требования к отображению истории;
- сроки хранения операционных и аудиторских данных.
