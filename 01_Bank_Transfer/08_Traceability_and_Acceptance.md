# 08. Трассируемость и критерии приёмки

## 1. Назначение документа

Документ связывает требования заинтересованных сторон с системными требованиями, бизнес-правилами, use cases и критериями приёмки.

Цель — показать, что ключевые требования имеют источник и проверяемый результат.

## 3. Критерии приёмки

### AC-01. Успешный перевод

**Given** клиент авторизован  
**And** оба рублёвых счёта принадлежат клиенту  
**And** счета доступны для соответствующих операций  
**And** доступный остаток достаточен  
**And** лимит не превышен  
**When** клиент подтверждает перевод на 10 000 RUB  
**Then** создаётся один перевод  
**And** перевод получает уникальный `transferId`  
**And** операция передаётся на исполнение  
**And** после подтверждения Core Banking получает статус `COMPLETED`.

---

### AC-02. Получение счетов

**Given** у клиента есть счета, доступные для перевода  
**When** Mobile App запрашивает список счетов  
**Then** возвращаются только счета клиента  
**And** для каждого счёта доступны валюта, доступный остаток и признаки допустимых операций.

---

### AC-03. Недостаточно средств

**Given** доступный остаток счёта равен 5 000 RUB  
**When** клиент пытается перевести 10 000 RUB  
**Then** финансовая операция не исполняется  
**And** возвращается `INSUFFICIENT_FUNDS`.

---

### AC-04. Совпадающие счета

**Given** sourceAccountId равен destinationAccountId  
**When** выполняется валидация  
**Then** операция отклоняется  
**And** возвращается `SAME_ACCOUNT`.

---

### AC-05. Превышен лимит

**Given** для клиента применим лимит ниже указанной суммы  
**When** выполняется проверка  
**Then** операция отклоняется  
**And** возвращается `TRANSFER_LIMIT_EXCEEDED`.

---

### AC-06. Чужой счёт

**Given** переданный accountId не принадлежит авторизованному клиенту  
**When** выполняется валидация или создание перевода  
**Then** операция не выполняется  
**And** система не раскрывает клиенту данные чужого счёта.

---

### AC-07. Идемпотентный повтор

**Given** запрос уже создал перевод с idempotency key K  
**When** повторно отправляется тот же запрос с K  
**Then** новый перевод не создаётся  
**And** повторное финансовое движение не выполняется  
**And** возвращается существующая операция.

---

### AC-08. Повтор ключа с другими параметрами

**Given** idempotency key K уже использован для одной операции  
**When** K используется с изменённой суммой или счетами  
**Then** запрос отклоняется как конфликт  
**And** существующая операция не изменяется.

---

### AC-09. Получение статуса

**Given** клиент ранее создал перевод  
**When** запрашивает состояние по `transferId`  
**Then** получает актуальный статус собственной операции.

---

### AC-10. Аудит

**Given** перевод был зарегистрирован  
**When** уполномоченная система выполняет аудит  
**Then** возможно определить клиента, счета, сумму, время создания, основные изменения состояния и итоговый результат.

---

### AC-11. Диагностика

**Given** перевод завершился ошибкой  
**When** служба сопровождения выполняет поиск по `transferId`  
**Then** доступны correlation data и код причины, достаточные для локализации этапа отказа без раскрытия секретов.

---

## 4. Негативные проверки

Минимальный набор:

| Test | Ожидаемый результат |
|---|---|
| amount = 0 | INVALID_AMOUNT |
| amount < 0 | INVALID_AMOUNT |
| source = destination | SAME_ACCOUNT |
| счёт не существует | controlled error |
| чужой счёт | access denied без раскрытия данных |
| unsupported currency | UNSUPPORTED_CURRENCY |
| blocked source | ACCOUNT_UNAVAILABLE |
| insufficient balance | INSUFFICIENT_FUNDS |
| limit exceeded | TRANSFER_LIMIT_EXCEEDED |
| повтор idempotency key | возвращается исходная операция |
| key + другие параметры | 409 IDEMPOTENCY_KEY_REUSED |

## 5. Приёмка API

Перед приёмкой должны быть проверены:

- соответствие OpenAPI фактическому контракту;
- обязательность заголовков;
- типы данных;
- HTTP status codes;
- формат ошибок;
- проверка object-level authorization;
- идемпотентность;
- отсутствие чувствительных внутренних данных в response.

---

## 6. Definition of Done для кейса

Документация кейса считается завершённой, когда:

- stakeholder requirements зафиксированы;
- Scope определён;
- Must functional requirements имеют идентификаторы;
- основной и негативные сценарии описаны;
- API-контракт существует в OpenAPI;
- логическая модель данных описана;
- NFR определены;
- трассировка SR -> FR/BR -> UC -> AC заполнена;
- подготовлены или специфицированы основные диаграммы;
- отсутствуют противоречия в идентификаторах и терминологии.

---

## 7. Известные ограничения концептуальной модели

До production design открытыми остаются:

- точные лимиты;
- типы поддерживаемых счетов;
- способ дополнительного подтверждения;
- конкретный протокол интеграции с Core Banking;
- поведение при неопределённом результате;
- SLA/SLO;
- требования к retention;
- AML/antifraud.

Они намеренно не выдумываются в рамках портфолио и должны уточняться у соответствующих stakeholders в реальном проекте.
