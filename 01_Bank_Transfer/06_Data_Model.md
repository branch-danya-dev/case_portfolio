# 06. Модель данных

## 1. Назначение документа

Документ описывает концептуальную и логическую модель данных, необходимую для поддержки перевода между собственными счетами клиента.

Модель не является физической схемой конкретной СУБД и не предполагает, что все сущности обязаны храниться в одном сервисе или одной базе данных.

---

## 2. Принципы

- идентификаторы являются непрозрачными значениями;
- денежные суммы хранятся в decimal-типе с фиксированной точностью;
- время хранится в UTC;
- данные клиента и счетов могут быть master-data других систем;
- Transfer Service хранит только данные, необходимые для жизненного цикла перевода и аудита;
- чувствительные реквизиты не дублируются без необходимости.

---

## 3. Основные сущности

### Client

Логическое представление клиента банка.

| Атрибут | Тип | Обяз. | Описание |
|---|---|---:|---|
| clientId | string | да | Уникальный идентификатор клиента |
| status | enum | да | Статус клиентской записи |

В рамках кейса Client является внешней/master сущностью и не проектируется детально.

---

### Account

Логическое представление банковского счёта.

| Атрибут | Тип | Обяз. | Описание |
|---|---|---:|---|
| accountId | string | да | Уникальный идентификатор счёта |
| clientId | string | да | Владелец счёта |
| accountType | enum | да | Тип счёта |
| currency | string(3) | да | ISO-код валюты |
| status | enum | да | Состояние счёта |
| availableBalance | decimal | да | Доступный остаток |
| canDebit | boolean | да | Допустимо списание |
| canCredit | boolean | да | Допустимо зачисление |

Account является master-data Account Service / Core Banking. Transfer Service может использовать snapshot отдельных атрибутов на момент операции, но не становится источником истины по счёту.

---

### Transfer

Центральная сущность кейса.

| Атрибут | Тип | Обяз. | Описание |
|---|---|---:|---|
| transferId | string | да | Уникальный идентификатор перевода |
| clientId | string | да | Инициатор и владелец обоих счетов |
| sourceAccountId | string | да | Счёт списания |
| destinationAccountId | string | да | Счёт зачисления |
| amount | decimal | да | Сумма |
| currency | string(3) | да | Валюта |
| status | enum | да | Текущее состояние |
| idempotencyKey | string | да | Ключ пользовательской команды |
| externalOperationId | string | нет | Идентификатор операции в Core Banking |
| failureCode | string | нет | Код неуспешного выполнения |
| createdAt | timestamp | да | Время создания |
| updatedAt | timestamp | да | Время последнего изменения |
| completedAt | timestamp | нет | Время завершения |

---

### TransferStatusHistory

История смены состояния операции.

| Атрибут | Тип | Обяз. | Описание |
|---|---|---:|---|
| historyId | string | да | Идентификатор записи |
| transferId | string | да | Ссылка на перевод |
| fromStatus | enum | нет | Предыдущее состояние |
| toStatus | enum | да | Новое состояние |
| reasonCode | string | нет | Причина перехода |
| changedAt | timestamp | да | Время изменения |

История позволяет восстановить жизненный цикл операции независимо от текущего значения `Transfer.status`.

---

### IdempotencyRecord

Логическая запись, обеспечивающая защиту от повторного создания.

| Атрибут | Тип | Обяз. | Описание |
|---|---|---:|---|
| clientId | string | да | Клиент |
| idempotencyKey | string | да | Ключ команды |
| requestHash | string | да | Отпечаток значимых параметров |
| transferId | string | да | Созданная операция |
| createdAt | timestamp | да | Время регистрации |

Уникальное ограничение:

```text
UNIQUE(clientId, idempotencyKey)
```

---

### AuditEvent

Логическое представление аудиторского события.

| Атрибут | Тип | Обяз. | Описание |
|---|---|---:|---|
| eventId | string | да | Идентификатор события |
| transferId | string | нет | Связанный перевод |
| clientId | string | нет | Клиент |
| eventType | string | да | Тип события |
| result | string | да | Результат |
| occurredAt | timestamp | да | Время события |
| traceId | string | нет | Техническая корреляция |

Физически audit trail может храниться во внешней платформе журналирования.

---

## 4. Связи

Концептуально:

```text
Client 1 ---- N Account

Client 1 ---- N Transfer

Account 1 ---- N Transfer (source)
Account 1 ---- N Transfer (destination)

Transfer 1 ---- N TransferStatusHistory
Transfer 1 ---- 0..1 IdempotencyRecord
Transfer 1 ---- N AuditEvent
```

---

## 5. Ограничения целостности

### DM-01

`sourceAccountId != destinationAccountId`.

### DM-02

`amount > 0`.

### DM-03

`currency = RUB` в рамках текущего Scope.

### DM-04

Пара `(clientId, idempotencyKey)` уникальна.

### DM-05

`completedAt` обязательно для `COMPLETED`.

### DM-06

`failureCode` обязателен для бизнес-значимых состояний `FAILED`, если причина определена системой.

### DM-07

Изменение статусов должно соответствовать разрешённой state model.

---

## 6. Денежные значения

Для денежных сумм запрещено использование binary floating-point типов.

На логическом уровне:

```text
amount DECIMAL(p, 2)
```

Фактическая точность должна определяться стандартами и валютной моделью банка.

---

## 7. Конкурентность

Проверка доступного остатка перед созданием операции не является достаточной гарантией наличия средств в момент исполнения.

Финальное решение о возможности списания должно приниматься системой, контролирующей фактический баланс и конкурентные операции.

Это предотвращает race condition:

```text
T1: проверка balance = 15 000
T2: проверка balance = 15 000
T1: списание 10 000
T2: попытка списания 10 000
```

Transfer Service не должен считать предварительно полученный balance блокировкой денежных средств.

---

## 8. Хранение snapshot-данных

Для аудита допускается сохранять значения, актуальные на момент создания перевода, например:

- currency;
- amount;
- идентификаторы счетов.

При необходимости отображаемые названия или маскированные реквизиты могут сохраняться отдельно как snapshot, но не должны использоваться как master-data.

Для итогового портфолио рекомендуется нарисовать ERD со следующими сущностями:
